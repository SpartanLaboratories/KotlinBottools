Lifecycles across systems

    
The phase's units in landing order, one repository's rewrite, and the life of the workspace.

    

      
The phase, unit by unit each unit lands through its own pull request

        
  1. preparation
  2. transfer rehearsal
  3. KotlinBottools rewrite and swap
  4. repository hygiene
  5. KotlinBottools made public
  6. GKB2 and GKB
  7. BotTools, TrumpBot and Support
  8. residual report and cleanup

        
No unit stops for a person before a push, a force-push or the visibility change: every stop is a failed verification, and nothing lands on KotlinBottools while unit 3 runs (architecture §8, §11).

      
One repository's rewrite each stage a gate

        
  1. list proof, pre-run checks
  2. positive control
  3. one filter-repo invocation
  4. post-run checks
  5. push preparation
  6. push, on request
  7. per-ref verification
  8. fresh mirror, exit tests
  9. residual probes

        
A failure before the push discards the mirror and changes nothing on GitHub; after it, the unit reports the tally and never repeats the push blindly (architecture §6.4, §8).

      
The workspace and the data folder both outside every repository

        
  1. WS and DATA created, access checked
  2. data copied, COPY-VERIFIED
  3. backups, mirrors and fresh mirrors in WS
  4. DATA re-verified
  5. tools copied into DATA
  6. WS deleted, deletion confirmed

        
DATA outlives the phase. Nothing under it is committed, printed or quoted; the records and the report carry counts only (architecture §5, §6.7).
