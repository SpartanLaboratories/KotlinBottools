# The secret-scan workflow on GitHub's hosted runner: do its pins still resolve and does it still run as written?

Read on 2026-11-11. The earlier findings that give the workflow ([§6.9 of the gitleaks findings](../../research/gitleaks-local-and-ci.md#69-the-workflow-githubworkflowssecret-scanyml), 4532 bytes, sha256 `b518b52717073c5667302a113814cb1a76f5aa8c9188a7d7e41346278d772c2e`) were verified on 2026-10-20 and 2026-10-21.

## 1. Question

Does `.github/workflows/secret-scan.yml` run as written on a hosted `ubuntu-latest` runner in a private repository of a GitHub Free organisation (read-only default token, Actions enabled for all actions), and do its pins still resolve to what they check: `actions/checkout` commit `3d3c42e5aac5ba805825da76410c181273ba90b1` (v7.0.1) and the gitleaks 8.30.1 Linux x64 archive with sha256 `551f6fc83ea457d62a0d98237cbad105af8d557003051f41f3e7ca7b3f2470eb`? Requirements: no redesign; a change is reported only if the platform forces one.

Idiomatic Kotlin does not bear on this question.

## 2. Bottom line

- **No platform change forces an edit. The file can be committed byte for byte.** Every pin still resolves (checkout tag, checkout commit, gitleaks asset URL, checksums file, asset digest), the checkout action's runtime (`node24`) is the runner's current default with no deprecation, no newer v7 or gitleaks release exists, and nothing GitHub changed since 2026-10-20 touches a workflow that uses `push`, `pull_request` (same repository), `workflow_dispatch`, `concurrency` and `contents: read`.
- **`ubuntu-latest` is mid-migration from Ubuntu 24.04 to Ubuntu 26.04** (rolling out 2026-10-19, to complete 2026-11-19), so the first run can land on either image. Both images have Python 3.12.3 or 3.14.4, Git 2.56.0, `curl`, `tar` and `coreutils`; the gitleaks binary is a static ELF that needs no system library; the wrapper imports only standard-library modules. The one part not identical on the two images is `sha256sum`: Ubuntu 26.04 ships Rust coreutils (uutils 0.8.0) by default for everything except `cp`, `mv` and `rm`, and the image's package list does not say which `sha256sum` it carries. The uutils 0.8.0 source supports the exact invocation (`--check --strict -`, a line `<hash>  <path>`), and a failure of that step is loud (the shell has `set -euo pipefail`), so the worst case is a red first run, not a false pass.
- **A `fetch-depth: 0` checkout holds** `refs/remotes/origin/*` (every branch), `refs/tags/*` and, on a `pull_request` event only, `refs/remotes/pull/<n>/merge` (the merge commit, checked out detached). On a `push` to `main` it holds the same branches and tags plus a local `main`. `git log --all` therefore counts the whole of `main`, every other branch of the repository and every tag, in both events; it does not reach other pull requests' `refs/pull/*` refs.
- **Newer releases exist for neither pin's family that matter:** checkout's newest release is still v7.0.1 (the tag still points at the pinned commit; one later commit on `main` is a changelog edit). gitleaks' newest release is still v8.30.1; the 26 commits on `master` since touch only documentation, dependencies and CI files; issues #2129 and #1981 (the silent pass of `gitleaks git`) are still open, so the wrapper's guard remains necessary.
- **Minutes:** a private repository of a GitHub Free organisation draws on $12 USD of included compute per month, which is 2,000 standard Linux minutes at $0.006 per minute (arithmetic from the documented rate; the page states the dollar amount). The job's timeout is 15 minutes.

### 3.2 Tools on the two images (primary source, image versions of 2026-11-01; claims 3, 4)

| Tool | Ubuntu 24.04 (image 20261101.360.1) | Ubuntu 26.04 (image 20261101.186.1) |
|---|---|---|

- `tomllib` needs Python 3.11 or newer (earlier claim 25); both images meet it. The wrapper (`secret_scan.py`) imports only `argparse`, `base64`, `collections`, `json`, `os`, `re`, `secrets`, `string`, `subprocess`, `sys` and `tomllib` (observed), parses under the Python 3.11 grammar (observed with `ast.parse(..., feature_version=(3, 11))`), and was verified on Python 3.14.7 (the earlier findings). None of those modules was removed in 3.12 to 3.14.
- Git is 2.56.0 on both images, one minor version newer than the 2.55.0 the earlier findings recorded. The 2.56.0 release notes list nothing that touches `git log`, `git clone --mirror`, `git init -b`, `git merge` or `git update-ref` (primary source, release notes read for these terms).
- **`sha256sum` on Ubuntu 26.04 (the one open point).** Canonical's post on Rust coreutils says it "shipped rust-coreutils as the default in Ubuntu 25.10", included uutils 0.8.0 in 26.04, and that only `cp`, `mv` and `rm` "continue to be provided by GNU coreutils in 26.04" (primary source; claim 5). The runner image's package list shows the `coreutils` package version `9.5-1ubuntu2+0.0.0~ubuntu25` and no separate Rust coreutils entry, so which implementation answers `sha256sum` on the hosted image is not stated by the image documentation (see Gaps). What the workflow does with it is the most common form: `echo "<hash>  <path>" | sha256sum --check --strict -`. In uutils 0.8.0 (`uucore/src/lib/features/checksum/validate.rs` and `checksum_common/src/cli.rs`) the `--check`, `--strict` and `--ignore-missing` options exist, a checksum-file name of `-` reads standard input, the standard text-mode separator is two spaces (`strip_prefix(b"  ")`), `--strict` turns improperly formatted lines into a failure, and a mismatch or missing file is a failure (claim 6). A reported uutils defect (a malformed free-text line before the first digest line makes later lines read in the single-space format) needs a malformed first line and does not apply to a single well-formed line. Reading the source is not the same as running it on a 26.04 runner; the first run on the pull request is that test.
- The gitleaks Linux x64 binary has no `PT_INTERP` or `PT_DYNAMIC` program header: it is statically linked, so the operating-system image does not matter to it (observed on the downloaded archive's `gitleaks`, machine type x86-64). `gitleaks version` prints `version.Version`, which the release build sets from goreleaser's `{{.Version}}` (no `v` prefix), so the comparison with `8.30.1` holds (claim 14).
- A concurrent incident does not touch this workflow: on 2026-11-11 Ubuntu mirror host names failed to resolve on all hosted Ubuntu images because of a Canonical outage ([issue 15296](https://github.com/actions/runner-images/issues/15296), open), with GitHub's own hosts resolving normally in the same jobs. The workflow uses no `apt`.

### 3.4 The refs a `fetch-depth: 0` checkout holds (primary source, source at the pinned commit; claim 9)

`getRefSpecForAllHistory` in `src/ref-helper.ts` fetches `+refs/heads/*:refs/remotes/origin/*` and `+refs/tags/*:refs/tags/*`; for a ref starting `refs/pull/` it adds `+<commit>:refs/remotes/pull/<n>/merge`. `getCheckoutInfo` then checks out:

| Event | `GITHUB_REF` | After checkout (`git log --all` sees) |
|---|---|---|
| `pull_request` (same repository) | `refs/pull/<n>/merge`, `GITHUB_SHA` is the merge commit | `HEAD` detached at `refs/remotes/pull/<n>/merge`; `refs/remotes/origin/<every branch, including the pull request's>`; `refs/tags/*`. No local branch. |
| `push` to `main` | `refs/heads/main`, `GITHUB_SHA` is the pushed tip | local `main` (start point `refs/remotes/origin/main`); `refs/remotes/origin/*`; `refs/tags/*`. |
| `workflow_dispatch` (once the file is on the default branch) | the chosen branch or tag | the same as `push`; a tag ref is checked out by its ref. |

Consequences for the wrapper: `--refs all` is `--all` and covers every row above; a `--branches --tags` count would not include `refs/remotes/pull/<n>/merge` or the remote-tracking branches, which is why the canary uses a mirror and the workflow scans the real checkout with `--refs all` only. Other pull requests' `refs/pull/<m>/head` refs and branches already deleted on the remote are not fetched. When the pull request has a merge conflict GitHub does not run `pull_request` workflows at all (claim 10), so the unit's branch must stay mergeable with `main` for its first run to start. The "Run workflow" button for `workflow_dispatch` exists only once the file is on the default branch, so the first run is the `pull_request` one.

## 4. How comparable projects do it

- **GitHub's hardening guidance** (claim 18): pin actions to a full-length commit SHA, keep the default token read-only. The workflow does both. **OpenSSF Scorecard**'s `Pinned-Dependencies` check says "For GitHub workflows used in building and releasing your project, pin dependencies by hash" (claim 19); it does not address downloaded binaries, so verifying a downloaded scanner by a constant checksum in the reviewed file is the stricter practice and matches the earlier findings.
- **gitleaks' own repository** at v8.30.1 uses `actions/checkout@v3` with `fetch-depth: 0` and its own action; the workflow here performs the same `gitleaks git` run with a verified binary (earlier findings, §4).
- **Runner labels.** The README's own mitigation for an unwanted migration is a fixed label (`ubuntu-24.04`). Projects that care about exact tool versions fix the label; projects whose steps depend only on `bash`, `git`, `python3` and a static binary conventionally keep `-latest`, which is also what the organisation's `ci.yml` files do (earlier findings, §3.11). The design keeps `ubuntu-latest`.

## 5. Pitfalls and regrets

1. **Label drift during the roll-out.** Until 2026-11-19 two successive runs of the same commit can run on different images. A first run that passes on 24.04 proves nothing about 26.04 and the reverse; a re-run is the cheap test.
2. **The hosted image changes under a fixed workflow.** Git moved from 2.55.0 to 2.56.0 in three weeks. The workflow holds only the binary and the action fixed; everything else (`python3`, `git`, `sha256sum`) floats with the image. Nothing in the file depends on a minor version.
3. **A merge conflict silently skips `pull_request` workflows.** The check then never reports, which on a repository without branch protection means nothing blocks a merge; on this repository the merge waits for a passed run, so the branch must be mergeable with `main`.
4. **Counting refs.** A pull request run's local checkout has no `refs/heads/*`; a scan that uses `--branches` on that checkout would see no commits at all, because the checkout has no local branch. The workflow uses `--all` for that reason.
5. **A required status check is not available while the repository is private** (branch protection and rulesets), so the green run is a convention enforced by the merge procedure, not by the platform.

## 6. Recommendation for this repository

Commit the workflow exactly as §6.9 gives it. No platform change since 2026-10-20 forces an edit: the pins resolve, the checkout action's `node24` runtime is current, gitleaks has no newer release, the hosted image provides every tool the steps call on both Ubuntu 24.04 and Ubuntu 26.04, and the event, permission and concurrency behaviour is unchanged. Keep the checkout and gitleaks pins: no release exists that fixes anything that bears on this use, and a version change would also change the verified baseline of the canary and the scans. Keep `ubuntu-latest`: a pin to a fixed image would be a design change, and the only unverified point (the `sha256sum` implementation on 26.04) fails closed.

Before the pull request is opened, the branch should be a descendant of the current `main` so GitHub can build the merge ref. If the first run is red at the "Install gitleaks" step on an Ubuntu 26.04 image with a checksum-tool message, treat that as the one new decision for the owner (pin `runs-on: ubuntu-24.04`, or rewrite the check without `--strict -`); there is no evidence today that it will happen. A red run on any other step is not explained by the platform changes found here.
