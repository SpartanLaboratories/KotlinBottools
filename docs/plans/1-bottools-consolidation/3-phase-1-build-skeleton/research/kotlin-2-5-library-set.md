# The library set on Kotlin 2.5: jda-ktx, kotlinx-serialization-json and kotlinx-coroutines beside JDA 6.7.0

Currency date of every finding: 2026-11-22 (Maven Central metadata, POMs and Gradle Module Metadata read as text; GitHub releases, files and issues read through the API). No build, compiler run or jar inspection was done; where a fact would need one it is marked as carried forward or as an inference.

## 1. Question

Which versions of jda-ktx, kotlinx-serialization-json and kotlinx-coroutines (core and test) are the newest that work together with each other, with JDA 6.7.0 and with the Kotlin Gradle plugin 2.5.0-RC, and does JDA have to move?

The answer has to meet these requirements, stated as facts about the build:

- The library builds with the Kotlin Gradle plugin 2.5.0-RC (a pre-release published 2026-11-11; 2.5.0 is not out) and moves to 2.5.0 on release; the serialization compiler plugin is at the same version. It compiles at language version 2.5 and API version 2.5, so a Kotlin 2.5 compiler reads its dependencies.
- The JDK toolchain and the Java floor are 21: a `verifyJavaFloor` check fails when a dependency on a published module's runtime classpath carries class files above major version 65 or declares a higher `org.gradle.jvm.version`.
- JDA stays at 6.7.0 unless the newest jda-ktx needs a newer JDA; if it does, that is reported with what would move.
- `bottools-core` declares JDA and kotlinx-coroutines as `api` and jda-ktx as `implementation`; an integration-set test in `bottools-core` compiles references to `RestAction.await()` and `JDABuilder.injectKTX()` and loads jda-ktx's `CoroutineEventManager` as JDA's `IEventManager`; `bottools-stats` and `bottools-plugins` use kotlinx-serialization-json with the compiler plugin and an integration-set test encodes and decodes a `@Serializable` probe; tests use kotlinx-coroutines-test. WebTools, a later dependency of `bottools-http`, brings kotlinx-coroutines 1.10.2. The organisation's kotlin-logging version is 8.0.7 (covered elsewhere).

## 2. Bottom line

- **Recommended set, newest of each, no conflict:**
  - JDA **6.7.0** (unchanged; it is still JDA's newest release);
  - jda-ktx **0.15.0** (replaces 0.14.2; the only release after 0.14.2);
  - kotlinx-coroutines-core and kotlinx-coroutines-test **1.11.0** (replaces 1.10.2; the newest stable release);
  - kotlinx-serialization-json **1.13.0** (replaces 1.9.0; the newest release, built on Kotlin 2.4.10).
- **JDA does not move.** jda-ktx 0.15.0 declares JDA 6.5.0 as a plain runtime requirement; Gradle's greatest-version rule lifts it to the `api` pin of 6.7.0. The one jda-ktx build file is at JDA 6.5.0, and the 6.5.0-to-6.7.0 source diff of JDA adds API and removes nothing jda-ktx's source touches. If a later JDA were wanted, 6.7.0 is already the newest, so nothing newer exists to move to.
- **Nothing in the set needs more than Kotlin 2.4.** The newest `kotlin-stdlib` any of the four requires is 2.4.10 (serialization-json 1.13.0); jda-ktx 0.15.0 requires 2.4.0 and coroutines 1.11.0 requires 2.2.20. The Kotlin Gradle plugin adds `kotlin-stdlib` at its own version, so the resolved `kotlin-stdlib` is 2.5.0-RC now and 2.5.0 after the move: equal to the compiler, never above it. Kotlin 2.5.0-RC reads class metadata up to 2.6.0, so metadata 2.2 (coroutines) and 2.4 (jda-ktx, serialization-json) are readable.
- **Java floor holds by the libraries' build files:** JDA, jda-ktx, coroutines and serialization-json all compile to JVM target 1.8. JDA and jda-ktx also publish `org.gradle.jvm.version` 8; coroutines and serialization-json publish no `org.gradle.jvm.version` on their JVM variants, so the metadata arm of `verifyJavaFloor` cannot flag them and only the class-file arm can. Class-file majors were not read from the jars (see Gaps).
- **coroutines 1.11.0 resolves across the whole graph.** `bottools-core`'s `api` pin, jda-ktx 0.15.0 and coroutines-test 1.11.0 all ask for 1.11.0; WebTools asks plain 1.10.2 (a floor), so the greatest version, 1.11.0, wins. That holds only while no module declares `strictly` on coroutines.
- **Rejected:** serialization-json 1.12.0 (a breaking exception-wrapping change its own notes say to skip); keeping jda-ktx 0.14.2 or coroutines 1.10.2 (valid, but older, and they pin the set to the Kotlin 2.2 era for no reason on a 2.5 compiler).

## 3. Findings

Tiers: **Established** = release metadata, a standard or a maintainer's own statement; **Common practice** = what mature libraries visibly do; **Inference** = my reading, stated as such.

### F2. The symbols the library uses exist in 0.15.0's source (Established; source at `4fc12af`)

At the commit that carries `version = "0.15.0"`:

- `coroutines/coroutines.kt`: `suspend fun <T> RestAction<T>.await(): T = submit().await()`, plus a `Task<T>.await()` overload.
- `jdabuilder/inject.kt`: `fun JDABuilder.injectKTX(timeout: Duration = Duration.INFINITE) = setEventManager(CoroutineEventManager(timeout=timeout))` and the `DefaultShardManagerBuilder.injectKTX` counterpart.
- `events/CoroutineEventManager.kt`: `open class CoroutineEventManager(scope: CoroutineScope = getDefaultScope(), var timeout: Duration = Duration.INFINITE) : IEventManager, CoroutineScope by scope`.

So the integration-set check named in the requirements (compile `RestAction.await()` and `JDABuilder.injectKTX()`, load `CoroutineEventManager` as an `IEventManager`) has exactly the same API in 0.15.0 as in 0.14.2.

### F3. JDA 6.7.0 is still the newest release and 0.15.0 links to it (Established for the release; Inference for the diff)

- JDA's [`maven-metadata.xml`](https://repo1.maven.org/maven2/net/dv8tion/JDA/maven-metadata.xml) has `release` 6.7.0, `lastUpdated` 20260920181746; the GitHub releases list ends at `v6.7.0` (2026-09-20). 6.5.0 (2026-07-05) and 6.6.0 (2026-09-06) sit between jda-ktx's JDA and the pin.
- 6.7.0 declares `org.gradle.jvm.version` 8 on its API and runtime variants and builds with `options.release = libraryJavaVersion.asInt()`, where `libraryJavaVersion` is Java 8 ([`build.gradle.kts` at v6.7.0](https://github.com/discord-jda/JDA/blob/v6.7.0/build.gradle.kts)). Its POM and module list no `kotlin-stdlib`; Kotlin reaches a JDA consumer only through OkHttp.
- The 6.5.0-to-6.7.0 comparison ([compare view](https://github.com/discord-jda/JDA/compare/v6.5.0...v6.7.0), 21 commits, 83 files) removes no public source file. The deleted lines in `api/` are an import changed to a fully-qualified name in `Mentions`, a nested `Builder` class gaining an interface in `AttachmentUpload`, the `Label` interface header, and documentation. The notes of 6.6.0 list two features and four changes; 6.7.0's one breaking change is that channels for interactions become snapshots (behavioural, "affects permission handling"). jda-ktx's source mentions none of the touched types except `OptionData(...)` (a constructor it only calls).
- The prior binary-linkage measurement (2026-10-20, same file §3 F6) found all 481 JDA references of the 0.15.0 jar resolve against JDA 6.5.0 and 6.7.0. It is carried forward; the diff above is independent support for it, not a replacement.
- **Consequence:** jda-ktx 0.15.0 does not need a newer JDA than 6.7.0. Nothing moves with JDA. Behaviour under 6.7.0's channel snapshots is unproven (see Gaps).

### F4. kotlinx-serialization-json: newest is 1.13.0, built on Kotlin 2.4.10; 1.12.0 has a regression to avoid (Established; releases and metadata)

- Releases: 1.13.0 (2026-11-11), 1.12.0 (2026-10-19), 1.11.0 (2026-04-09). Maven Central `release` is 1.13.0 (`lastUpdated` 20261111185449).
- 1.13.0: "This release is based on Kotlin 2.4.10 and reverts a breaking change introduced in 1.12.0." The repository at the tag pins `kotlin = "2.4.10"` ([`gradle/libs.versions.toml` at v1.13.0](https://github.com/Kotlin/kotlinx.serialization/blob/v1.13.0/gradle/libs.versions.toml)) and its README shows plugin and Kotlin `2.4.10`.
- 1.12.0's own notes carry a caution: it "contains a breaking behavioral change related to serializer's exception propagation in Json encoder/decoder" (every exception thrown during deserialization wrapped in `JsonException`) and says to update to 1.13.0. 1.13.0 rolls that back. 1.9.0 to 1.11.0 added experimental `JsonException` types and `exceptionsWithDebugInfo`; 1.10.0 stabilised several `Json` options. The jump from 1.9.0 to 1.13.0 therefore has no breaking change left in effect (read from the release notes of 1.10.0, 1.11.0, 1.12.0, 1.13.0).
- Published metadata ([`kotlinx-serialization-json-jvm` 1.13.0 module](https://repo1.maven.org/maven2/org/jetbrains/kotlinx/kotlinx-serialization-json-jvm/1.13.0/kotlinx-serialization-json-jvm-1.13.0.module)): `kotlin-stdlib` `requires` 2.4.10, `kotlinx-serialization-core` and the BOM `requires` 1.13.0, no `org.gradle.jvm.version`. Core 1.13.0 requires `kotlin-stdlib` 2.4.10 as well.
- Class files: the build sets `jvmTarget = JvmTarget.JVM_1_8` and `-Xjdk-release=1.8` in `setJava8Compatible()` ([`CompilerOptions.kt` at v1.13.0](https://github.com/Kotlin/kotlinx.serialization/blob/v1.13.0/buildSrc/src/main/kotlin/CompilerOptions.kt)).
- Open issues since the release (to 2026-11-22): none on Json encoding or decoding; the open bugs found are ProtoBuf and CBOR.

### F5. The compiler plugin at 2.5.0-RC against runtime 1.13.0 (Common practice; one direction is checked, the other is the normal case)

- The 2.5.0-RC compiler plugin exists on Maven Central: the `org.jetbrains.kotlin.plugin.serialization` marker's `release` is `2.5.0-RC` (`lastUpdated` 20261111082541), depending on `kotlin-serialization` 2.5.0-RC.
- kotlinx.serialization releases lag the compiler: its README says "of the serialization plugin are released in tandem with each new Kotlin compiler version", and 1.13.0 is built on 2.4.10 while Kotlin has had 2.4.20, 2.4.21 and 2.5.0-RC since. Running a newer plugin on the last published runtime is therefore the ordinary state of every build between a Kotlin release and the next runtime release.
- The version check that exists points the other way: 1.7.0-RC says its runtime "will be rejected by older plugins" (plugin at least 2.0.0-RC1). I found no minimum-plugin statement in the 1.13.0 notes and no maximum anywhere.
- The 2.5.0-RC release notes list one serialization item (KT-91224, Java enums annotated `@Serializable` regress); `kotlinx.serialization` issues mention 2.5.0 only for build chores. The repository's `gradle.properties` at the 1.13.0 tag names `kotlin.version.snapshot=2.5.255-SNAPSHOT`, i.e. the library is already built against 2.5 snapshots in its bootstrap mode.
- **Inference:** the combination plugin 2.5.0-RC with runtime 1.13.0 is expected to work and is not documented as tested. The integration-set `@Serializable` round-trip probe is the proof, and it must also run on 2.5.0 when that is released.

### F6. kotlinx-coroutines: 1.11.0 is the newest stable release, built on Kotlin 2.2.20 (Established; releases and metadata)

- Releases: 1.11.0 (2026-05-08), after 1.11.0-rc01 and rc02; before it 1.10.2 (2025-04-08). Core and test both have `release` 1.11.0 on Maven Central.
- 1.11.0's notes: "Kotlin was updated to 2.2.20". The tag's `gradle.properties` has `kotlin_version=2.2.20`. Core's JVM module `requires` `kotlin-stdlib` 2.2.20 (1.10.2 required 2.1.0), and `org.jetbrains:annotations` 23.0.0. Test's JVM module requires core 1.11.0 and `kotlin-stdlib` 2.2.20. Neither JVM variant has an `org.gradle.jvm.version`. The conventions set `jvmTarget = JvmTarget.JVM_1_8` for both the JVM and multiplatform builds (`kotlin-jvm-conventions.gradle.kts`, `kotlin-multiplatform-conventions.gradle.kts` at 1.11.0). The core and test JVM jars carry a `module-info` ([`module-info.java` in `kotlinx-coroutines-core/jvm/src`](https://github.com/Kotlin/kotlinx.coroutines/blob/1.11.0/kotlinx-coroutines-core/jvm/src/module-info.java)) built through `Java9Modularity.kt`, so a multi-release entry under `META-INF/versions/9` (major 53, within the floor) is expected (inference from the build files).
- Changes between 1.10.2 and 1.11.0 that touch this library: `kotlinx-coroutines-test` removed the APIs already at `ERROR` level and raised the `runTest` overloads that take a dispatch timeout to `ERROR` (PR #4604, merged 2026-03-05); `CoroutineDispatcher` as a context key is deprecated. Neither affects `runTest`, `TestScope`, `StandardTestDispatcher` or `TestCoroutineScheduler`, which WebTools' own test fixtures use.
- Open bugs filed since 1.11.0 (2026-05-08 to 2026-11-22) concern `limitedParallelism`, suppressed exceptions on `CancellationException`, channel operators and Android; none concerns the Kotlin line or this library's use.

### F7. Gradle resolves the set to one coroutines version, 1.11.0 (Established: Gradle's documented rule; Inference: the graph)

- Gradle's rule: "Gradle resolves any dependency version conflicts by selecting the greatest version found in the dependency graph." A plain version is a required version, so it is a floor; only `strictly` overrides: "A strict version cannot be upgraded and overrides any transitive dependency versions". ([`dependency_versions.adoc` at v9.7.1](https://github.com/gradle/gradle/blob/v9.7.1/platforms/documentation/docs/src/docs/userguide/reference/dependency-management/declaring-dependencies/dependency_versions.adoc).)
- WebTools' only coroutines declarations are plain: `api("org.jetbrains.kotlinx:kotlinx-coroutines-core:1.10.2")` in `webtools-http` and `"jvmTestFixturesApi"("org.jetbrains.kotlinx:kotlinx-coroutines-test:1.10.2")`; no `strictly` constraint on coroutines appears in the four module build files read (`webtools-http`, `-feeds`, `-browser`, `-scraping`; the only "strictly" there is a comment about a different version); three further module build files were not read (read at `master`, head `98b7749`, 2026-11-22).
- The graph this implies (**inference**; not resolved by a Gradle run):

| `net.dv8tion:JDA` | `bottools-core` `api` 6.7.0; jda-ktx 0.15.0 runtime 6.5.0 | **6.7.0** |

- The Kotlin Gradle plugin's own rule: "A dependency on the standard library (`stdlib`) is added automatically to each source set. The version of the standard library used is the same as the version of the Kotlin Gradle plugin."
- WebTools' calling modules are compiled against coroutines 1.10.2 and will run on 1.11.0. coroutines publishes binary-compatibility validation of its API, and the only removals are in the test artifact's already-`ERROR` APIs (F6); WebTools' fixtures do not use them. I did not run a resolution or a link check; this is an inference.

### F8. What a Kotlin 2.5.0-RC compiler reads (Established; compiler source at `v2.5.0-RC`)

`MetadataVersion` at `v2.5.0-RC` has `val INSTANCE = MetadataVersion(2, 5, 0)` and `val forwardCompatibility = if (isStrictSemantics) INSTANCE else INSTANCE_NEXT`, where `INSTANCE_NEXT = INSTANCE.next()` (2.6.0). A compiler therefore reads class metadata up to one minor above its own, and anything older. jda-ktx 0.15.0 and serialization-json 1.13.0 (Kotlin 2.4) and coroutines 1.11.0 (Kotlin 2.2) are readable. None of the four was built by a pre-release compiler, so none of them carries the pre-release marker that a 2.5.0-RC build would write; consumer-side effects of the library's own pre-release build are another question's subject.

### F9. What the organisation's builds pin (Common practice; read 2026-11-22)

- WebTools' build-logic applies the Kotlin Gradle plugin through exact marker versions (`2.2.0`) and its modules pin coroutines, OkHttp (`okhttp-jvm:5.5.0`) and slf4j by exact literal versions, with no ranges and no version catalog. WebTools already ships a `VerifyJavaFloor` task and a `JavaFloorScan` object (`build-logic/src/main/kotlin`) that skip `META-INF/versions/` entries and read `org.gradle.jvm.version` from Gradle Module Metadata.
- MyGameTools' build-logic states "Kotlin and its serialization plugin stay in lockstep on one version." and applies both at 2.2.0. GeneralTools applies `kotlin("jvm") version "2.2.0"`. None of the three has moved to 2.5 yet, so there is no organisation precedent for the 2.5 set; the pattern to follow is exact versions, one version for the compiler and its serialization plugin.

## 4. How comparable projects do it

- **jda-ktx** itself: Kotlin stdlib and coroutines as `api`, JDA as `implementation` (runtime scope in the POM), so a consumer must bring its own JDA; it is built at JVM target 1.8 and tracks its own JDA version, trailing the newest JDA by two minors (6.5.0 against 6.7.0). Its build file: [`build.gradle.kts`](https://github.com/MinnDevelopment/jda-ktx/blob/4fc12afb5da25f2229bb10ef631633dd648c1283/build.gradle.kts) and [`libs.versions.toml`](https://github.com/MinnDevelopment/jda-ktx/blob/4fc12afb5da25f2229bb10ef631633dd648c1283/gradle/libs.versions.toml).
- **kotlinx.serialization and kotlinx.coroutines** both compile to JVM target 1.8 with the stdlib of an older Kotlin (2.4.10 and 2.2.20) and let consumers run newer compilers; their `kotlin-stdlib` requirements are floors, which the Kotlin Gradle plugin raises. This is the arrangement that makes a newest-everything set on 2.5 possible.
- **BotCommands** (v3.4.0, from the earlier findings) builds on Kotlin 2.4.20, JDA 6.6.0 and coroutines 1.11.0, which shows the same JDA 6 and coroutines 1.11 pairing in use on a 2.4 compiler.

## 5. Pitfalls and regrets

1. **Taking serialization-json 1.12.0.** Its own release notes tell users to update to 1.13.0 because of the exception-wrapping change; 1.13.0 is both newest and the safe one.
2. **A `strictly` on coroutines anywhere in the graph.** WebTools' 1.10.2 is a floor today. If WebTools (or any later module) ever declares `strictly` 1.10.2, Gradle will hold coroutines at 1.10.2, below the 1.11.0 that jda-ktx 0.15.0 and coroutines-test 1.11.0 were built against. A graph check that fails when the resolved coroutines version is not 1.11.0 would catch it.
3. **Reading "stdlib 2.4.x required" as "Kotlin 2.4 needed".** The requirement is a floor on the stdlib; with the Kotlin Gradle plugin at 2.5.0-RC the resolved stdlib is the plugin's, 2.5.0-RC, and consumers of the library receive whatever the library's published metadata says (a question for the consumer-side findings).
4. **Plugin ahead of runtime.** A serialization plugin newer than the runtime is the usual state but is not tested by JetBrains for 2.5.0-RC with 1.13.0. When 2.5.0 is released, re-run the probe and look for a serialization release built on 2.5 (the repository is already bootstrapped on 2.5 snapshots).
5. **jda-ktx is a single maintainer's library that trails JDA.** 0.15.0 is 20 weeks old and targets JDA 6.5.0; it has no tag or release notes. JDA ships breaking changes in minors (6.7.0's channel snapshots), and the linkage evidence is static. The earlier findings' "smallest replacement" (an in-house `await` and event manager behind the one internal adapter) remains the fallback if a JDA bump breaks it.
6. **Removed test APIs in coroutines-test 1.11.0.** Tests written with `runBlockingTest`, `TestCoroutineScope`, `TestCoroutineDispatcher` or `runTest(dispatchTimeoutMs = ...)` do not compile; use `runTest`, `TestScope` and `StandardTestDispatcher`.
7. **`verifyJavaFloor` must read class files for coroutines and serialization.** Their JVM variants publish no `org.gradle.jvm.version`, so a metadata-only check passes them without checking; coroutines carries a multi-release `module-info` entry, which the check should accept below the floor rather than skip all of `META-INF/versions/`.

## 6. Recommendation for this repo

Use the following set, each version exact, no ranges, declared once and changed together:

- Kotlin Gradle plugin and serialization compiler plugin: **2.5.0-RC**, then 2.5.0.
- `net.dv8tion:JDA` **6.7.0**, `api` (unchanged).
- `club.minnced:jda-ktx` **0.15.0**, `implementation`, behind the one internal adapter (replaces 0.14.2).
- `org.jetbrains.kotlinx:kotlinx-coroutines-core` **1.11.0**, `api` in `bottools-core`; `kotlinx-coroutines-test` **1.11.0** for tests (replaces 1.10.2).
- `org.jetbrains.kotlinx:kotlinx-serialization-json` **1.13.0** in `bottools-stats` and `bottools-plugins` (replaces 1.9.0).

Reasoning: each is the newest release of its library, none requires a Kotlin compiler above 2.4, the highest `kotlin-stdlib` requirement (2.4.10) is below the plugin's own, and the Gradle graph resolves coroutines to 1.11.0 and JDA to 6.7.0 without any `strictly`. Treat the set as one coupled change, as the earlier findings did for the JDA and jda-ktx pair, and record each version in the changelog.

Checks to keep with the set: the existing integration-set tests (the `await`/`injectKTX`/`CoroutineEventManager` compile-and-load check and the `@Serializable` round trip), plus a check that the resolved coroutines version equals 1.11.0, the resolved JDA equals 6.7.0 and the resolved `kotlin-stdlib` is not above the compiler's version. Keep the class-file arm of `verifyJavaFloor` (WebTools' `JavaFloorScan` is organisational precedent), since two of the four libraries publish no `org.gradle.jvm.version`.

Rejected: staying on jda-ktx 0.14.2 / coroutines 1.10.2 / serialization 1.9.0 (the 2.2-era set). The compiler now reads them and the newer ones, and the older set offers nothing in return. Rejected: serialization-json 1.12.0 (regression). ## 8. Gaps

- **No jar was opened, no build run.** The `@Metadata` version of jda-ktx 0.15.0 (2.4.0) and its 481 JDA references resolving against JDA 6.7.0 come from the earlier findings' measurement of the published jars (2026-10-20), carried forward; the build file and the JDA source diff support them. The class-file major version of coroutines 1.11.0 and serialization-json 1.13.0 jars is inferred from their build files (JVM target 1.8, `-Xjdk-release=1.8` for serialization-json, a `module-info` for coroutines), not read from the jars. If a class above major 65 existed, `verifyJavaFloor` would fail; no source suggests it.
- **The resolved graph in F7 is derived from published metadata, not from a Gradle resolution.** What would change if wrong: a conflicting requirement (a `strictly`, or a constraint in WebTools' published module that I did not see) would hold coroutines or JDA below the table's value.
- **Plugin 2.5.0-RC with runtime 1.13.0 is undocumented as supported.** It is a normal pairing in practice (F5), but nothing states it. If the probe fails, the options are plugin 2.4.21 with language and API version 2.4 (conflicts with the settled language version) or waiting for a runtime built on 2.5.
- **Behavioural compatibility of jda-ktx 0.15.0 with JDA 6.7.0 is unproven**, notably with 6.7.0's snapshot channels in interaction events. The integration-set check proves loading, not event-handling behaviour. There are no jda-ktx release notes, since the repository has no GitHub releases and no tag after `0.12.0`.
- **WebTools compiled against coroutines 1.10.2 running on 1.11.0** is not link-checked. The API removals found are in the test artifact and are not used by WebTools' fixtures; main-artifact binary compatibility is not established from a source I read.
- **A newer jda-ktx release or a serialization release on Kotlin 2.5 may appear** before 2.5.0 is final; the recommendation is for the versions published on 2026-11-22.
- **The ranking of "newest that works together" for coroutines 1.11.0 against a Kotlin 2.5 compiler** rests on the metadata rule and the absence of reported issues; no issue search of the Kotlin tracker was done for 2.5.0-RC regressions with coroutines.
- **kotlin-logging and OkHttp's requirements** are out of this file's scope; OkHttp 5.5.0's `kotlin-stdlib` 2.2.21 requirement is quoted from the earlier findings.
