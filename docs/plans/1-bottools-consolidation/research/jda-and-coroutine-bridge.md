# JDA release line and coroutine bridge for bottools-core

For: SpartanLaboratories/KotlinBottools#1
Date read: 2026-10-20.
Applies to: JDA 5.6.1 (2025-06-08) and 6.0.0 to 6.7.0 (2026-09-20, latest on Maven Central); `club.minnced:jda-ktx` 0.12.0 to 0.15.0 (0.15.0 published 2026-07-05, latest); Kotlin compilers 2.2.x to 2.4.x. Code pins: JDA `v6.7.0` (`7c900019ca511a994087320ce98d19cd79a2c4b0`) and `v5.6.1` (`f8e78d6d29737fd4d488a56c374bf61124062492`); jda-ktx `master` @ `4fc12afb5da25f2229bb10ef631633dd648c1283` (its `build.gradle.kts` says `version = "0.15.0"`; the repository has no tag after `0.12.0`, so 0.13.0 to 0.15.0 are read from their published POMs and jars); BotCommands `v3.4.0` (`c23a9e41b56874045e709b0d9a941e77a3c0b1cb`) and the checked-out head `09e7440b6804a959f20094f4e6616bd615d06a6c` (2026-10-06).

## 1. Question

Which JDA release line should `bottools-core` build on, and does `jda-ktx` work as its internal coroutine bridge?

An answer has to satisfy these facts about the work:

- `jda-ktx` is an `implementation` dependency of `bottools-core`. It is never on a consumer's compile classpath, but it is on every consumer's runtime classpath, so it must resolve from Maven Central alone.
- The toolchain is JDK 21 and Kotlin 2.2.x. The organisation's build logic (MyGameTools `build-logic`) applies Kotlin Gradle plugin 2.2.0, so the compiler that builds `bottools-core` reads class metadata up to 2.3.0 and writes metadata 2.2.0.
- JDA must support slash commands with subcommand groups, user and message context menus, components (buttons, select menus, modals), autocomplete and sharding.
- JDA's transitive dependencies must not conflict with the HTTP/JSON stack chosen elsewhere.

## 2. Bottom line

- **`jda-ktx` is on Maven Central and consumers on Kotlin 2.2.x are unaffected, but the latest release (0.15.0) cannot be used with the pinned toolchain or the pinned JDA.** Coordinates are `club.minnced:jda-ktx`, on `repo1.maven.org`, no JitPack needed, Apache-2.0. Its POM requires `kotlin-stdlib` 2.4.0, `kotlinx-coroutines-core-jvm` 1.11.0 and JDA 6.5.0 (runtime scope). Its classes carry `@Metadata` version 2.4.0, which a Kotlin 2.2.x compiler (reads up to 2.3.0) cannot read. It also links against JDA 6 classes that do not exist in 5.6.1. Consumers never compile against `jda-ktx` (it is `implementation`), so the metadata limit bites only the compiler that builds `bottools-core`.
- **Pairings that hold, established from Maven Central POMs and jar contents:**

  | JDA | jda-ktx | Kotlin stdlib in its POM | `@Metadata` mv | Readable by a 2.2.x compiler | Links to that JDA |
  |---|---|---|---|---|---|
  | 5.6.1 | 0.13.0 | 2.2.10 | 2.2.0 | yes | yes (all 377 JDA references resolve) |
  | 6.7.0 | 0.14.2 | 2.3.0 | 2.3.0 | yes (the upper edge of the rule) | yes (480 references resolve) |
  | 6.7.0 | 0.15.0 | 2.4.0 | 2.4.0 | **no** | yes (481 references resolve) |
  | 5.6.1 | 0.14.x or 0.15.0 | n/a | n/a | n/a | **no** (34 classes missing, including every component class) |

  So "JDA 5.6.1 plus Kotlin 2.2.x plus the latest `jda-ktx`" cannot hold. "JDA 5.6.1 plus `jda-ktx` 0.13.0" holds. "JDA 6.7.0 plus `jda-ktx` 0.14.2" holds. `jda-ktx` 0.15.0 needs the building compiler to be Kotlin 2.4.0 or newer.
- **Build on the JDA 6 line, pinned to 6.7.0.** 5.6.1 is the last 5.x release (2025-06-08); there is no 5.x branch and no 5.x release in the 16 months since, while 6.x shipped 16 stable releases (6.0.0 on 2025-10-04 to 6.7.0 on 2026-09-20), including Discord's modal `Label` change, Components V2 and channel obfuscation (mandatory 2026-11-16). The migration cost from the current code is small: all 41 distinct JDA classes KotlinBottools imports exist in 6.7.0, and 45 of GKB2's 47 do (the two that moved are `ActionRow` and `Button`, used only by GKB2's poker command). JDA 6.7.0 also puts OkHttp on `okhttp-jvm:5.5.0`, the same artifact and version Ktor 3.6.0's OkHttp engine uses; JDA 5.6.1 sits on `okhttp:4.12.0`.
- **Use `jda-ktx` 0.14.2 while the build compiler is Kotlin 2.2.x.** Use only its coroutine core: `RestAction.await`, `Task.await`, `PaginationAction.asFlow`, `CoroutineEventManager` with `injectKTX` for `JDABuilder` and `DefaultShardManagerBuilder`, and the `ShardManager.listener` overloads. Keep every use behind one internal adapter file in `bottools-core`. `jda-ktx` does not fail a requirement; if a later JDA 6.x breaks 0.14.2 before the toolchain can move, the smallest replacement is `RestAction.await` plus a `CoroutineEventManager` (my estimate: on the order of 100 lines), which is what BotCommands ships.
- **Expose JDA as `api` and `jda-ktx` as `implementation`.** The typed event registry and handlers pass JDA event and entity types to consumers, so consumers compile against JDA. `jda-ktx` types must not appear in any public signature, public `inline` body, supertype or default argument of `bottools-core`.

POM `dependencies` (all from repo1.maven.org; claim 14):

| jda-ktx | `kotlin-stdlib` (compile) | `kotlinx-coroutines-core-jvm` (compile) | `JDA` (runtime) |
|---|---|---|---|
| 0.12.0 | 2.0.0 | 1.8.1 (`kotlinx-coroutines-core`) | 5.0.0 |
| 0.13.0 | 2.2.10 | 1.10.2 | 5.6.1 |
| 0.14.0, 0.14.1 | 2.3.0 | 1.10.2 | 6.2.0 |
| 0.14.2 | 2.3.10 | 1.10.2 | 6.3.2 |
| 0.15.0 | 2.4.0 | 1.11.0 | 6.5.0 |

Measured `@Metadata` `mv` of `dev/minn/jda/ktx/events/CoroutineEventManager.class` and `.../coroutines/CoroutinesKt$await$3$1.class`, decoded from the published jars (class-file constant pool and `RuntimeVisibleAnnotations`): 0.13.0 `[2, 2, 0]`; 0.14.2 `[2, 3, 0]`; 0.15.0 `[2, 4, 0]`. The `@Metadata` version equals the build compiler's language version when no flag lowers it, which matches the stdlib versions in the POMs.

The compiler rule: a compiler reads metadata up to its own version plus one minor. `MetadataVersion.isCompatibleWithCurrentCompilerVersion` accepts `INSTANCE_NEXT` unless strict semantics apply, and `INSTANCE` is `MetadataVersion(2, 2, 0)` at tag `v2.2.0` (claim 3; the GeneralTools compatibility research reaches the same rule, section 3 F1 of `kmp-build-and-kotlin-compat.md`). So Kotlin 2.2.x reads 0.13.0 (2.2.0) and 0.14.x (2.3.0), and rejects 0.15.0 (2.4.0).

### F6. Binary linkage between jda-ktx and JDA (Measured; static, not behavioural)

I compared every constant-pool reference (classes, methods, fields) from each jda-ktx jar to `net/dv8tion/jda/*` against the class files of each JDA jar, following inherited methods through JDA supertypes:

- 0.13.0 against JDA 5.6.1: 377 references, all resolve. Against 6.7.0: 16 classes missing (the whole `api.interactions.components.*` and `api.interactions.modals.*` tree) and 5 method signatures (`setComponents(LayoutComponent[])` on four actions, `replyModal(Modal)`).
- 0.14.2 against JDA 6.3.2, 6.5.0 and 6.7.0: 480 references, all resolve. Against 5.6.1: 34 classes (every `api.components.*` and `api.modals.*` class) and 10 members missing.
- 0.15.0 against JDA 6.5.0 and 6.7.0: 481 references, all resolve. Against 5.6.1: the same 34 classes and 10 members missing.
- The one reported "missing" member in every run is `Message$MentionType.ordinal()`, an `Enum` method my checker does not model; it is not a real gap.

Limits: this proves symbols exist, not that behaviour is unchanged, and it does not prove Kotlin default-argument bridges or JDA behavioural changes (for example 6.7.0's channel snapshots) are harmless. It shows that mixing 0.14.x or 0.15.0 with JDA 5.6.1 fails at class loading for any component code path, and that mixing 0.13.0 with JDA 6 fails the same way.

### F7. Version resolution skew: jda-ktx's runtime JDA edge (Practice; Gradle semantics)

`jda-ktx` declares JDA at `runtime` scope. A `bottools-core` that pins JDA 5.6.1 in `api` and `implementation`s `jda-ktx` 0.15.0 resolves JDA to 6.5.0 on the runtime classpath (Gradle picks the highest requested version) while consumers compile against 5.6.1. That is a compile/runtime skew, and F6 shows it fails at class loading. The same applies in the other direction if `jda-ktx` 0.13.0 is kept while the JDA pin moves to 6.x: the runtime would still resolve to the higher JDA, and `jda-ktx` 0.13.0 would break. `jda-ktx` and JDA therefore have to be moved together.

### F8. What jda-ktx offers and which parts a library would use (Practice; source at `4fc12af`)

- `suspend fun <T> RestAction<T>.await(): T = submit().await()` (using `kotlinx.coroutines.future.await`) and a `Task<T>.await()` built on `suspendCancellableCoroutine` that calls `cancel()` on cancellation. `PaginationAction.asFlow()`. `JDA.await<Event>` and `ShardManager.await<Event>` event waiters (`coroutines/coroutines.kt`, `events/events.kt`).
- `CoroutineEventManager(scope: CoroutineScope = getDefaultScope(), timeout: Duration = Duration.INFINITE) : IEventManager, CoroutineScope by scope`, installed with `JDABuilder.injectKTX()` or `DefaultShardManagerBuilder.injectKTX()` (`jdabuilder/inject.kt`). `getDefaultScope(pool, job, errorHandler, context)` builds a scope on `Dispatchers.Default` with a `SupervisorJob` and a logging `CoroutineExceptionHandler`; a custom scope can be passed in, so lifecycle ownership stays with the library.
- `JDA.listener<T>`, `onCommand`, `onContext`, `onCommandAutocomplete`, `onComponent`, `onButton`, `onStringSelect`, `onEntitySelect`, each with a `ShardManager` overload, so sharding is covered.
- Also: slash-command and component builders, message and embed builders, `light()`/`default()` JDA builders, `ref()` delegates, an SLF4J delegate, and a logback `WebhookAppender` (logback and discord-webhooks are `compileOnly` in the build).
- A library that has its own immutable command tree would use only the coroutine core (`await`, `asFlow`, `CoroutineEventManager`, `injectKTX`, `ShardManager.listener`). It would not use the command, component or message builders, which duplicate its own surface and track JDA's component API, the part that changed most between JDA 5 and 6.

## 4. How comparable projects do it

- **BotCommands (freya022), `v3.4.0` / head `09e7440`.** Its `BotCommands-core/build.gradle.kts` declares `compileOnly(libs.jda)`, so the consumer supplies JDA ("After adding JDA" in its README; badge "JDA 6.6.0+"), and `api(libs.kotlinx.coroutines.core)` because its public API is `suspend`. It does not depend on `jda-ktx`: it ships its own `BotCommands-jda-ktx` module ("Kotlin extensions and top-level functions, similarly to jda-ktx"), whose `Coroutines.kt` is `suspend fun <T> RestAction<T>.await(): T = submit(true).await()` plus a `Task<T>.await()` on `suspendCancellableCoroutine`. Its event manager, `CoroutineEventManagerImpl : IEventManager` in `internal.core.hooks`, is documented as "more a barebone listener which replaces jda-ktx's CoroutineEventManager"; it dispatches annotated listeners first on the caller thread (to support blocking listeners), then runs `EventListener` subclasses in a new coroutine, with a configurable scope and timeout. Its build uses Kotlin 2.4.20, JDA 6.6.0, coroutines 1.11.0, and publishes under MPL-2.0. This is the evidence for the "smallest replacement" if `jda-ktx` ever blocks the toolchain.
- **jda-ktx itself** declares JDA `implementation` (runtime scope in the POM) and Kotlin and coroutines as `api`; it expects the consumer to depend on JDA directly.
- **JDA's own README** lists `jda-ktx` under "Extensions" as the Kotlin option and shows `light(BOT_TOKEN)`, `jda.onCommand` and `event.reply(...).await()`.

## 5. Pitfalls and regrets

1. **Taking 0.15.0 because it is "latest".** It forces JDA 6.5.0+ and a Kotlin 2.4.0+ compiler on the building side. Under Kotlin 2.2.x it fails with the standard "incompatible version of Kotlin ... metadata version 2.4.0" error.
2. **0.14.2 sits exactly on the 2.2.x compiler's limit (metadata 2.3.0).** It works by the documented next-version rule, but any move of `jda-ktx` beyond 0.14.x needs the toolchain to move first. Prove it with a one-line `bottools-core` compile that calls `dev.minn.jda.ktx.coroutines.await` under Kotlin 2.2.0.
3. **Runtime stdlib and coroutines versions are higher than the consumer's compile versions.** With 0.14.2 a Kotlin 2.2.0 consumer's runtime classpath resolves `kotlin-stdlib` 2.3.10; with 0.15.0, 2.4.0 and coroutines 1.11.0. That is harmless at runtime but means the runtime does not match what the library compiled against; the published `api` variant still declares only what `bottools-core` itself declares.
4. **Leaking `jda-ktx` into the consumer compile classpath by accident.** `implementation` keeps it out of the published API variant, but a public `inline`/`reified` function that calls `jda-ktx`, a public class that implements `CoroutineEventListener`, a default argument of a `jda-ktx` type, or a `typealias` to one forces consumers to compile against it. Hide every use behind `internal` code. Because `bottools-core`'s public API is `suspend`, it must also declare `kotlinx-coroutines-core` as `api` itself (BotCommands does); `jda-ktx` exposing coroutines as `api` only helps `bottools-core`'s own compile classpath.
5. **`CoroutineEventManager` defaults surprise a library.** Reading `events/events.kt`: `handle(event)` launches one coroutine per event on `Dispatchers.Default` and runs the registered listeners one after another inside it, so a slow listener delays the others for that event, and events are handled concurrently with no ordering guarantee between them. The default scope is created by the library and is not cancelled by `JDA.shutdown()`. The `timeout` defaults to `Duration.INFINITE`. `getRegisteredListeners()` is implemented as `mutableListOf(listeners)` (a list that contains the list), which reads as a defect in that source revision; do not rely on it. A library should pass its own scope and a timeout, and treat the event manager as replaceable (BotCommands replaced it for exactly these reasons: blocking-listener support and configuration).
6. **Blocking JDA calls on `Dispatchers.Default`.** `complete()` and `Task.get()` inside coroutine listeners starve the pool; the existing start-up `complete()` calls should not be carried into the bridge.
7. **Minor-version breakage in JDA.** JDA ships breaking changes in minors (6.3.1, 6.7.0). A range such as `6.+` is unsafe; pin one version, record the tested version in the changelog, and bump deliberately. Consumers who raise JDA past the tested version are on their own.
8. **JDA 5 plus an OkHttp 5 stack.** JDA 5.6.1's `okhttp:4.12.0` next to any OkHttp 5 consumer (Ktor 3.6.0's OkHttp engine) likely gives duplicate `okhttp3.*` classes (F3). Staying on 5.6.1 would need a Gradle capability rule or exclusion.
9. **A modal or component built the JDA 5 way fails to compile on 6.x.** Modals take `Label.of(label, component)`, `TextInput.create(id, style)` loses its label, and `ActionRow` is immutable. GKB2's poker command is the only such code in the two bases.

## 6. Recommendation for this repo

- **JDA.** Build `bottools-core` on **JDA 6.7.0**, declared as `api("net.dv8tion:JDA:6.7.0")` with an exact version. Rationale: 6.x is the only maintained line and the only one that carries Discord's 2026 platform changes; the move costs nothing in KotlinBottools (0 of 41 imports break) and a poker rewrite in GKB2; and its OkHttp 5.5.0 matches Ktor 3.6.0's engine. `api` rather than `implementation` because the typed event registry, plugin API and handlers pass JDA events and entities to consumers (a separate question, owned by the public-API research, is whether library-owned wrapper types replace them; if they ever fully do, JDA can drop to `implementation` without a source change for consumers). The alternative of `compileOnly` with the consumer supplying JDA (BotCommands) is rejected here because the library is also a runtime for MagicBot and must resolve a tested JDA by itself. Consumers may exclude `opus-java` and `tink`.
- **Bridge.** Use **`club.minnced:jda-ktx:0.14.2` as `implementation`** while the library is built by Kotlin 2.2.x, and use only the coroutine core named in F8. Put it behind one internal adapter file so replacing it with an in-house `await` plus `CoroutineEventManager` is a single-file change. If the toolchain moves to Kotlin 2.4.0 or newer, 0.15.0 becomes usable; do not take it before then. Keep the pair (JDA version, jda-ktx version) as one reviewed change.
- **Reject** "JDA 5.6.1 plus `jda-ktx` 0.15.0" (does not link, does not compile). **Reject staying on 5.6.1 plus 0.13.0 as the long-term choice** (it works, but it freezes the library on an unmaintained line before its first release); it is the fallback if the poker-style component rewrite or a 6.x regression must be deferred.
- **Pin facts to the changelog.** Record Kotlin 2.2.x compiler, JDA 6.7.0, `jda-ktx` 0.14.2, `kotlinx-coroutines` chosen by `bottools-core` itself, and the rule above, so a later bump of any one is recognised as a coupled change.

- **No official JDA 5 end-of-life statement found.** The "unmaintained" judgment rests on release history and branch layout, not a policy page.
- **Behavioural compatibility is unproven.** My linkage checks (F6) show symbols exist, not that `jda-ktx` 0.14.2 behaves correctly on JDA 6.7.0 (for example under 6.7.0's snapshot channels). Nothing was built or run. `jda-ktx` 0.14.2 on JDA 6.7.0 needs one spike under Kotlin 2.2.0: compile `bottools-core` against it, then run an event through `injectKTX` against a JDA test double.
- **The Kotlin 2.2.x compiler reading metadata 2.3.0 is established from compiler source and the Kotlin-compat research, not run.** It is the upper edge of the rule, so the spike above should include it.
- **Duplicate OkHttp classes with JDA 5.6.1 beside OkHttp 5 (F3, pitfall 8) is inference** from module metadata, not a resolved dependency graph.
- **Whether JDA 5.6.1 keeps working after Discord's channel obfuscation becomes mandatory on 2026-11-16** is not established; 6.7.0 is the first JDA release that says it is aware of it.
- **The KGP version that will build `bottools-core` is not fixed by the brief.** I assumed Kotlin Gradle plugin 2.2.0 (as in MyGameTools' `build-logic`).
