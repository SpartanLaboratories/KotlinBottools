## 1. Question

What can OpenDota and Steam provide for Dota 2 account links, profiles, match history, match detail and patch notes, and what call budget does a public bot that posts new matches automatically have to live within? An answer has to give: the endpoints and fields the Dota 2 provider needs; account resolution (Steam64, account id, profile URL, vanity name); the rate limits, key price, signalling and terms; how fresh recent matches are and which fields need a parsed match; a calls-per-tracked-account model; a patch-notes source that is documented and not scraped (which decides that no feed parser belongs in the stats module); and image URLs from documented constants plus a CDN.

Facts about the work this answer is written against:

- MagicBot is a public bot holding the privileged `GUILD_MEMBERS` intent and not holding `MESSAGE_CONTENT`. Its typed form is reached by @-mention in servers (`@MagicBot setid 123`) and by the prefix in DMs (`!setid 123`); `setid`, `getid`, `lastgame` and `showstats` stay as typed aliases.
- Dota 2 patch notes come from Steam's JSON news API through a news source in `bottools-stats`, with no feed parser. A general RSS/Atom feeds plugin in `bottools-plugins` (feed parser behind a `FeedParser` port, SSRF guard, subscription storage, admin commands) is separate and is installed by MagicBot.
- MagicBot's privacy policy and terms name the third parties whose data it uses.

## 2. Bottom line

- **No requirement is contradicted.** OpenDota is usable as the provider without a key, with a defined path to a key; Steam's keyless JSON news API carries Dota 2 patch posts with a server-side `tags=patchnotes` filter. Two things the design must absorb: (a) the Steam patch post is often only a pointer ("Patch 7.41f is out now ... check out the patch notes [url]here[/url]") to `https://www.dota2.com/patches/<version>`, so the post is a signal with title, date and link rather than a structured change list; (b) one gameplay patch (7.41e) is not tagged `patchnotes`, so the tag alone under-selects.
- **Limits and price, read from the deployed service.** `GET https://api.opendota.com/api/metadata` returns `"freeCallLimit":3000,"freeRateLimit":60,"premRateLimit":3000`; the key page's deployed bundle shows `$0.01 per 100 calls`, "Unlimited" call limit for a keyed account and a payment method required. So: keyless = 60 calls per minute and 3,000 per day (per client IP); keyed = 3,000 per minute, no daily cap, about $0.0001 per call (the source default of 300 per minute is not what production serves). Signalling: `X-Rate-Limit-Remaining-Minute` always and `X-Rate-Limit-Remaining-Day` keyless only, HTTP 429 with a JSON `error`, no `Retry-After`. A parse request costs 10 rate units.
- **OpenDota publishes no written terms for the API.** Its "Privacy & Terms" link is a 2014 FAQ whose whole terms section is "The service is provided on a best-effort basis." It sets no attribution, caching or commercial-use clause for API data; it asks for credit only when the MIT-licensed code is reused. A link back to `opendota.com/matches/{id}` is a courtesy and a path to the parse view, not an obligation. MagicBot's policy should say this plainly and name OpenDota and Valve as data sources.
- **The keyless daily allowance is the binding constraint; with a key, money is.** 3,000 a day is about 2 a minute. A uniform interval fits a few dozen accounts; activity-tiered polling gives hot accounts 5-minute freshness at the cost of a 30-minute uniform interval (about 51 calls an account a day, 37 keyless accounts after an interactive reserve). Keyed, the minute limit stops binding (about 67,000 accounts at the tiered mix) and the cost is about $0.15 per tracked account per month.
- **One `recentMatches` call per distinct account per tick, one `matches/{id}` call per new match, never an automatic parse request.** Live checks confirm the split: `recentMatches` carries K/D/A, GPM/XPM, last hits, hero and tower damage, healing, lane and role (when parsed); the detail call adds denies, net worth, Radiant/Dire score, talents and items; an unparsed match returns `lane`, `lane_role`, `is_roaming`, `purchase_log` and `lane_efficiency_pct` as null. Lane outcome is not an OpenDota field.
- **Account input: Steam64, 32-bit id, and the `opendota.com`, `dotabuff.com` and `steamcommunity.com/profiles` URL forms need no key** (`account_id = steam64 - 76561197960265728`). Vanity names need a Steam Web API key; a keyless call returns HTTP 400 `Required parameter 'key' is missing`. Keep vanity resolution an opt-in capability used only on a user's own typed request. SteamDB's patch-notes RSS is rejected: it is a depot-build feed (`Dota 2 update for 19 October 2026 / SteamDB Build 26065111`) that SteamDB says is "not intended to be used for automatically monitoring for new patches", and its FAQ disallows scraping.

## 3. Findings

Evidence tiers: **consensus** (multiple independent credible sources or a standard), **practice** (what mature code visibly does), **single source** (one source's statement, including a service's own code or live response for its own behaviour). "Live" means read from the running service on 2026-10-20 and re-runnable.

### 3.1 OpenDota limits, keys and signalling

- **Deployed values.** Live `GET /api/metadata` (not rate limited: the response carries no `X-Rate-Limit-*` headers) returned `"freeCallLimit":3000,"freeRateLimit":60,"premRateLimit":3000`. Tier: single source (live). The code defaults (`odota/core` `config.ts` @ `449fb7b`: `API_FREE_LIMIT: "3000"`, `NO_API_KEY_PER_MIN_LIMIT: "60"`, `API_KEY_PER_MIN_LIMIT: "300"`, `API_BILLING_UNIT: "100"`, `ENABLE_API_LIMIT: ""`) agree for the free tier but not the keyed minute limit, which production sets ten times higher. Live keyless responses carry `X-Rate-Limit-Remaining-Minute` and `X-Rate-Limit-Remaining-Day`; those headers are only set inside the `ENABLE_API_LIMIT` branch of `svc/web.ts`, so the limiting is on in production. Whether a daily 429 is actually returned was not exercised (Gap 2). The OpenAPI text still says "remove monthly call limits", and a 2018 blog post advertised 50,000 calls per month; both are superseded by the daily figure in `/metadata`.
- **Who is counted.** `svc/web.ts` keys counters by API key when a valid one is sent (`Authorization: Bearer <key>`, documented in the live OpenAPI `securitySchemes`, or `?api_key=`), otherwise by client IP (`cf-connecting-ip`, else `req.ip`). Minute counters expire at the next wall-clock minute, day counters at the end of the UTC day. Consequences: every shard or process behind one public IP shares one keyless quota; counters are incremented before the limit check, so requests answered with 429 still count. A key in a header, not the query string, keeps it out of URL logs. Tier: single source (the service's own code).
- **Signalling.** Over the limit the answer is HTTP 429 with body `{"error": "minute rate limit exceeded"}` or `{"error": "daily api limit exceeded"}`; the daily check applies to keyless requests only (`!res.locals.isAPIRequest && remDay < 0`). A malformed key (not a UUID) gets HTTP 400 `Invalid API key format`; an unknown or cancelled key gets HTTP 400. There is no `Retry-After` (nothing under `svc/` sets it), so the pause target is the next minute boundary or UTC midnight. Tier: single source.
- **Cost of a parse request.** The live OpenAPI states for `POST /request/{match_id}`: "Submit a new parse request. This call counts as 10 calls for rate limit (but not billing) purposes." The middleware adds 10 to both counters. Tier: single source (live spec plus code).
- **Key price and billing.** The deployed key page (bundle `assets/index-Beg1ol7M.js` plus the language chunk) renders: Free tier "Key Required? No", "$limit per day", "$num calls per minute"; Premium tier "$price per $unit calls" with `s=100` and `m=.01` in the page script (that is $0.01 per 100 calls), "Yes -- requires payment method", call limit "Unlimited", and the strings "You're charged $cost per call, rounded up to the nearest cent.", "Getting an API key requires a linked payment method. We'll automatically charge the card at the beginning of the month for any fees owed." and "Responses with status codes 404, 429 or 500 aren't billed." Billing in `svc/apiadmin.ts` sends `quantity: Math.ceil(usageCount / Number(config.API_BILLING_UNIT))` for the month's recorded successful keyed calls, with no free allowance subtracted. So $0.0001 per call from the first call. Tier: single source (the service's own deployed client and code).
- **Key terms.** One active key per OpenDota account; a key is a UUID. Tier: single source (code).

### 3.2 OpenDota's terms of use

Tier: single source (the only terms text the service publishes).

- The site's "Privacy & Terms" footer link (deployed bundle: `{name:e.app_privacy_terms,path:"//blog.opendota.com/2014/08/01/faq/#what-is-your-priv...`) points to the 2014 FAQ at `blog.opendota.com/2014/08/01/faq/`. That page's sections on the subject say: data "comes from public sources such as the Steam WebAPI, Steam community profiles, and match replay files"; Valve lets a player opt out by leaving "Expose Public Match Data" unchecked, which makes them anonymous in future matches while "existing data is not deleted"; analytics cookies on the site; and, under "What are your terms and conditions?", only "The service is provided on a best-effort basis. Since it relies on Valve infrastucture, we cannot make any guarantees of availability."
- **Attribution:** no requirement for API data. The FAQ asks "We would also appreciate a credit/attribution in your project if you use the code!", which concerns reuse of the MIT-licensed code. **Caching:** no clause. **Commercial use:** no clause on API data; the FAQ says the code licence "allows commercial and personal usage free of charge", and the project says it does not intend to profit, with a per-call price for keyed use. No separate terms page exists (`www.opendota.com/terms` and `/privacy` return the single-page-app shell; `docs.opendota.com/terms` is 404). The `odota/core` and `odota/web` READMEs contain no terms.
- Practical reading: caching responses for the life of a fan-out and for constants is consistent with how OpenDota itself caches (60 s Redis match cache when enabled). The service sets no clause either way, so the safe stance is to cache modestly, identify the bot with a `User-Agent`, stay inside the published limits, and link back.

### 3.4 Freshness and the parsed/unparsed split

- **Freshness (measured, partial).** Five `GET /publicMatches` samples over about three minutes on 2026-10-20 gave, for the newest listed match, a time since its end (`start_time + duration`) of 38 s, 46 s, 91 s, 137 s and 76 s; the 10th percentile of each 100-row sample was 199 to 224 s and the median about 355 s. `publicMatches` is a random sample, so its newest row overstates the delay of the very newest match; it shows that matches are visible within about 40 s to a few minutes of ending, not a guaranteed bound. The per-player `recentMatches` path was not measured end to end (Gap 3). Source behaviour agrees: `svc/scanner.ts` polls Valve's `GetMatchHistoryBySequenceNum` in a loop ("This endpoint is limited to something like 1 request every 5 seconds"). Tier: single source (live sample plus code).
- **Matches that never arrive.** `svc/scanner.ts`: "This is sometimes 99 now since Valve is hiding high MMR matches"; `svc/fullhistory.ts`: "As of March 2025 high level matches are removed from results but still counted in results_remaining". Players with "Expose Public Match Data" off are anonymous in the feed (OpenDota FAQ). The tracker needs an "account has no visible matches" outcome distinct from "no new match".
- **History before the first poll.** A newly seen account has only matches OpenDota scanned since discovering it; `POST /players/{id}/refresh` backfills up to 500 from Valve's per-player history.
- **What needs a parse (confirmed live).** On a parsed match document (`od_data.has_parsed: true`, `version: 22`) the player object had `lane`, `lane_role`, `is_roaming`, `lane_efficiency_pct`, `lane_pos`, `purchase_log`, `first_purchase_time`. On an unparsed match (`od_data` `has_api: true, has_gcdata: true, has_parsed: false`, no `version`) those were all null, while `net_worth`, `denies`, `ability_upgrades_arr`, `item_0`..`item_5`, `item_neutral` and the Radiant/Dire score were present. `lane`, `lane_role` and `is_roaming` are computed from `lane_pos` which only the replay parse produces (`getLaneFromPosData` in `svc/util/compute.ts`).
- **Who is auto-parsed.** `queueParse` in `svc/util/insert.ts` auto-parses a fresh match only when a player in it is in the "tracked" set (OpenDota subscribers plus contributors, `cacheTrackedPlayers` in `svc/util/queries.ts`) or it is a league match. Otherwise the match stays unparsed until someone calls `POST /request/{match_id}`. The OpenDota FAQ: replay data "usually takes a few minutes after the match is played to become available"; users "can request a parse of any match manually as long as the replay hasn't expired from Valve servers"; replays "generally expire after 10 days".
- **Parse request mechanics.** The server queues a `gcdata` job and a `parse` job into a priority queue behind auto-parses of tracked players, so a request has no guaranteed latency. MangoByte polls the job every 20 s for up to 120 s.
- **Detecting parsed state.** `od_data` (`has_api`, `has_gcdata`, `has_parsed`, `has_archive`) is present on live match documents but absent from the OpenAPI schema; treat as optional and fall back to "lane fields non-null".
- **Server-side caching.** `MATCH_CACHE_SECONDS: "60"` when `ENABLE_MATCH_CACHE` is set; there is no cache-header contract, and the live responses carry only an `ETag`.

### 3.5 Account resolution

- **Conversion.** `account_id = steam64 - 76561197960265728` and `steam64 = account_id + 76561197960265728` (`convert64to32`, `convert32to64`, `isSteamID64` in `svc/util/utility.ts`; MangoByte subtracts the same constant). Tier: practice (two independent codebases). Use `Long`.
- **Forms that need no key.** MangoByte's link command accepts `opendota.com/players/<id>`, `dotabuff.com/players/<id>`, `steamcommunity.com/profiles/<id64>` and a bare number, then fetches the player to confirm it exists. It does not resolve vanity names. Tier: practice (one mature bot).
- **Vanity names.** `steamcommunity.com/id/<vanity>` needs `ISteamUser/ResolveVanityURL/v1`. Valve's Steamworks documentation (`partner.steamgames.com/doc/webapi/ISteamUser`) lists `key` (string, required, "Steamworks Web API user authentication key"), `vanityurl` (string, required, "The vanity URL to get a SteamID for") and `url_type` ("1 (default): Individual profile, 2: Group, 3: Official game group"). A keyless call returned HTTP 400 "Required parameter 'key' is missing" (live). Response shape: Valve's documentation page does not state it; a typed third-party client models `response: { success: 1 | 42; steamid?: string; message?: string }` (`JonaWe/steam-api-wrapper-ts`, `ResolveVanityURL.ts`), 42 being "no match". Tier: single source (third-party wrapper); the Valve wiki page that documents it is behind a bot challenge (Gap 5).
- **Steam Web API key: who may get one, and the terms.** Valve's "Authentication using Web API Keys" page: "The standard user keys are available to everyone, all that is required is a Steam account and the domain name that will be associated with this key." Accounts under $5.00 of Steam spend are "limited" and cannot use the Web API (`help.steampowered.com` Limited User Accounts lists "Accessing the Steam Web API" and the $5.00 threshold). The Steam Web API Terms of Use (`steamcommunity.com/dev/apiterms`, "Last updated July 2010") require, among other things: "You will post a privacy policy regarding the use of nonpublic end user data (including such Steam Data), and you will treat the Steam Data consistent with that policy. You will only retrieve Steam Data about a Steam end user as requested by the end user. You will inform the end user about any Steam Data you will store, and you will store the Steam Data in a country (or countries) identified in your privacy policy."; "You agree to keep your Steam Web API key confidential, and not to share it with any third party."; "You may not present the Steam Data ... so that it appears (a) that your Application is endorsed or affiliated with Valve or Steam"; and "You are limited to one hundred thousand (100,000) calls to the Steam Web API per day." Valve "may change or terminate the Steam Web API entirely or your access in particular." Tier: single source (the terms page; a 2010 text that names a per-key licence, so its application to keyless endpoints is not stated).
- **What that means for a public bot.** The 100,000-a-day cap is two orders of magnitude above this bot's needs. The binding terms are the privacy-policy and per-user-request clauses, the keep-secret clause, and the no-implied-affiliation clause. A vanity lookup typed by the user, storing only the resulting account id, fits them; a background loop over Steam user data does not. The key never belongs in the tracker.
- **No-key fallback.** `GET /search?q=<name>` finds players by persona name; it can offer a pick list but cannot be an authoritative link.

- **What Steam's feed carries for app 570 (live, `count=20`, `maxlength=200`).** `appnews.count` is 3,253 items. Items come from several feeds: `steam_community_announcements` (feed type 1: Valve's own posts) and third-party press such as PC Gamer and PCGamesN (feed type 0). A selection rule of "`tags` contains `patchnotes` or title matches `Gameplay Patch` / `Update`" in `steam_community_announcements` covers all seven in the window read.

The 7.41f post body is a pointer to `https://www.dota2.com/patches/7.41f` plus a list of bug fixes; the 7/1/2026 post carries 7.5 KB of text. In one sample the Steam post appeared about 12 hours after the `patch_timestamp` that dota2.com lists for the same patch (07:00 vs 18:44 UTC on 2026-09-15). `maxlength=0` returns full content.
- **Caching hint.** The response carries `Expires` one hour ahead of `Date`. `ThomasBassa/steam-news` also stores items by `gid`. An hourly poll is ample.
- **SteamDB's statements (FAQ, read at source).** "Does SteamDB have an API?" — "We are looking to build better relations and tools for developers and publishers. This will most likely mean an API at some point." "Can I use auto-refreshing plugins or automatically scrape/crawl SteamDB?" — "No, there's a chance you'll get automatically banned for doing so. We also do not allow scraping/crawling on SteamDB. Please get the information from Steam itself." "Do you have an RSS for game updates?" — "Yes, there is an RSS available on individual game's patchnotes page. However this is heavily cached and is not intended to be used for automatically monitoring for new patches." The RSS response sends `Cache-Control: public, max-age=3600` and `ttl` 3600. SteamDB's Discord-bot terms are unrelated to this use.
- **Consequence for the feed parser.** Both qualifying sources are JSON, so the Dota patch-notes poll needs no RSS/Atom parser; Rome stays a dependency of the feeds plugin in `bottools-plugins` only.
- **Old behaviour to drop.** Today's `postPatchNotes` scrapes SteamDB through an HTML scraper and posts text-to-speech. The replacement posts title, link and a short excerpt, de-duplicated by `gid`.

- **Lane outcome.** Dotabuff's "lane outcome" has no OpenDota counterpart. Either drop the line or define a clearly named OpenDota-derived value (lane efficiency percentage, parsed matches only). A won/lost label from gold at minute 10 would be an invented metric.

- **Three ways to get the constants.** (a) `GET /constants/{resource}` on the API (1 budgeted call each); (b) raw files at a pinned commit; (c) a build-time snapshot. Constants change when a hero or item is added, so the provider survives an unknown id (`Hero #N`, no icon).

No shared temp file is involved, so concurrent invocations cannot overwrite each other.

## 4. How comparable projects do it

- **MangoByte** (`mdiller/MangoByte` @ `c56f30f`, `cogs/dotastats.py`). Appends the owner's OpenDota key to every query (`opendota_query_get_url`); fetches the last match with `/players/{id}/matches?limit=1&significant=0`; caches `/matches/{id}` only once `is_parsed` is true; requests a parse with `POST /request/{id}`, waits 3 s, polls `/request/{jobId}` every 20 s up to 120 s, treats a `null` job as done; links every embed to `https://www.opendota.com/matches/{id}` and `.../players/{id}`; its link command accepts a Steam32 id, Steam64 id, an OpenDota/Dotabuff player URL or a `steamcommunity.com/profiles/` URL and validates by fetching the player. It does not poll for new matches or resolve vanity names.
- **OpenDota's own web client** (`odota/web` @ `91b1d42`). Image URLs are CDN base plus the constant's path; the key page shows price and limits from `/metadata`.
- **`steam-news`** (`ThomasBassa/steam-news`). Calls keyless `GetNewsForApp` with `maxlength=0&count=10`, stores items by `gid`.
- **No public Dota 2 Discord bot with automatic match posting at scale was found.** A GitHub repository search for Dota Discord bots (2026-10-20) returned MangoByte, a stack-assembly bot, a lobby/inhouse bots and a reminder bot, none of which polls players for new matches in the code read. The polling model in section 6 is derived from the enforcement code and is not a copy of any bot.

## 5. Pitfalls and regrets

- **Per-IP keyless quota, hidden sharing.** Counting is by IP. A bot on a shared or NATed host, or several shards behind one address, shares 3,000 per day with everything on that address; the budget is process-wide and reads `X-Rate-Limit-Remaining-Day` back. MagicBot's host is outside this work, so the IP is unknown.
- **429s are not free.** The server increments before it checks, so retrying into a 429 digs deeper. Pause until the minute boundary (or UTC midnight on a daily 429); slow down using the remaining-count headers before the limit.
- **Billing surprises on a key.** Every successful keyed call is billed from the first; there is no keyed free allowance in the billing code. A looping tracker bug costs $10 per 100,000 calls. A keyed configuration needs a hard daily stop.
- **`recentMatches` is 20 rows with no `limit`.** An account that plays more than 20 matches between polls loses matches; at any realistic interval this is safe.
- **`matches` hides non-standard modes by default** (`significant=1`).
- **Unparsed matches show null lanes.** Auto-posting renders "lane unavailable"; an automatic parse request per posted match is not affordable (10 units plus polling).
- **Undocumented fields move.** `net_worth`, `od_data`, `item_neutral2` work but are outside the OpenAPI schema: optional fields, unknown keys ignored.
- **Accounts OpenDota has not seen** return 404 on the profile; accounts with the public-match setting off return empty lists. Different user-facing advice.
- **High-MMR matches may be missing** after March 2025; a tracked top-rank account can look inactive.
- **Docs disagree with code and with each other.** The OpenAPI text says "monthly", the config comment says "per day", the code default keyed minute limit is 300 while production serves 3,000. The tracker reads live headers and the `/metadata` document, and treats configured numbers as defaults.
- **Steam tag filter under-selects** (7.41e untagged) and **Steam patch posts are often pointers.** Select on tag or title; render title, link and excerpt.
- **SteamDB's RSS looks like a patch feed and is not one**: build ids only, heavily cached.

## 6. Recommendation for this repo

**Provider shape.** One `OpenDotaDotaProvider` behind a game-agnostic stats-provider interface that expresses what Dota 2 needs and nothing OpenDota-specific:

- `resolveAccount(input): Result<AccountRef>` for the key-free forms (value classes `AccountId(Long)` and `SteamId64(Long)` with base constant `76561197960265728`; a number below `2^32` is an account id, at or above the base is a Steam64, anything between is rejected), returning a distinct "needs vanity lookup" failure for `/id/<name>`. Vanity resolution is an optional capability (a small separate interface) present only when a Steam key is configured, so the provider's capability set rather than a nullable method tells callers what it can do.
- `profile(id)`, `recentMatches(id)` (newest first, `match_id` as cursor), `matchDetail(id)`, and an optional `ParseRequester` capability (`requestParse`, `parseStatus`) costing 10 budget units. Lookups that can miss (unknown account, unknown match, private history) are `Result` failures with distinct types, never nullable returns.
- Match models make parsed state explicit: a sealed `MatchDetail` with unparsed and parsed forms, or `parsed: Boolean` plus a nullable lane group; lane, role, roaming, efficiency and item timings exist only on the parsed form. Wire types are `internal` serializable classes with unknown keys ignored, mapped to public domain types; the wire shape is not exposed.
- Constants load through a cached, refreshable component (daily refresh, `Hero #N` fallback) trimmed to the modelled fields on decode; do not retain `abilities.json` whole.
- The HTTP client sends the key (when configured) as `Authorization: Bearer`, a descriptive `User-Agent`, and reads `X-Rate-Limit-Remaining-*` into the shared budget; startup reads `/metadata` once to set the limits, with the code defaults as fallback.

**Budget model.** Two lanes, `interactive` (commands) and `tracker`, sharing one per-provider budget. Reserve a fixed share for interactive calls (the examples use 500 a day); the tracker spends the rest and stretches its intervals, not drops accounts, when demand exceeds it.

Assumptions, labelled as such: 3 matches per tracked account per day (a judgment); 20% safety margin below the limit; keyless 60 per minute and 3,000 per day, keyed 3,000 per minute (all live `/metadata`).

*Per-account cost.* Polling every `T` seconds costs `86400 / T` calls a day; each new match adds one detail call (shared when two tracked accounts were in one match and fanned out to every subscription following either). Subscriptions are per guild, polls per distinct account, so many guilds following one account cost one poll.

*Keyless, uniform interval* (tracker budget 1,900 calls a day = 3,000 x 0.8 - 500):

| Interval T | Calls per account per day (incl. 3 detail calls) | Accounts that fit |
|---|---|---|
| 5 min | 291 | 6 |
| 15 min | 99 | 19 |
| 30 min | 51 | 37 |
| 60 min | 27 | 70 |

The 60-per-minute limit is not binding at these sizes.

*Prioritised by recent activity.* Tiers by time since the account's last match ended: hot (under 2 hours) every 5 minutes, recent (under 24 hours) every 30 minutes, dormant every 3 hours. At a mix of 10% hot, 30% recent, 60% dormant the average is `0.10 x 288 + 0.30 x 48 + 0.60 x 8 = 48` polls a day plus 3 detail calls = 51 a day per account: the cost of a uniform 30-minute interval (37 keyless accounts), with active players seen within about 5 minutes. A floor of about 2 minutes is the shortest worthwhile interval, because Valve's publication delay (tens of seconds to minutes, 3.4) dominates below that. When the account's last match is still in progress (`start_time + duration` in the future or just past), poll sooner. Add jitter so hot accounts do not all poll on the same tick.

*Keyed.* No daily cap and a 3,000-per-minute limit, so money binds first. Cost per tracked account per month at $0.0001 per call: uniform 2 min $2.17, 5 min $0.87, 15 min $0.30, 30 min $0.15, 60 min $0.08; tiered mix $0.15. For 100, 1,000 and 10,000 accounts the tiered mix costs about $15, $153 and $1,530 a month and averages 3.5, 35 and 354 calls a minute; the minute limit (80% = 2,400) would bind only beyond roughly 67,000 accounts. The tracker's call budget is therefore a configured calls-per-day figure derived from what the operator will pay, with a hard stop. Moving from keyless to keyed becomes worthwhile when the tracked set exceeds about 40 accounts at the tiered mix.

*Parse requests.* Never automatic. A parse costs 10 units plus polling (MangoByte-style 20 s polling for up to 2 minutes is 6 calls) and a detail refetch: about 17 calls against 2 for an unparsed post. Offer parsing only on an explicit user command, reserve it for the interactive lane, and let auto-posts say lane data is unavailable unless OpenDota already parsed the match.

*Behaviours that follow.* On a 429, pause the whole provider until the next minute boundary (minute 429) or UTC midnight (daily 429), keep polling state, resume without a burst. When `X-Rate-Limit-Remaining-Day` falls below the interactive reserve, stretch tracker intervals by the ratio of demand to what remains. Cache `matchDetail` by `match_id` for the life of a post fan-out; cache parsed matches much longer than unparsed ones.

**Account links.** Accept the key-free forms by default. Make the Steam key optional configuration that enables `steamcommunity.com/id/<name>` only; call it only for a vanity the user typed, and name in the privacy policy which Steam data is stored and where (account id and display name). Verify a link by fetching `players/{id}`: a 404 gets "OpenDota has not seen this account"; an empty `recentMatches` gets the "enable Expose Public Match Data" message. Links stay global per Discord user; the tracker subscribes by guild.

**Patch notes.** A `GameNewsSource` in `bottools-stats` backed by `GetNewsForApp` (item id `gid`, title, url, date, tags, contents), polled hourly with `count` small, `feeds=steam_community_announcements` and a client-side selection of "tag `patchnotes` or title matches `Gameplay Patch` / `Update`". De-duplicate by `gid` per subscription cursor. Post title, link to `https://www.dota2.com/patches/<version>` (extract from the post's `[url]` when present), and a trimmed excerpt converted from BBCode. `dotaconstants` `patchnotes.json` is an optional enrichment; the undocumented `dota2.com/datafeed` is not used. No RSS parser in `bottools-stats`.

**Attribution and third parties.** Footer text or description carries "Data: OpenDota" linked to `opendota.com/matches/{id}` (also the user's route to the parse view), alongside the existing "Automated message" / "Requested by" content. MagicBot's privacy policy and terms name the third parties: OpenDota (match and profile data, which OpenDota collects from Valve's public match feed and replays), Valve/Steam (patch-notes feed, Valve's image CDN, and, when configured, vanity resolution through the Steam Web API under its terms), and any feed host an administrator subscribes a channel to. The terms add that MagicBot is not affiliated with or endorsed by Valve (Steam Web API Terms §2), and the policy states where stored Steam data lives.

**Rejected.** Per-subscription polling (a per-guild loop) multiplies calls by the guilds following one account. Resolving vanity names by default needs a secret key, a privacy-policy disclosure and a clause that limits retrieval to the user's request. Auto-parsing every posted match is unaffordable. STRATZ as a second provider is rejected: unreadable terms, no need. SteamDB's RSS and the undocumented `dota2.com` datafeed are rejected as sources.

## 8. Gaps

1. **OpenDota's terms for caching and commercial use are not written anywhere reachable.** The only published text is the 2014 FAQ ("best-effort basis"; code credit appreciated). No contact was made. If MagicBot's policy needs OpenDota's position on caching match data or on a public bot with many subscribers, the question goes to `support@opendota.com` (the address shown on the key page); no message has been sent.
2. **Whether the daily 429 is returned in production.** The headers and `/metadata` show the limits are active, but exceeding 3,000 calls was not tried. The tracker treats a daily 429 as possible and honours the headers.
3. **End-to-end freshness is only partly measured.** The `publicMatches` sample shows matches visible within roughly 40 s to a few minutes of ending; the `recentMatches` path for a specific tracked account was not timed (it needs an account that finishes a match during the test). The 2-minute polling floor is a judgment.
4. **No public Dota 2 Discord bot with automatic match posting at scale was found**, so the polling model has no field-tested precedent; its constants (3 matches per account per day, tier thresholds, population mix, 500-call interactive reserve, 2-minute floor) are labelled assumptions, not measurements.
5. **`ResolveVanityURL` response semantics.** The Valve wiki page that documents the response (`developer.valvesoftware.com/wiki/Steam_Web_API`) answers with a bot challenge to this client, and a successful call needs a key (none was used). The `success` 1/42 shape comes from a third-party client only. Steam's `GetNewsForApp` terms coverage for keyless calls is not stated either: the 2010 terms describe key licensees.
6. **Valve CDN terms.** No published terms for hotlinking or caching images from `cdn.cloudflare.steamstatic.com` were found (searched, and the Steam Web API terms §9 only state ownership). Using the constants' paths is what OpenDota's own client does; whether that is permitted for a third party is unestablished.
7. **STRATZ.** Its own pages are script-rendered or refuse this client (`api.stratz.com` 403, `stratz.medium.com` 403), so claim 20 is unverified. Comparison only.
8. **Steam key registration conditions beyond the above.** The $5.00 limited-account rule and the "Steam account plus domain name" requirement were read; the live registration form (`steamcommunity.com/dev/apikey`) needs a sign-in and was not opened. Whether a bot with no web domain can register (what to put in the domain field) is not established.
9. **Net worth outside parsed matches is verified only on two sampled matches.** `net_worth` was present in both a parsed and an unparsed live match; the model still treats it as optional because the schema omits it.
10. **Patch-post selection is validated on one window.** The "tag or title" rule covered seven gameplay patches from March to September 2026; later patch posts may follow other title patterns.
