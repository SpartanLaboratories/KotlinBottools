## 1. Question

What can OpenDota and Steam provide for Dota 2 account links, profiles, match history, match detail and patch notes, and what call budget does a public bot that posts new matches automatically have to live within? An answer has to give: the endpoints and fields the Dota 2 provider needs; account resolution (Steam64, account id, profile URL, vanity name); the rate limits, key price, signalling and terms; how fresh recent matches are and which fields need a parsed match; a calls-per-tracked-account model; a patch-notes source that is documented and not scraped (which also decides whether a feed parser is needed in the stats module); and image URLs from documented constants plus a CDN.

## 2. Bottom line

- **Unfinished — needs a planner re-pass: OpenDota's published limits and terms of use, and the live content of the patch-notes sources; unreachable: `api.opendota.com`, `docs.opendota.com`, `www.opendota.com`, `blog.opendota.com`, `api.steampowered.com`, `steamcommunity.com`, `partner.steamgames.com`, `developer.valvesoftware.com`, `steamdb.info`, `www.dota2.com`, `cdn.cloudflare.steamstatic.com`, `api.stratz.com`, `stratz.com`.** Everything below about limits, price and fields is read from OpenDota's own open-source server and web client (the code that enforces and displays them), which is authoritative for defaults and wire shape but is not the deployed configuration (`GET /api/metadata`, which serves the live values, was not reachable). The terms of use were not readable at all (Gaps 1 to 3).
- **Provider: OpenDota, no key required to start, a key before the audience grows.** Defaults in the server source: 60 calls per minute and 3,000 per day per client IP without a key; 300 per minute with a key and no daily cap, billed at $0.01 per 100 calls ($0.0001 per call) with 404, 429 and 500 responses not billed. Limits are signalled by `X-Rate-Limit-Remaining-Minute` (always) and `X-Rate-Limit-Remaining-Day` (keyless only), and by HTTP 429 with a JSON `error`; there is no `Retry-After`. A parse request counts as 10 calls toward the rate limits.
- **The daily keyless allowance, not the per-minute one, is the binding constraint.** 3,000 calls a day is about 2 a minute. Polling every tracked account on a uniform interval supports only a few dozen accounts; activity-tiered polling (hot accounts every 5 minutes, dormant ones every 3 hours) gives the same 5-minute freshness for active players at the cost of a 30-minute uniform interval. A keyed bot pays about $0.15 per tracked account per month at that profile and about $0.87 at a uniform 5-minute interval.
- **One `recentMatches` call per distinct account per tick, one `matches/{id}` call per new match, never an automatic parse request.** `recentMatches` already carries K/D/A, GPM/XPM, last hits, hero and tower damage, healing, duration, winner, hero and (when the match is already parsed) lane and role. Denies, net worth, items, talents and the Radiant/Dire score need the detail call. Lane outcome is not an OpenDota field at all.
- **Account input: Steam64, 32-bit account id, `opendota.com/players/<id>`, `dotabuff.com/players/<id>` and `steamcommunity.com/profiles/<id64>` need no key** (`account_id = steam64 - 76561197960265728`). Vanity names (`steamcommunity.com/id/<name>`) need a Steam Web API key and are best left as an opt-in capability driven by configuration, used only on a user's own request.
- **Patch notes are JSON, so no feed parser belongs in `bottools-stats`.** The documented candidates are Steam's keyless `ISteamNews/GetNewsForApp` (JSON) and `odota/dotaconstants` `build/patchnotes.json` (MIT, derived from game files). SteamDB's RSS is rejected (no API, scraping disallowed) and `dota2.com/datafeed/...` patch endpoints are undocumented. What Steam's news feed for app 570 actually carries was not observable and needs a live check.
- **Images: `https://cdn.cloudflare.steamstatic.com` plus the `img` or `icon` path that `dotaconstants` stores on each hero and item**; no HTML is needed. The item line is composed in memory per invocation from cached icon bytes, with no shared temp file.

## 3. Findings

Evidence tiers: **consensus** (multiple independent credible sources or a standard), **practice** (what mature code visibly does), **single source** (one source's statement, including a service's own code for its own behaviour).

### 3.1 OpenDota limits, keys and signalling

- **Defaults and enforcement.** `config.ts` defines `API_FREE_LIMIT: "3000"`, `NO_API_KEY_PER_MIN_LIMIT: "60"`, `API_KEY_PER_MIN_LIMIT: "300"`, `API_BILLING_UNIT: "100"` and `ENABLE_API_LIMIT: ""` (limits are enforced only when set). Tier: single source (the service's own code). Applies to `odota/core` @ `449fb7b`. The deployed values are unverified (Gap 1). A 2018 blog post advertised 50,000 calls per month for the free tier; the current code and web client express a daily figure instead, and the OpenAPI text in `svc/api/spec.ts` still says "remove monthly call limits", so published numbers have moved and the code is the better authority.
- **Who is counted.** The middleware in `svc/web.ts` keys counters by API key when a valid one is sent (`?api_key=` or `Authorization: Bearer`), otherwise by client IP (`cf-connecting-ip`, else `req.ip`). Minute counters expire at the next wall-clock minute (`getStartOfBlockMinutes(1, 1)`), day counters at the end of the UTC day (`getEndOfDay`). Consequences: a restart does not reset the server's count; every shard or process behind one public IP shares one keyless quota; counters are incremented before the limit check, so requests answered with 429 still count.
- **Signalling.** Every limited response carries `X-Rate-Limit-Remaining-Minute`; keyless responses also carry `X-Rate-Limit-Remaining-Day`; `X-IP-Address` echoes the address the server saw. Over the limit the answer is HTTP 429 with body `{"error": "minute rate limit exceeded"}` or `{"error": "daily api limit exceeded"}`. A search for `retry-after` under `svc/` finds nothing, so the pause target is the next minute boundary or UTC midnight. Keyed requests are never refused for the daily total; the daily 429 applies to keyless requests only. Tier: single source.
- **Cost of a parse request.** `POST /request/{match_id}` is documented in the spec as "This call counts as 10 calls for rate limit (but not billing) purposes."; the middleware adds 10 to both the minute and the day counter. Tier: single source.
- **Key price and billing.** `odota/web` `Api.tsx` hard-codes `premUnit = 100` and `premPrice = 0.01`, and shows fees as `premPrice * ceil(usage_count / premUnit)`. The strings say "You're charged $cost per call, rounded up to the nearest cent." and "Responses with status codes 404, 429 or 500 aren't billed." Getting a key "requires a linked payment method" and the card is charged at the beginning of the month. The usage recorder counts every successful keyed call (not 404/429/500) against the month, with no free allowance subtracted. That is $0.0001 per call. The live rate limits shown on the key page come from `GET /api/metadata` (`freeCallLimit`, `freeRateLimit`, `premRateLimit`, which read the same config), so the production numbers are one request away from being verified (Gap 1). Tier: single source.
- **Key terms.** One active key per OpenDota account (the key-management router treats a subscription and a key as one-to-one). A key is a UUID; any other format is rejected with HTTP 400. Tier: single source.

All under `https://api.opendota.com/api` (the `servers` entry of the OpenAPI spec in `svc/api/spec.ts`). Tier: single source (the spec is generated from the same routes).

### 3.3 Freshness and the parsed/unparsed split

- **Freshness.** `svc/scanner.ts` polls Valve's `GetMatchHistoryBySequenceNum` in a loop; the code comments "This endpoint is limited to something like 1 request every 5 seconds" and waits 5 seconds unless the page was mostly full. Each scanned match is inserted into the players' caches that `recentMatches` reads. So OpenDota's own pipeline adds seconds to a few minutes; the dominant delay is how soon Valve publishes a finished match to that feed, which was not measured (Gap 4). Tier: single source, inferred from code, not a measured figure.
- **Matches that never arrive.** The scanner comments "This is sometimes 99 now since Valve is hiding high MMR matches", and `svc/fullhistory.ts` notes "As of March 2025 high level matches are removed from results but still counted in results_remaining". Players who have turned off Dota's "Expose Public Match Data" setting are anonymous in the feed; the player endpoints return an empty list for an account whose history OpenDota marked unavailable (`fh_unavailable`). The tracker therefore needs an "account has no visible matches" outcome that is distinct from "no new match".
- **History before the first poll.** A newly seen account has only the matches OpenDota scanned since discovering it; `POST /players/{id}/refresh` backfills up to 500 matches from Valve's per-player history.
- **What needs a parse.** `lane`, `lane_role` and `is_roaming` are computed from `lane_pos`, which only the replay parse produces (`getLaneFromPosData` in `svc/util/compute.ts`); lane efficiency, `purchase_log`, `first_purchase_time` (item timings), `gold_t`, `xp_t`, wards, teamfights and the like also come from the parse. They are `null` or absent on an unparsed match. Everything else in the table in 3.6 is in the API-sourced data.
- **Who is auto-parsed.** `queueParse` in `svc/util/insert.ts` auto-parses a fresh match only when a player in it is in the "tracked" set or the match is a league match. The tracked set is OpenDota subscribers plus contributors (`cacheTrackedPlayers` in `svc/util/queries.ts`). Any other match stays unparsed until someone calls `POST /request/{match_id}`.
- **Parse request mechanics.** The server queues a `gcdata` job and a `parse` job into a priority queue (lower number first; request jobs rank behind auto-parses of tracked players' matches), so a parse request has no guaranteed latency. Replays may not be available yet for a just-finished match (the auto path retries up to 50 times), and the parser source records that "Valve doesn't keep non-league replays for more than a few weeks". The parse job id is polled with `GET /request/{jobId}` (1 call each). MangoByte, the best-known Dota bot on OpenDota, polls every 20 seconds for up to 120 seconds.
- **Detecting parsed state.** The match document includes `od_data` (`has_api`, `has_gcdata`, `has_parsed`, `has_archive`), set in `buildMatch`; `version` ("Parse version") is also present on parsed matches. `od_data` is not in the OpenAPI schema, so a provider should treat it as optional and fall back to "lane fields non-null".
- **Server-side caching.** OpenDota caches a built match in Redis for `MATCH_CACHE_SECONDS: "60"` when `ENABLE_MATCH_CACHE` is set. There is no per-endpoint cache header contract; the client owns its own cache.

### 3.4 Account resolution

- **Conversion.** `account_id = steam64 - 76561197960265728` and `steam64 = account_id + 76561197960265728` (`convert64to32`, `convert32to64` and `isSteamID64` in `svc/util/utility.ts`; `isSteamID64` is `id >= 76561197960265728`). MangoByte subtracts the same constant. Tier: practice (two independent codebases; the constant is Valve's individual-account base, `0x0110000100000000`). Use `Long`; account ids fit in 32 bits unsigned, Steam64 needs 64.
- **URL forms that need no key.** MangoByte's account-link parser accepts `opendota.com/players/<id>`, `dotabuff.com/players/<id>` and `steamcommunity.com/profiles/<id64>`, and any bare number; it then fetches the player to confirm it exists. It does not resolve vanity names. Tier: practice (one mature bot).
- **Vanity names.** `steamcommunity.com/id/<vanity>` needs `ISteamUser/ResolveVanityURL/v1`, whose parameters in Valve's published interface list are `key` (required), `vanityurl` (required) and `url_type` (optional; 1 individual, 2 group, 3 official game group). Tier: single source (`SteamTracking` `API/ISteamUser.json`, a daily capture of Valve's `GetSupportedAPIList`).
- **Steam Web API key terms.** From excerpts of Valve's Steam Web API Terms of Use (page dated July 2010; the page itself was unreachable, Gap 2): a limit of one hundred thousand calls per day; the key must be kept confidential; the operator must disclose what Steam data it stores and where (privacy policy); "You will only retrieve Steam Data about a Steam end user as requested by the end user"; Valve may change or end the API. Registration (per third-party guides, 2015 to 2016) asks for a domain name and requires an account that has spent at least $5. Tier: single source plus secondary guides, all unverified at the source host. These terms point to keeping the Steam key out of any background loop: use it only for a vanity lookup the user types, and never for tracking.
- **No-key fallback.** `GET /search?q=<name>` finds players by persona name, which is a different thing from a vanity URL and can return many matches; it can offer a pick list but cannot be an authoritative link.

### 3.7 Constants and images

- `odota/dotaconstants` (MIT, `10.8.0`) exposes `build/heroes.json` (127 heroes at this commit; each has `id`, `name`, `localized_name`, `primary_attr`, `roles`, `img`, `icon`), `build/items.json` (501 items; `id`, `dname`, `img`, `cost`, `qual`), `build/item_ids.json` (id to internal name), `build/hero_abilities.json` (`abilities`, `talents`, `facets` per hero), `build/ability_ids.json` and `build/abilities.json` (about 2 MB), plus `patch.json`, `game_mode.json` and `lobby_type.json`. Tier: single source (the repository's own data).
- Image paths are relative: heroes `"img": "/apps/dota2/images/dota_react/heroes/antimage.png?"`, `"icon": "/apps/dota2/images/dota_react/heroes/icons/antimage.png?"`; items `"img": "/apps/dota2/images/dota_react/items/blink.png?t=1593393829403"`. OpenDota's own web client prepends `VITE_IMAGE_CDN || "https://cdn.cloudflare.steamstatic.com"`. Tier: practice (the reference client). No published terms for hotlinking Valve's CDN were found (Gap 6).
- **Three ways to get the constants.** (a) `GET /constants/{resource}` on the API (1 budgeted call each; mirrors the version deployed on OpenDota's side); (b) raw files of the repository at a pinned commit; (c) a build-time snapshot from the package. Constants change when a hero or item is added, so the provider has to survive an unknown hero or item id (show `Hero #N` and no icon) rather than fail.
- **Item line.** Six icons plus backpack and neutral slots composite cleanly in memory: fetch each distinct icon once, keep the decoded bytes in a Caffeine cache keyed by item name, draw into a `BufferedImage` per invocation, and attach the PNG bytes. No file path is involved, so concurrent invocations cannot overwrite each other.

### 3.8 STRATZ as a comparison only

Not readable at source (Gap 7). A STRATZ post found by search describes token tiers where an Individual Token doubles the default to 4,000 calls per hour and 20,000 per day (undated; may be outdated), and MangoByte's `get_stratz_match` shows the REST v1 form `https://api.stratz.com/api/v1/match/{id}` with a bearer token, a required `User-Agent: STRATZ_API` header, and an HTTP 204 for "hasn't received this match yet". What it would add: richer parsed analytics without a replay-parse step and a GraphQL surface. What it costs: a mandatory token for every call, a second client with its own limits and caching, and its terms were not obtainable. It is not part of the design.

## 4. How comparable projects do it

- **MangoByte** (`mdiller/MangoByte` @ `c56f30f`, `cogs/dotastats.py`). Appends the owner's OpenDota key to every query (`opendota_query_get_url`); fetches the last match with `/players/{id}/matches?limit=1&significant=0`; caches `/matches/{id}` only once `is_parsed` is true (an unparsed copy is dropped so the next view refetches); requests a parse with `POST /request/{id}`, waits 3 seconds, then polls `/request/{jobId}` every 20 seconds up to 120 seconds and treats a `null` job as done; links every embed back to `https://www.opendota.com/matches/{id}` and `.../players/{id}`; its link command accepts a Steam32 id, a Steam64 id, an OpenDota/Dotabuff player URL or a `steamcommunity.com/profiles/` URL, and validates by fetching the player. It does not poll for new matches or resolve vanity names.
- **OpenDota's own web client** (`odota/web` @ `91b1d42`). Builds image URLs as CDN base plus the constant's path; shows key price and limits from `/metadata`.
- **`steam-news`** (`ThomasBassa/steam-news`). Calls the keyless `GetNewsForApp` with `maxlength=0&count=10`, stores items by `gid` and respects an expiry time per app, which is the polite pattern for a patch-notes poller.
- **No public Dota 2 Discord bot with automatic match posting at scale was found in the sources reachable here**; the polling model in section 6 is derived from the enforcement code and is not a copy of any bot.

## 5. Pitfalls and regrets

- **Per-IP quota, hidden sharing.** Keyless counting is by IP. A bot on a shared or NATed host, or several shards behind one address, shares 3,000 per day with everything else on that address; the budget must be process-wide and read back from `X-Rate-Limit-Remaining-Day`.
- **429s are not free.** The server increments before it checks, so retrying into a 429 digs the counter deeper. Pause until the minute boundary (or UTC midnight on a daily 429) and use the remaining-count headers to slow down before the limit.
- **Billing surprises on a key.** Every successful keyed call is billed from the first call; there is no keyed free allowance in the billing code. A tracker bug that loops costs money at $0.0001 per call (100,000 calls is $10). A keyed configuration needs a hard daily stop in the budget.
- **`recentMatches` is 20 rows with no `limit`.** That bounds the poll gap: an account playing more than 20 matches between polls loses matches. At any realistic interval this is safe, which is also why polling less often is acceptable.
- **`matches` hides non-standard modes by default** (`significant=1`). A "last match" command that uses `matches?limit=1` without `significant=0` skips turbo and similar matches.
- **Unparsed matches show null lanes.** Auto-posting must render "lane unavailable" rather than a blank; and an automatic parse request per posted match is not affordable (10 rate units plus polling, section 6).
- **Undocumented fields move.** `net_worth` and `od_data` work but are not in the OpenAPI schema; model them optional, decode with unknown keys ignored.
- **Accounts OpenDota has not seen** return 404 on the profile; accounts with the public-match setting off return empty lists. Both are user-facing outcomes with different advice.
- **High-MMR matches may be missing** from the feed after March 2025, per OpenDota's own comments; a tracked top-rank account can look inactive.
- **Docs disagree with code.** The OpenAPI text says "monthly", the config comment says "per day". The tracker should read the live headers, not hard-code the figure.

## 6. Recommendation for this repo

**Provider shape.** One `OpenDotaDotaProvider` behind a game-agnostic stats-provider interface that expresses what Dota 2 needs and nothing OpenDota-specific:

- `resolveAccount(input): Result<AccountRef>` for the key-free forms (value classes `AccountId(Long)` and `SteamId64(Long)` with the base constant `76561197960265728`; a number below `2^32` is an account id, a number at or above the base is a Steam64, anything between is rejected), returning a separate "needs vanity lookup" failure for `/id/<name>`. Vanity resolution is an optional capability (a separate small interface) present only when a Steam key is configured, so the capability set rather than a nullable method tells callers what the provider can do.
- `profile(id)`, `recentMatches(id)` (newest first, stable `match_id` as the cursor), `matchDetail(id)`, and an optional `ParseRequester` capability (`requestParse`, `parseStatus`) that costs 10 budget units. Lookups that can miss (unknown account, unknown match, private history) are `Result` failures with distinct types, never nullable returns.
- Match models make parsed state explicit: a sealed `MatchDetail` with an unparsed form and a parsed form, or a `parsed: Boolean` plus nullable lane group; lane, role, roaming, efficiency and item timings exist only on the parsed form. Wire types are `internal @Serializable` with unknown keys ignored, mapped to public domain types; do not expose the wire shape.
- Constants load through a cached, refreshable component (daily refresh, `Hero #N` fallback for unknown ids) and are trimmed to the modelled fields on decode. Do not retain `abilities.json` whole; keep only talent names for heroes that appear.

**Budget model.** Use the in-house limiter with two lanes, `interactive` (commands) and `tracker`, sharing one per-provider budget. Reserve a fixed share for interactive calls (the examples below use 500 calls a day); the tracker spends the rest and stretches its intervals, not drops accounts, when demand exceeds that.

Assumptions, labelled as such: 3 matches per tracked account per day (a judgment; a heavy player plays more, a casual one fewer), 20% safety margin below the published limit, the keyless day limit of 3,000 and the keyed minute limit of 300 as read from the source defaults.

*Per-account cost.* Polling an account every `T` seconds costs `86400 / T` calls a day; each new match adds one detail call (shared when two tracked accounts were in the same match, and fanned out to every subscription that follows either account). Subscriptions are per guild, polls are per distinct account, so many guilds following one account cost one poll.

*Keyless, uniform interval* (tracker budget 1,900 calls a day = 3,000 x 0.8 - 500):

| Interval T | Calls per account per day (incl. 3 detail calls) | Accounts that fit |
|---|---|---|
| 5 min | 291 | 6 |
| 15 min | 99 | 19 |
| 30 min | 51 | 37 |
| 60 min | 27 | 70 |

The per-minute limit (60) is not binding at these sizes (at a 5-minute interval, 240 accounts would fit by the minute limit alone).

*Prioritised by recent activity.* Tiers by time since the account's last match ended: hot (under 2 hours) every 5 minutes, recent (under 24 hours) every 30 minutes, dormant every 3 hours; with a population mix of 10% hot, 30% recent, 60% dormant the average is `0.10 x 288 + 0.30 x 48 + 0.60 x 8 = 48` polls a day plus 3 detail calls, 51 a day per account. That is the same cost as a uniform 30-minute interval (37 keyless accounts) but active players are seen within about 5 minutes. A floor of about 2 minutes is the shortest interval worth using, because OpenDota's own intake cadence and Valve's publication delay dominate below that. When the account's last match is still in progress (its `start_time + duration` is in the future or just past), poll sooner.

*Keyed.* No daily cap, so the limits are the minute rate (300 as default, 240 with margin) and money. Cost per tracked account per month at `$0.0001` per call: uniform 2 min $2.17, 5 min $0.87, 15 min $0.30, 30 min $0.15, 60 min $0.08; with the tiered mix $0.15. For 100, 1,000 and 10,000 accounts the tiered mix costs about $15, $153 and $1,530 a month and averages 3.5, 35 and 354 calls a minute, so the minute limit starts to bind a little under 8,000 accounts at that mix (one key per OpenDota account). The tracker's call budget is therefore a configured number of calls per day derived from what the operator will pay, with a hard stop.

*Parse requests.* Never automatic. A parse costs 10 units and takes polling calls on top (MangoByte-style 20-second polling for up to 2 minutes is 6 calls); with the detail refetch, one parse is about 17 calls against 2 for an unparsed post. Offer parsing only on an explicit user command ("show lane details"), reserve it for the interactive lane, and let auto-posts say lane data is unavailable unless OpenDota already parsed the match (`od_data.has_parsed` or non-null `lane`).

*Behaviours that follow.* On a 429, pause the whole provider until the next minute boundary (minute 429) or UTC midnight (daily 429), keep polling state intact, and resume without a burst. When `X-Rate-Limit-Remaining-Day` falls below the interactive reserve, stretch tracker intervals by the ratio of demand to what remains. Cache `matchDetail` by `match_id` for the life of a post fan-out and cache parsed matches for much longer than unparsed ones (an unparsed match can still change).

**Account links.** Accept the key-free forms by default. Make the Steam key optional configuration that enables `steamcommunity.com/id/<name>` only; call it only for a vanity the user typed, and record in the privacy policy which Steam data is stored and where (profile id and display name). Verify a link by fetching `players/{id}`: a 404 gets the "OpenDota has not seen this account" message, an empty `recentMatches` gets the "enable Expose Public Match Data" message. Links stay global per Discord user; the tracker subscribes by guild.

**Patch notes.** Use the Steam news endpoint as a JSON source behind a small `PatchNoteSource` port (item id `gid`, title, url, date, contents), poll with `count` small and a long interval (hourly is ample), de-duplicate by `gid` per subscription cursor, post title, link and a trimmed excerpt, and filter by feed name or tag only after a live check shows which one marks Dota patches. Offer `dotaconstants` `patchnotes.json` as an optional enrichment that is not required to post. No RSS parser in `bottools-stats`.

**Attribution.** No attribution requirement was found in OpenDota's code or the sources readable here (Gap 3), and the convention in the leading bot is a link to `opendota.com/matches/{id}`. Put "Data: OpenDota" with that link in the embed footer text or description, which also gives users a path to a full parse view; keep the existing "Automated message" / "Requested by" footer content in the description area rather than losing it.

**Rejected.** The obvious option of keeping per-subscription polling (as a per-guild loop would do) is rejected: it multiplies calls by the number of guilds following the same account and is the cost model that does not scale. Resolving vanity names by default is rejected: it needs a secret key, a privacy-policy disclosure and a terms clause that limits retrieval to the user's request. Auto-parsing every posted match is rejected on cost. STRATZ as a second provider is rejected for this release: unverifiable terms and no need.
