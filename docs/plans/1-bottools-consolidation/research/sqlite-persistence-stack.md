## 1. Question

Which access layer, migration mechanism, connection model and coroutine integration should `bottools-data-sqlite` use to implement the storage ports on SQLite, and what shape must the ports in `bottools-core` take so that any of them can be implemented?

Requirements the answer meets:

- Ports live in `bottools-core` with no database dependency. They are `suspend` and return `Result`. Keys are 64-bit snowflake value classes. An in-memory implementation exists for tests and development.
- Stored: account links `(user, game) -> account` (global per user); subscriptions of every kind (match posts for a linked account, game news, RSS and Atom feeds), each per guild channel, in one shared store where every row carries its own cursor and health; typed guild settings (prefix, default role, welcome message, matches channel, patch-notes channel, plugin toggles); job state; private key-value storage per plugin (reaction-role mappings now, poker chip balances later).
- Everything stored about one Discord user can be erased on request.
- Backups are short-lived: the bot deletes backups older than 14 days, the retention window its privacy policy states, and no erasure log is kept.
- Schema changes migrate existing database files. A one-off legacy importer writes through the same ports. Level-3 tests run against temporary SQLite files.
- JDK 21, Kotlin 2.2.x, Apache-2.0 library, every dependency on Maven Central and current. Single-host SQLite (no multi-process sharding).

Today's storage, by symbol: `bottools.dataprocessing.KotGDP` (an `XMLReader` by delegation to one shared `BaseXMLReader`, switched between files with `setDocument`, and `BaseXMLReader.write` rewrites a whole file through a `Transformer`); keys are names, not snowflakes. GKB2's `dataprocessing.Database` is a port-like interface whose methods return `Result<Unit>` but whose accessors are non-suspend, navigate with `div`/`minus` and key by `Guild`/`Member` objects.

## 2. Bottom line

- **Use plain JDBC on `org.xerial:sqlite-jdbc` (3.51.3.0 floor, 3.53.4.0 pin) behind a thin internal Kotlin layer. Do not use Exposed, SQLDelight, jOOQ, an R2DBC stack, or a connection pool library.** The workload is about six tables and a few dozen fixed statements. The hard parts are SQLite-specific (one writer, transaction mode, pragmas, error mapping, dispatchers, migrations) and no access layer supplies them. Exposed's JDBC `suspendTransaction` does not move work off the calling thread, Exposed has no R2DBC SQLite dialect, and its `1.3.0`+ line pulls Kotlin stdlib 2.3.20, coroutines 1.11.0, `kotlin-reflect` and `kotlinx-datetime` onto every consumer of a library built on Kotlin 2.2.x.
- **Connections: one long-lived writer connection plus a small fixed set of read-only connections, all owned by the store, file in WAL mode.** Writer: `transaction_mode=IMMEDIATE`, confined to `Dispatchers.IO.limitedParallelism(1)`. Readers: read-only, on `Dispatchers.IO.limitedParallelism(n)`, opened after the writer has created the WAL files, with short read transactions only. Every connection sets `busy_timeout` and `foreign_keys=ON` and, for the writer, `journal_mode=WAL` and `synchronous=NORMAL` (a `Durability` policy parameter allows `FULL`). Each port call is one self-contained transaction; no transaction is ever held across a suspension point.
- **Migrations: hand-written, forward-only, ordered migrations keyed by `PRAGMA user_version`, each applied in one `BEGIN IMMEDIATE` transaction that also sets the new version.** Refuse to open a file whose version is newer than the library knows. Take a `VACUUM INTO` copy before migrating a non-empty file. Migrations that rebuild a table switch `foreign_keys` off before the transaction begins, because the pragma is a no-op inside one. Flyway (Apache-2.0, SQLite in core) works but adds a history table, Jackson annotations and a `ServiceLoader` plugin registry that needs merged service files in fat jars; Liquibase 5.x is under the Functional Source License and is excluded; Exposed's migration tooling generates SQL that must be reviewed by hand on SQLite.
- **Port shape: every method is a complete unit of work (no transaction lambda in a port); read-modify-write is expressed as named atomic operations or a pure `update` lambda run inside the write section; misses are `Result.failure(NotFound)`; `eraseUser`/`eraseGuild` are single atomic operations; every table that can hold user data carries a `user_id` column with an index, and plugin key-value rows declare an owner scope so erasure is a predicate, not a scan. Subscriptions of every kind live in one `subscription` table keyed by `(guild, channel, kind, target)`, each row holding its own cursor and health columns.**
- **The SQLite version floor is documented and met.** SQLite's documentation names a WAL-reset corruption bug present in all versions from 3.7.0 (2010-07-21) through 3.51.2 (2026-01-09), fixed in 3.51.3 (2026-03-13), with backports to 3.44.6 and 3.50.7 [C20]. `sqlite-jdbc 3.53.4.0` builds from SQLite 3.53.4 [C28], and the 3.53.4 release notes list the fix among the changes since 3.53.0 [C30], so the pin is above the fix; the first `sqlite-jdbc` release that carries it is `3.51.3.0` [C29]. The bug needs two connections writing or checkpointing at the same instant [C20]; the design has one writing connection. Check `sqlite_version()` at open and log a warning below 3.51.3.
- **Backups: `VACUUM INTO` a timestamped file, pruned after a configurable retention that defaults to 14 days; no erasure log.** `VACUUM INTO` writes a consistent snapshot and purges deleted content, so a backup holds no forensic traces of earlier deletions [C35]. A restored backup can contain users erased after it was taken, for at most the retention window; the privacy policy states that window.

## 3. Findings

Tiers: **Consensus** = official documentation, source or several independent sources. **Practice** = what mature libraries visibly do. **Opinion** = one source's view. **Measured** = read at the pinned version. **Inference** = my reasoning from cited facts, not run. `[C#]` refers to section 7.

### F1. Access layer

**Exposed (Measured, 1.6.0).**

- `1.0.0` is final (Maven Central, 2026-01-22) and the line is active: `1.6.0` on 2026-10-16 [C1]. `1.0.0` was a restructuring for R2DBC: every package gained a `v1` prefix and JDBC-specific classes moved out of core ("`org.jetbrains.exposed.sql.Database` → `org.jetbrains.exposed.v1.jdbc.Database`") [C6]. The 1.0 cycle also carried renames in transaction management (`Transaction.id` → `txId`, JDBC transaction refactoring) [C6]. A project starting now writes `v1` imports from day one, so the 0.x-to-1.0 migration cost does not apply here.
- **Kotlin and classpath.** `1.0.0` to `1.2.0` depend on Kotlin stdlib/reflect `2.2.20` and coroutines `1.10.2`; `1.5.1` and `1.6.0` depend on `2.3.20` and `1.11.0` (plus `kotlinx-datetime-jvm`) [C2]. The README states the requirement as "Kotlin version 2.2.+" [C3]. The build pins Kotlin 2.2.x and jda-ktx 0.14.2 requires coroutines 1.10.2, so the current Exposed line is one minor ahead on both. Whether a 2.2.x compiler consumes the 2.3.20-compiled artifacts without flags was not tested (Gaps).
- **Coroutines.** The JDBC module's `suspendTransaction` is documented as "available to call suspend functions alongside blocking database operations" [C4]; its source switches no dispatcher (the only `withContext` is `NonCancellable` cleanup) [C4]. It propagates transaction context into coroutines; it does not make JDBC non-blocking. The non-blocking route is `exposed-r2dbc`, whose dialect metadata files cover H2, MariaDB, MySQL, Oracle, PostgreSQL and SQL Server and have no SQLite entry [C5]; the documentation itself says "R2DBC is still evolving, and not all databases or features are supported equally compared to JDBC" [C5]. So on SQLite, Exposed would still need `withContext(writerDispatcher)` around every transaction.
- **DSL versus DAO (Consensus on facts, Inference on fit).** `exposed-dao` is a separate, JDBC-only module [C3]. The DAO's mutable entities do not fit ports that take value-class ids and return immutable data; only the DSL would be used.
- **Fit.** Exposed would give typed `Table` objects and `upsert`. Against that: reflection and datetime on the runtime classpath, a transaction manager built around `ThreadLocal` that sits under a `limitedParallelism(1)` dispatcher (which guarantees sequential execution but "no guarantee that the underlying system thread will always be the same" [C12]), and no control over `BEGIN IMMEDIATE` except through driver properties. None is disqualifying; none is needed at this scale.

**Plain JDBC with a thin layer (Measured/Practice).**

- `sqlite-jdbc` `3.53.4.0` is Apache-2.0, has one runtime dependency (`slf4j-api` 1.7.36), ships natives for Windows, macOS, Linux (libc and musl), FreeBSD and Android in one 12 MB default jar, plus a `without-natives` classifier since `3.53.0.0` [C7]. It is compiled `-DSQLITE_THREADSAFE=1` (serialized) [C8]. Its `SQLiteException.getResultCode()` exposes a typed `SQLiteErrorCode` (`SQLITE_BUSY`, `SQLITE_CONSTRAINT`, `SQLITE_FULL`, `SQLITE_READONLY`...) for error mapping [C8].
- BotCommands `v3.4.0`, a JDA framework with a database layer, did exactly this: its own `Database` interface (`suspend fun fetchConnection(readOnly: Boolean = false): Connection`), `compileOnly` HikariCP marked "Optional", Flyway only in its test and sample setup [C13]. It targets PostgreSQL and H2, not SQLite.

**SQLDelight 2.4.1 (Measured).**

- Strength: SQL is checked at build time and `verifyMigrations` verifies `.sqm` migration files against the current schema. The driver depends on `sqlite-jdbc` `3.53.4.0` and Kotlin stdlib `2.3.10` [C9].
- Gaps found in the JVM driver. `JdbcSqliteDriver(url, properties)` has no schema or migration parameter in 2.0.2, 2.2.1, 2.3.2 or 2.4.1 sources, while the 2.4.1 documentation still shows `JdbcSqliteDriver(url, Properties(), Database.Schema)` and says it "uses `PRAGMA user_version`" [C9]: the documentation and the code disagree, so the version bookkeeping would be hand-written anyway. For file databases it keeps one connection per thread (`ThreadLocal`), closes it after each transaction, and starts transactions with `BEGIN TRANSACTION` (deferred) [C9], which is the pattern that provokes `SQLITE_BUSY` on read-to-write upgrade [C10][C15]. Its JDBC mode is blocking; coroutine support is a separate layer.
- It also needs the Gradle plugin and code generation in the convention plugins, and generated declarations land in a library with `explicitApi()`. Whether generated classes can be made `internal` was not established (Gaps). Credible runner-up if the schema grows to dozens of tables.

**jOOQ 3.21.9 (Measured).** The POM is Apache-2.0 and the `SQLITE` dialect is not flagged commercial in `SQLDialect` [C11], so the open-source build covers it. It is a 30-dialect dynamic-SQL builder with a code generator needing either a live database or DDL files at build time. Overkill for fixed statements. Rejected.

### F2. Connections, WAL, busy handling, durability

- **WAL gives concurrent readers beside one writer (Consensus, SQLite documentation).** "WAL provides more concurrency as readers do not block writers and a writer does not block readers", and "since there is only one WAL file, there can only be one writer at a time" [C14]. `lang_transaction.html` states the same for the engine: multiple simultaneous read transactions "but only one simultaneous write transaction" [C15]. The source comments in `wal.c` agree [C14].
- **The upgrade trap (Consensus).** A write statement inside a read transaction upgrades it "if possible"; if another connection has already modified the database, "upgrading to a write transaction is not possible and the write statement will fail with SQLITE_BUSY" [C15]. In WAL mode this surfaces as `SQLITE_BUSY_SNAPSHOT`, raised when a connection promotes a read transaction after another connection wrote and "thus invalidated prior reads" [C31]. The busy handler does not rescue it: "If SQLite determines that invoking the busy handler could result in a deadlock, it will go ahead and return SQLITE_BUSY to the application instead of invoking the busy handler" [C16]. sqlite-jdbc documents the same hazard ("auto-upgrading" read-only transactions) [C10]. Its default `begin;` is deferred; `transaction_mode=IMMEDIATE` makes it send `begin immediate;` [C17], which "causes the database connection to start a new write immediately" and fails with `SQLITE_BUSY` only if another write transaction is already active [C15]. Therefore the writer connection must open write transactions as `IMMEDIATE`, and reads must never be promoted to writes.
- **busy_timeout (Consensus).** `sqlite3_busy_timeout` sets a handler that "will sleep multiple times until at least "ms" milliseconds of sleeping have accumulated" and then makes `sqlite3_step()` return `SQLITE_BUSY`; a value of zero or less turns busy handling off; there is one busy handler per connection and setting the timeout replaces any other handler [C16]. sqlite-jdbc applies a default of `3000` ms [C17]; set it explicitly (for example 5000 ms). With one in-process writer, contention can only come from another process (a CLI inspecting the file, a backup) or from recovery and last-close cleanup: the documentation lists the cases where a WAL-mode query can still return `SQLITE_BUSY`, among them a recovery run by the first connection after a crash, and the exclusive lock the last closing connection holds while it cleans up the WAL and shared-memory files [C37].
- **Read-only connections (Measured, Consensus).** sqlite-jdbc refuses `Connection.setReadOnly` after the connection is established unless explicit-read-only mode is on ("Cannot change read-only flag after establishing a connection. Use SQLiteConfig#setReadOnly...") [C18]. A pool that toggles read-only (HikariCP's `readOnly`) therefore cannot split readers from writers; the mode is chosen when the connection is opened through `SQLiteConfig`. SQLite's documentation adds a WAL-specific condition: since 3.22.0 a read-only connection can open a WAL-mode database "if the -shm and -wal files already exist or those files can be created or the database is immutable" [C32]. The writer therefore opens first (creating the WAL files), the data directory must be writable, and readers are opened after it. Journal mode is persistent in the file and "will be set on all connections to the same database file if it is set on any one connection" [C32], so only the writer issues `journal_mode=WAL`; it checks that the pragma returned `wal` (any other value means the conversion did not happen, for example on an unsuitable filesystem [C32]) and fails the open otherwise.
- **synchronous (Consensus).** SQLite's documentation: "WAL mode is safe from corruption with synchronous=NORMAL... WAL mode is always consistent with synchronous=NORMAL, but WAL mode does lose durability. A transaction committed in WAL mode with synchronous=NORMAL might roll back following a power loss or system crash. Transactions are durable across application crashes regardless of the synchronous setting or journal mode." `FULL` "is atomic, consistent, isolated, and durable (ACID) in WAL mode" and `EXTRA` is no different from `FULL` in WAL mode [C19]. Under `NORMAL` the only syncs happen in the checkpoint [C32][C19]. For a bot's settings and links this is acceptable; poker balances later may want `FULL`, so durability is a parameter, not a constant.
- **WAL needs a local filesystem (Consensus).** "All processes using a database must be on the same host computer; WAL does not work over a network filesystem" because the wal-index is shared memory [C14]. The database file must live on local disk of the one host.
- **Checkpointing (Consensus).** By default a checkpoint runs automatically when a commit leaves the WAL at 1000 pages or more, and when the last connection closes; automatic checkpoints are `PASSIVE` [C32][C36]. "A long-running read transaction can prevent a checkpointer from making progress" and a database that always has an overlapping reader grows its WAL without bound [C32]. Reads on the reader connections therefore stay short, and no cursor or result set is held open across a suspension point.
- **A version floor matters (Consensus, SQLite documentation).** The WAL-reset bug: "The bug is likely present in all version of SQLite from 3.7.0 (2010-07-21) through 3.51.2 (2026-01-09). It is fixed in version 3.51.3 (2026-03-13) and later. Backports of the fix are available for some earlier releases: 3.44.6 and 3.50.7." It "only affects databases in WAL mode when there are two or more database connections open on the same file, in separate threads or processes, and when those two connections attempt to write or checkpoint at the same instant." SQLite calls it rare and "not an emergency", but a reproducer without special test hooks was published on 2026-08-24, and "application developers should upgrade to a version of SQLite that fixes the problem" [C20]. SQLite's release log lists the fix under 3.51.3 [C29] and again among the changes of the 3.53 line [C30]. `sqlite-jdbc` follows SQLite's version [C7] and builds from the `version` in its `VERSION` file, `3.53.4` for the `3.53.4.0` tag [C28]; the first `sqlite-jdbc` tag whose `VERSION` is `3.51.3` is `3.51.3.0`, and no `3.52.0.0` release exists because SQLite withdrew 3.52.0 [C29]. The pin is therefore above the fix, with `3.51.3.0` as the lowest acceptable floor. In this design only the writer connection writes or checkpoints; the readers are read-only (Inference: a read-only connection cannot write, so the two-writers precondition needs a second process, such as an operator running the `sqlite3` shell against the live file). Keep the floor explicit and test it.
- **Pool libraries.** HikariCP 7.1.0 (Apache-2.0, Java 11+) lists SQLite via `org.sqlite.SQLiteDataSource` [C21], but its model (N interchangeable connections, validation, max lifetime, read-only toggling) targets networked databases. For SQLite it would need two pools (writer size 1, readers size n) and per-connection properties, which is what a 40-line store-owned checkout queue does without another dependency.

### F3. Coroutine integration

- **Pattern (Practice, Consensus on the dispatcher contract).** Blocking JDBC behind `withContext` on an injected `Dispatchers.IO.limitedParallelism(n)` view. kotlinx.coroutines documents `limitedParallelism(1)` as the confinement pattern: "the implementation guarantees that tasks are executed sequentially and that a happens-before relation is established between them", with no guarantee of the same thread [C12]. `Dispatchers.IO` views are elastic, so the writer and reader views do not starve each other [C12; idiomatic-kotlin-api-shape.md C14b]. This is the same shape the API-shape research settled for blocking ports.
- **Cancellation.** A blocking JDBC call is not cancellable. The port returns to the caller on cancellation at the next suspension point, but the statement completes; because each call is one transaction, the effect is all-or-nothing and the connection returns to its pool in `finally`. Library code uses the internal `suspendCatching` (rethrows `CancellationException`) rather than `runCatching` around the `withContext` (idiomatic-kotlin-api-shape.md F7).
- **No suspension inside a write.** The writer dispatcher is single-lane. A port that opened a transaction and then awaited another port call would deadlock behind its own lane. Hence no transaction lambda in the port surface (see section 6).
- **Exposed's and SQLDelight's coroutine layers do not change this.** Exposed's JDBC `suspendTransaction` [C4] and SQLDelight's JDBC driver [C9] both leave the work on the caller's thread.

### F4. Migrations

- **`PRAGMA user_version` (Consensus, SQLite documentation).** "The user_version pragma will get or set the value of the user-version integer at offset 60 in the database header... SQLite makes no use of the user-version itself" [C22]; the source stores it as a 32-bit signed integer in the header and compiles the pragma to `OP_Transaction` then `OP_SetCookie`, i.e. it runs inside the open transaction [C22]. A companion `application_id` pragma holds a 32-bit application identifier at offset 68 that identifies a file's owner, which lets the store reject foreign files [C22].
- **DDL runs inside a transaction (Consensus).** `lang_transaction.html` lists `CREATE` and `DROP` among the "write statements" that start a write transaction [C15], and the ALTER TABLE documentation's procedure for arbitrary schema changes is: disable foreign keys, "Start a transaction", create `new_X`, copy, drop `X`, rename `new_X` to `X`, rebuild indexes, `PRAGMA foreign_key_check`, "Commit the transaction" [C34]. Setting `user_version` in the same `BEGIN IMMEDIATE` as the migration's DDL therefore makes "migrated" and "version bumped" one atomic step (Inference from the two documented facts).
- **The foreign-key pragma cannot be toggled inside the migration transaction (Consensus).** "This pragma is a no-op within a transaction; foreign key constraint enforcement may only be enabled or disabled when there is no pending BEGIN or SAVEPOINT" [C33]. The table-rebuild procedure needs enforcement off, so the runner sets `foreign_keys=OFF` before `BEGIN IMMEDIATE` for a migration that rebuilds a table, runs `foreign_key_check` before `COMMIT`, and restores `ON` afterwards. Enforcement is also off by default (since 3.6.19), so every connection must set it explicitly [C33].
- **SQLite alter limits (Consensus).** The directly supported schema changes are rename table, rename column, add column and drop column; `ADD COLUMN` cannot add a `PRIMARY KEY` or `UNIQUE` column and a `NOT NULL` column needs a non-null default [C34]. Everything else is the create-copy-drop-rename sequence above. This is true of every runner below; it is why hand-written SQL stays necessary.
- **Flyway 13.10.3 (Measured).** Apache-2.0 per its POM; SQLite is listed among supported databases and `SQLiteDatabaseType` ships inside `flyway-core` [C23]. Costs for an embedded library database: a `flyway_schema_history` table of its own, `jackson-annotations` as a compile dependency, and plugin registration through `META-INF/services/org.flywaydb.core.extensibility.Plugin` [C23] (fat jars then need merged service files; see `bot-runtime-design.md` F3 on `ServiceLoader`). Redgate's other editions are separate commercial products ("these editions are not part of the Flyway open source project") [C23]. The benefit is checksum validation of applied scripts, which is cheap to reproduce in a test.
- **Liquibase 5.0.4 (Measured).** Its POM declares `FSL-1.1-ALv2` ("Functional Source License, Version 1.1, ALv2 Future License") [C24]. A source-available licence on a dependency of an Apache-2.0 library is a licence-compatibility problem for consumers; excluded without further evaluation.
- **Exposed migration tooling (Measured, 1.6.0).** `MigrationUtils.statementsRequiredForDatabaseMigration` and `generateMigrationScript` compare table definitions to a live schema and emit SQL; the documentation states "Exposed does not apply generated migration scripts automatically", that SQLite's limited `ALTER TABLE` "may lead to partial or failed migrations if not reviewed", and that the SQL it emits for SQLite can fail at runtime on `ADD COLUMN` rules [C25]. A Gradle plugin (1.3.0) and Maven plugin (1.4.0) generate scripts at build time [C25]. Useful as a diff aid, not a runner.
- **SQLDelight.** `.sqm` files and `verifyMigrations` are the strongest migration tooling of the four, but only at build time; the JVM driver does not run them (F1).

### F5. Erasure, backups and the data model

- **Erasure is a schema property.** Red-DiscordBot requires every cog to override `red_delete_data_for_user` (`bot-runtime-design.md` F3); the plugin API here already requires an erasure function. For store-owned data the cheapest guarantee is structural: every table that can hold user data has a `user_id` column that is part of a key or index, so `DELETE ... WHERE user_id = ?` is one statement per table inside one transaction.
- **Plugin key-value rows need an owner scope.** A free-form `(plugin, key) -> value` table cannot be erased per user without scanning values. Give rows optional `guild_id` and `user_id` owner columns (stored as `0` when absent so they can sit in the primary key, because snowflakes are never 0). Reaction-role mappings are guild-scoped rows with no user; poker balances are user-scoped rows. Erasing a user deletes `user_id = ?` rows; leaving a guild deletes `guild_id = ?` rows.
- **Subscriptions share one table (Inference).** Match posts, game news and feed subscriptions are all "post new items from a source to a guild channel": the key is `(guild_id, channel_id, kind, target)`, where `kind` is an open string key (`dota2.matches`, `news.steam`, `feed.atom`) so a plugin adds a kind without a migration, and `target` is the source identifier (an account, an app id, a feed URL). The row carries its own cursor and health (`cursor`, `last_polled_at`, `last_success_at`, `consecutive_failures`, `last_error`), so the poller reads due rows by `(kind, last_polled_at)` and a failing feed never blocks another. `user_id` is the user the subscription is about (the linked account's owner for match posts) and `0` for subscriptions that are not about a user. Erasure deletes rows with `user_id = ?`. If a creator is also recorded, that column is user data too and erasure clears it to `0` rather than deleting a guild's feed (Inference: a guild's feed is the guild's data).
- **Deleted bytes persist for a while (Consensus).** "The off setting for secure_delete improves performance by reducing the number of CPU cycles and the amount of disk I/O. Applications that wish to avoid leaving forensic traces after content is deleted or updated should enable the secure_delete pragma prior to performing the delete or update, or else run VACUUM after the delete or update." The `fast` setting purges b-tree pages but leaves traces on freelist pages [C26]. The writer enables `secure_delete` (sqlite-jdbc exposes it as a pragma [C26]) and the erasure operation is followed by a `wal_checkpoint(TRUNCATE)`, which copies the WAL into the database and truncates the WAL file to zero bytes [C36] (Inference: this removes old page images that mention the user from the `-wal` file; it blocks concurrent writers while it runs, which is acceptable for a rare operation).
- **Backups.** The pre-migration copy and any scheduled copy use `VACUUM INTO`: it "is an alternative to the backup API for generating backup copies of a live database", the result "is a consistent snapshot of the original database", "all deleted content is purged from the backup, leaving behind no forensic traces", it is not a write operation of the source (unlike plain `VACUUM`), the target must not exist or must be empty, and it fails inside an open transaction [C35]. The online backup API is the alternative; it "uses fewer CPU cycles and can be executed incrementally" [C35], which does not matter at this size. Backups are deleted after a retention window (default 14 days, the window the privacy policy states). No erasure log is kept, so restoring a backup can resurrect a user who was erased after it was taken; the exposure is bounded by the window and is stated in the policy. The store offers `backup(directory)` and `pruneBackups(directory, retention)`; scheduling is the host's concern.
- **Snowflake storage.** Discord snowflakes are unsigned 64-bit; current values fit a signed `Long`, so the value class's `Long` is stored as `INTEGER` without conversion. Printing uses the unsigned form (`idiomatic-kotlin-api-shape.md` F4).
- **Table options (Consensus).** `STRICT` tables exist from 3.37.0 (2021-11-27); a database containing one can only be read and written by 3.37.0 or later, which matters to an operator inspecting the file with an old `sqlite3` shell [C27]. Upsert exists from 3.24.0 (2018-06-04) and `DO UPDATE` without a conflict target from 3.35.0 [C27]. Both are far below the 3.51.3 floor. `WITHOUT ROWID` fits composite natural keys. sqlite-jdbc exposes `foreign_keys`, `journal_mode`, `synchronous`, `busy_timeout`, `wal_autocheckpoint` and `transaction_mode` through `SQLiteConfig` [C17].

## 5. Pitfalls and regrets

1. **Deferred transactions on a writer.** `begin;` then a read then a write returns `SQLITE_BUSY` (`SQLITE_BUSY_SNAPSHOT` in WAL mode) immediately even with a busy timeout, because the read-to-write upgrade cannot wait [C15][C16][C31][C10]. Use `transaction_mode=IMMEDIATE` on the writer.
2. **Treating a pool as the concurrency model.** More than one writing connection only produces lock waits; WAL does not add writers [C14][C15]. A reader pool is useful, a writer pool is not. Two writing connections are also the precondition of the WAL-reset bug on unfixed versions [C20].
3. **A transaction across a suspension point on a single-lane dispatcher.** The lane is held while the coroutine awaits something that needs the same lane. Keep ports transaction-free and operation-shaped.
4. **`setReadOnly` through a generic pool.** sqlite-jdbc throws unless the connection was opened read-only or explicit-read-only mode is on [C18].
5. **`:memory:` for multi-connection tests.** Each plain in-memory connection is its own database, which is why SQLDelight's driver holds a single static connection for it [C9]. Level-3 tests use temporary files, as required; the in-memory port implementation is a separate pure-Kotlin class and never an SQLite `:memory:` database.
6. **Docs and code disagree in SQLDelight's JVM driver (schema and migration constructor).** Read the code at the tag before depending on documented behaviour [C9].
7. **Exposed version skew.** Upgrading from the `1.2.x` line to `1.3.0`+ changes the required Kotlin and coroutines versions [C2]; a library that publishes a dependency on it forces that choice on consumers.
8. **Network filesystems and WAL.** A bot whose data directory sits on NFS or a similar share breaks the shared-memory assumption [C14]. Document local disk as a requirement.
9. **Silent version drift.** Opening a database written by a newer library version and "migrating" nothing is data corruption by omission. Refuse files whose `user_version` is greater than the latest known migration.
10. **Rewriting an applied migration.** Once released, a migration is immutable; fixes are new migrations. A checksum test over the migration list catches edits.
11. **Backups outliving an erasure.** A restore resurrects users erased after the backup was taken. With no erasure log the guarantee is the retention window: backups older than 14 days are deleted, `VACUUM INTO` copies carry no deleted content [C35], and the privacy policy states the window. A backup directory that is never pruned silently breaks that promise, so pruning runs at `open` and on a schedule, and a test asserts it.
12. **A Level-2-only story.** Mocking JDBC proves nothing about SQLite behaviour; the contract tests must run against real temporary files.
13. **Toggling `foreign_keys` inside the migration transaction.** The pragma is a no-op there, so a table-rebuild migration that "disables" it inside `BEGIN` runs with enforcement still on and the `DROP TABLE` can cascade [C33][C34]. Switch it off before `BEGIN IMMEDIATE`.
14. **Long read transactions starve checkpoints.** A reader that holds a result set across a suspension point keeps the WAL from being reset and the file grows [C32]. Reads are page-sized and fully materialised before the connection returns to the queue.
15. **Old `sqlite3` shells and `STRICT`.** An operator opening the file with a shell older than 3.37.0 cannot read it [C27]; say so in the README's operations note.

## 6. Recommendation for this repo

**Stack.** In `bottools-data-sqlite`: `org.xerial:sqlite-jdbc` as the only runtime dependency beyond `bottools-core` and `kotlinx-coroutines-core`; library code logs through slf4j only. No Exposed, SQLDelight, jOOQ, Flyway, Liquibase or HikariCP. Reasoning: the surface is small and fixed; SQLite's difficulties live below any access layer; the dependency footprint stays one jar; and JDA's closest Kotlin framework made the same choice. Rejecting Exposed is a close call on convenience, not on quality: choose Exposed's DSL (pinned at the `1.2.x` line to match the toolchain, or `1.6.x` once the Kotlin pin moves) only if the table count outgrows hand-written statements; SQLDelight is the better choice at that scale for its build-time SQL checking.

**Layout (all `internal` to the module):**

- `SqliteStorage` implements the core ports and is created by `SqliteStorage.open(path, config): Result<SqliteStorage>` (open, set pragmas, check `sqlite_version()`, migrate, return). `close()` drains and closes all connections after the runtime's jobs and handlers have stopped (`bot-runtime-design.md` stop order step 7).
- `Connections`: one writer `Connection` and `readers` read-only connections (default 2, configurable), checked out through a bounded queue. The dispatchers are injected as `CoroutineDispatcher`s with the defaults `Dispatchers.IO.limitedParallelism(1, "bottools-sqlite-writer")` and `Dispatchers.IO.limitedParallelism(readers, "bottools-sqlite-readers")`.
- Per-connection setup through `SQLiteConfig`: `busy_timeout` (5000 ms), `foreign_keys=ON`; writer only: `journal_mode=WAL` (result checked), `synchronous` from a `Durability` policy (`NORMAL` default, `FULL` available), `transaction_mode=IMMEDIATE`, `secure_delete=ON`; readers: opened read-only, after the writer.
- Statement helpers: `inline fun <T> Connection.write(block: (Connection) -> T): T` that begins, commits, rolls back, and maps `SQLiteException` result codes to the typed storage failures; `Connection.read`. SQL text lives in one internal `Sql` object or `.sql` resources listed explicitly (no classpath scanning).
- Schema: `STRICT` tables with natural composite keys: `account_link(user_id, game, account, ...)`; `subscription(guild_id, channel_id, kind, target, user_id, cursor, last_polled_at, last_success_at, consecutive_failures, last_error, ...)` keyed by `(guild_id, channel_id, kind, target)` with indexes on `user_id` and on `(kind, last_polled_at)`, shared by match posts, game news and feeds; `guild_setting(guild_id, key, value)` holding codec-encoded text so adding a setting or a plugin toggle needs no migration; `job_state(job_key, next_due_at, last_started_at, last_succeeded_at, consecutive_failures, cursor)` for jobs that are not subscriptions; `plugin_kv(plugin_id, guild_id, user_id, key, value)` with owner scope as in F5 and an index on `user_id`. Per-subscription cursors and health are columns of the subscription row, so they are erased with it. Timestamps are epoch-millisecond integers.
- Migrations: `internal val migrations: List<Migration>` with strictly increasing `toVersion` from 1, each a list of SQL statements (a Kotlin lambda is allowed for data fix-ups) and a flag for "rebuilds a table" that makes the runner switch `foreign_keys` off outside the transaction. `open` reads `user_version`; if greater than the last migration, fail with `SchemaTooNew`; if lower and the file is non-empty, take a `VACUUM INTO` backup first; apply each pending migration inside one `BEGIN IMMEDIATE` that also executes `PRAGMA user_version = n`. Also store a bottools `application_id` to reject foreign files.
- Backups: `SqliteStorage.backup(directory): Result<Path>` runs `VACUUM INTO` a new timestamped file named with the source `user_version`, on the writer lane (whether it may run on a read-only reader connection was not established, see Gaps); `pruneBackups(directory, retention = 14.days)` deletes files older than `retention` by last-modified time, called from `open` for the configured directory and available to a scheduled job. No erasure log table exists.
- Erasure: `eraseUser`/`eraseGuild` run in one write transaction and are followed by `PRAGMA wal_checkpoint(TRUNCATE)` outside it.
- Tests: a contract test class (abstract, per port) executed against the in-memory implementation and against `SqliteStorage` on a `@TempDir` file; a migration test that creates a database at every released `user_version` (kept as generated fixtures) and upgrades it to head with data preserved; a drift test that compares `sqlite_master` of a freshly created database with a fully migrated one; a concurrency test (parallel `put`s and reads) that expects no `SQLITE_BUSY` at the port boundary; an erasure test that seeds every table and every plugin scope for one user and asserts no row mentions that user afterwards; a backup test that checks a backup is a consistent snapshot and that `pruneBackups` removes files older than the window and keeps newer ones; a version test that asserts `sqlite_version()` is at least 3.51.3.

**Shape constraints for the ports in `bottools-core`** (these keep an in-memory and an SQLite implementation interchangeable):

1. Every port method is a complete unit of work and one transaction. Ports do not expose a transaction block, a connection, or a cursor. Multi-row atomic operations are named methods (`replaceLink`, `eraseUser`, `eraseGuild`, `claimDueJob`, `recordPoll`).
2. Read-modify-write is expressed as atomic operations (`putIfAbsent`, `compareAndSet`) or as `update(key, transform: (V?) -> V?)` where `transform` is a pure, non-suspending function documented to run inside the store's write section. Poker balance changes use it.
3. All parameters and results are value-class ids and immutable data; nothing from JDA, `java.sql` or Exposed appears. Returns are `Result<T>`; a lookup that can miss is `Result.failure(NotFound(...))` (stackless, open base `StorageException` shared with `BotToolsException`), a list query returns an empty list on success. Failure kinds the SQLite module maps: `NotFound`, `Conflict` (constraint), `Busy`/`Unavailable` (after timeout), `SchemaTooNew`, `Corrupt`, `Unexpected(cause)`.
4. Unbounded reads are paged (`subscriptionsDue(kind, now, after, limit)`), because a reader connection returns a full result set to one coroutine. A subscription is one port type for every kind: a `Subscription` value holds its key, `cursor` and a `Health` value (last polled, last success, consecutive failures, last error), and `recordPoll(key, cursor, outcome)` updates cursor and health atomically.
5. Erasure: `UserDataEraser.eraseUser(UserId): Result<ErasureReport>` and `eraseGuild(GuildId)` are single atomic operations over all store tables and all plugin key-value owner scopes; plugins that keep data elsewhere erase through their own hook (`bot-runtime-design.md` F3). The report holds per-table counts for the confirmation message. The port records nothing about the erasure beyond that report (no erasure log).
6. Settings are typed by a `Setting<T>(key, codec, default)` value in core; the port reads and writes encoded text, so storage never learns setting types.
7. The legacy importer uses idempotent upserts (`link`, `subscribe`, `set`) so a rerun is safe, and runs through the same writer lane; it needs no bulk API.
8. Ports are `fun interface`/interfaces with default implementations only where the default is real (the in-memory store). They are stable to call; implementing them is covered by the `@SubclassOptInRequired` convention (`idiomatic-kotlin-api-shape.md` F8) because the library will add port methods in feature releases.

## 8. Gaps

- **Hosts that refused or did not resolve:** `www.jetbrains.com` (Exposed's published documentation; read from the repository's `documentation-website` sources at tag 1.6.0 instead), `antithesis.com`, `theconsensus.dev`, `www.theregister.com`, `www.techzine.eu`, `mjtsai.com` (secondary WAL-reset reports, no longer relied on), `docs.liquibase.com` and `www.liquibase.com` (read only through search summaries), `www.jooq.org`, `flywaydb.org`, `developer.android.com` (Room's pool API could not be read in a usable form, so Room is not used as evidence), `ktor.io`. `sqlite.org` answers and is the source for all SQLite behaviour above.
- **Bundled SQLite version of the jar.** The version is read from sqlite-jdbc's `VERSION` file, `Makefile.common` and release notes at the tag, which state what the build compiles. The native library inside the published jar was not opened (nothing was run); the `sqlite_version()` check at open is the runtime confirmation.
- **Backport lines.** SQLite lists fixed backports 3.44.6 and 3.50.7 [C20]; which sqlite-jdbc releases, if any, bundle them was not checked, because the floor is taken from the 3.51 line.
- **`VACUUM INTO` on a read-only connection.** The documentation says `VACUUM INTO` is not a write operation of the source but does not say whether it may run on a connection opened read-only. The recommendation runs it on the writer lane until a Level-3 test establishes otherwise. Whether the `INTO` file name can be bound as a `?` parameter through sqlite-jdbc was not tested; a quoted literal with doubled quotes is the fallback.
- **Erasure and the WAL file.** SQLite's documentation describes `secure_delete` for database pages and `wal_checkpoint(TRUNCATE)` for the WAL file; that the combination removes an erased user's bytes from the `-wal` file is my inference, not a documented guarantee. A Level-3 test can byte-scan the database and `-wal` files for a seeded marker after erasure.
- **Kotlin 2.2.x consuming Exposed 1.6.0.** Not tested; the README says "Kotlin version 2.2.+" while the artifacts are built with 2.3.20. Relevant only if Exposed is chosen later.
- **SQLDelight.** Not tested: compatibility of its Gradle plugin with Kotlin 2.2.x and Gradle 8.10/9.x; whether generated declarations can be `internal`; the cause of the docs-versus-code mismatch for `JdbcSqliteDriver` (documentation might describe a different artifact). jOOQ's Java baseline was not read.
- **Performance.** No benchmark was run. The reader-count default (2) and `busy_timeout` (5000 ms) are reasoned defaults, not measured; at bot scale (events per second, small tables) they are not expected to matter.
- **Backup scheduling.** Database location, backup scheduling and shutdown checkpoints are host concerns outside the library; the library offers `backup`, `pruneBackups` (retention default 14 days) and a `close` that checkpoints. Whether the 14-day pruning also covers backups the host takes outside the library is the host's responsibility and must be stated in the privacy policy text.
- **Schema scope.** Tables for stats frameworks (match history, patch-note cursors beyond the single global cursor in `job_state`) are owned by the stats and tracker research; this report fixes only the owner-column rule that makes them erasable and the shape of the shared `subscription` table. The exact column set of `subscription` (for example a stored creator) is a proposal, not a measured need.
- **Source for the "common practice" claim.** Beyond BotCommands, I did not find a survey of what Kotlin Discord bots use for SQLite; the claim that Exposed is the most common Kotlin ORM is not made here.
