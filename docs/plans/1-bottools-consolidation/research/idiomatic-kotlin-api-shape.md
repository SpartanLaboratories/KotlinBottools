# The public Kotlin API shape of bottools

- **For:** SpartanLaboratories/KotlinBottools#1
- **Date read:** 2026-10-20
- **Applies to:**
  - Kotlin 2.2.0 to 2.2.21 (the build compiler), with the facts that change at Kotlin 2.3.0 (2025-12-16) and 2.4.0 (2026-07-14) noted where they matter.
  - JDA `v6.7.0` and jda-ktx 0.14.2 (settled by `jda-and-coroutine-bridge.md`); kotlinx.coroutines `1.10.2`.
  - Comparable code, all pinned: Ktor `3.6.0` (`111c5807d0a9004c8e0f17ae01e12a71aae56a29`) and `2.3.12`; Kord `main` @ `db459ec8fc140e42c08997a2dcd21491660dba3d` (2026-09-23); BotCommands `v3.4.0` (`c23a9e41b56874045e709b0d9a941e77a3c0b1cb`); Kord Extensions `v2.6.0` (`f86bef8eedc9db7f2f62aa56ce0a3bb62a86437d`, 2026-08-26, read from `codeberg.org/Kord-Extensions/kord-extensions`; documentation at `docs.kordex.dev`, read 2026-10-20); binary-compatibility-validator 0.18.2 (Maven Central, 2026-09-02).
  - In-repo precedent: MyGameTools (`gametools-core`: `SupportedExtension`, `ExperimentalGameToolsApi`, `MissingWorldSystemException`), KotlinBottools `main` @ `b2f2078`, GKB2 `master` @ `9422f85`.

## 1. Question

What shape should the public Kotlin API of `bottools-core`, `bottools-data-sqlite`, `bottools-stats` and `bottools-plugins` take, so that it is idiomatic, evolvable without breaking consumers, and safe under concurrent invocations? That covers the command DSL, the handler signature, option access, identifiers, JDA types, failures, stability tiers, ABI checking, system-versus-domain types and coroutine ownership.

Facts about the work that an answer must meet:

- The build compiler is Kotlin 2.2.x and consumers are Kotlin 2.2.x on the JVM. Only stable language features appear in the public API; anything in preview stays out or sits behind the Experimental marker. No Java-facing variants.
- Command definitions are immutable and one definition serves concurrent invocations through a per-invocation context. One declared option schema feeds slash registration, the typed parser and help. Aliases live in an immutable, typed-only path-alias table. The typed grammar is a pull-based binder with a sealed `ArgumentError`.
- JDA 6.7.0 is an `api` dependency; jda-ktx 0.14.2 is `implementation` only and never appears in a public signature; `kotlinx-coroutines-core` is `api`.
- Expected failures and lookups that can miss return `Result`, never a nullable. Library code logs through the slf4j API only. Every public declaration has KDoc.
- The design is open-ended: interface plus default implementation for systems, inheritance for domain types, policy parameterised, hooks exposed, additions opt-in, three stability tiers (Stable Core, `@SupportedExtension`, Experimental behind `@RequiresOptIn`).

## 2. Bottom line

- **Definitions: a `@DslMarker` builder that produces immutable, sealed data; handlers are `suspend CommandContext.() -> Unit`.** The receiver form is Ktor's idiom (`RoutingHandler = suspend RoutingContext.() -> Unit`) and is the same function type as `suspend (CommandContext) -> Unit`, so it costs nothing in evolvability. Annotations (BotCommands) need `kotlin-reflect` on the consumer's API and bind by name at start-up; class-per-command is the defect that keeps per-invocation state in shared fields. Kotlin context parameters are preview with `-Xcontext-parameters` in 2.2.x and stable only from 2.4.0 (2026-07-14); they stay out of the public API, and adopting them later is a breaking signature change, so the stable API is designed without them.
- **Options: typed keys, `ctx[option]`, explicit factories, no reified generics and no name-inferring delegates.** `Option<T>` is declared once on the definition and read from the per-invocation context. Delegates would put invocation state on a shared object (Kord Extensions' `Arguments` subclasses hold the parsed values in their converter delegates, and the framework instantiates one for every invocation, registration and signature render [C25]) and would let a Kotlin rename silently change a Discord-visible option name. Public `reified` inline functions leak internals into consumers' bytecode (`@PublishedApi` rules). Optional options carry their absence or default in the key's type; dynamic by-name lookup returns `Result`.
- **Identifiers: `@JvmInline value class GuildId/UserId/ChannelId/RoleId/MessageId(val value: Long)`.** Boxing in generics and collections costs about what `Long` already costs there; the gain is that the compiler rejects a `UserId` passed as a `GuildId`. All ports (storage, stats providers) take these, never JDA types. Kord's `Snowflake` is a plain class holding a `ULong`; I found no stated reason, so it is not evidence against value classes.
- **JDA: keep live JDA entities out of the semantic core, allow JDA data types, and say where JDA appears.** Live entities (`Guild`, `Member`, channels, events) are tied to a connected `JDA` instance and change in JDA minors; the library-owned `CommandContext` interface, value-class ids, parser, tree, alias table, help and all storage and provider ports are JDA-free. JDA appears in exactly three documented places: the typed event registry, entity-valued options and replies (JDA data types such as `MessageEmbed` and `MessageCreateData` need no connection), and an explicit native accessor. Everything else follows from JDA being `api`.
- **Failures: `kotlin.Result<T>` carrying typed, stackless exception subclasses, with sealed types only for closed protocol sets.** This is already the organisation's pattern (`MissingWorldSystemException` overrides `fillInStackTrace`). It runs against the stdlib's own guidance (Kotlin's `Result` KEEP says `findUserByName(): Result<User>` is an ERROR and to return `User?`); that disagreement is reported in section 3 (F6) and the cost is contained by narrow helpers. No library code wraps a suspend call in `runCatching`: it swallows `CancellationException`, and the stdlib issue that would fix it (kotlinx.coroutines #1814) has been open since 2020.
- **Tiers and ABI: copy MyGameTools' two markers, turn on explicit API mode, and gate the build with binary-compatibility-validator 0.18.2.** The Kotlin Gradle plugin's built-in ABI validation is experimental in 2.2.0 ("we don't recommend using it in production yet") and its DSL was reworked in 2.4.0; the standalone plugin is in maintenance mode but supported for current Kotlin. Exclude Experimental declarations from the dump. Use `@SubclassOptInRequired` (stable since 2.1.0) on interfaces the library may extend, so "stable to call" and "stable to implement" can differ.
- **Coroutines: one library-owned `CoroutineScope(SupervisorJob(parent) + dispatcher + handler)`, injected context, cancelled on close, never `GlobalScope`.** Handlers run off JDA's gateway thread on `Dispatchers.Default`; blocking storage sits behind main-safe ports on an injected `Dispatchers.IO.limitedParallelism(n)`; scheduled jobs are loops inside a `supervisorScope` child of the same scope.

## 3. Findings

Tiers: **Consensus** = official documentation, a spec, or several independent mature sources; **Practice** = what mature libraries visibly do; **Opinion** = one source's view; **Inference** = my reasoning from the cited facts, untested. Quote numbers `[C#]` refer to section 7.

### F1. Definition style: builder DSL over immutable data (Practice, Consensus for the mechanism)

- **Mechanism (Consensus).** A DSL is a function taking a lambda with receiver; `@DslMarker` makes the compiler refuse implicit access to outer receivers, so `head { head { } }` is an error [C9]. The Kotlin API guidelines add: required values are function parameters, because the compiler cannot check that a lambda set a required property [C16].
- **Ktor 3.6.0 (Practice).** `Route`/`RoutingNode` are marked `@KtorDsl` (a `@DslMarker`); `RoutingHandler = suspend RoutingContext.() -> Unit`; `routing { post("/article") { … } }` [C23]. In 2.3.12 the same handler was `PipelineInterceptor<Unit, ApplicationCall>`, i.e. the public receiver was the internal pipeline machinery, and `Route` was an open class; 3.6.0 replaced the receiver with a small `RoutingContext(val call: RoutingCall)` and made `Route` an interface [C23]. The lesson is to expose a small purpose-built context as the handler receiver and never the machinery behind it. Ktor 3.6.0 still carries `// TODO KTOR-8809: Uncomment the annotation` on `RoutingContext` and `Route`: they could not yet put `@KtorDsl` on the handler receiver without breaking code.
- **BotCommands v3.4.0 (Practice).** Two front ends: annotations (`@JDASlashCommand`, `@SlashOption`) and a Kotlin DSL `manager.slashCommand("say", function = ::onSlashSay) { option("channel") { description = … } }`. Both bind options to handler *parameters by name* through reflection: `BotCommands-core/build.gradle.kts` declares `api(libs.kotlin.reflect)`, and `SlashOption.name` is "optional if the parameter name is found" [C24]. A mismatch between a declared option and a handler parameter is therefore a start-up error, not a compile error.
- **Kord Extensions 2.6.0 (Practice, read at source).** `publicSlashCommand(arguments = ::MyArguments) { name = …; action { … } }` with an `Arguments` subclass of converter delegates (`val target by user { … }`). The `action` is a receiver lambda (`suspend C.(M?) -> Unit` on `SlashCommand`, `suspend ChatCommandContext<out T>.() -> Unit` on `ChatCommand`), and `@ExtensionDSL` is a `@DslMarker`. The delegate builders (`user { … }`) are not hand-written: each converter class carries `@Converter("user", types = […], builderFields = […])` and a KSP processor generates the builder functions, so writing a custom converter needs the `dev.kordex:annotation-processor` artifact (docs: "KSP annotation processor required for a few things"). The command objects are mutable classes configured inside the lambda, and a definition that fails validation is logged and dropped (CFP-C36 in `command-framework-prior-art.md`) [C25].
- **In-repo.** Today's `Command` keeps `guild`, `member`, `channel`, `args`, `reply` as instance fields on singletons, which is the concurrency defect `command-framework-prior-art.md` records. Class-per-command is the right tool for *domain types* under the organisation's rule; a command definition is configuration data, so it is not a domain type.

### F2. Handler signature: receiver, parameter or context parameter (Consensus on facts)

- A function type with a receiver and the same type with the receiver as first parameter are interchangeable [C11]. So `suspend CommandContext.() -> Unit` in the builder and `suspend (CommandContext) -> Unit` in the stored definition are one type; choosing the receiver form is a call-site ergonomics decision, not an ABI one.
- **Context parameters in Kotlin 2.2.x are a preview feature.** The 2.2.0 notes title the section "Preview of context parameters", mark it experimental, and require `-Xcontext-parameters` [C1]. Kotlin 2.4.0 (released 2026-07-14) promotes "Context parameters, except for context arguments and callable references" to Stable [C2]. The current documentation page for the feature still carries restrictions (no constructors, no delegated or backing-field properties) and an experimental `-Xexplicit-context-arguments` flag.
- Because the build language level is 2.2 and consumers are 2.2.x, a public signature using `context(...)` cannot be part of 1.0.0. Adding a context parameter to a published function later changes its JVM signature, so it would be a breaking change at the next major. **Inference:** this is a reason to design the stable handler type without relying on them, and to revisit at a major once the consumer floor is Kotlin 2.4.
- **Receiver scope hazard.** A handler body is inside the builder's lambda, so without `@DslMarker` on `CommandContext` the outer builder's members (`option(...)`, `handler { }`) resolve inside the handler. Ktor's unresolved `KTOR-8809` shows this is not trivial to retrofit; mark the context with the marker from day one.

### F3. Option access (Practice, Inference)

- **Kord Extensions 2.6.0** declares options as delegates on an `Arguments` subclass and exposes them as `arguments.target` in the action; the docs call the base class "Base class you should extend to represent a set of command arguments" and say the `args` list holds the converters "stored in the order they were defined" [C25]. The delegate returns the converter's own `parsed` field (`Converter.getValue(thisRef: Arguments, property: KProperty<*>)`, which throws `UninitializedPropertyAccessException` when the value is read before it was filled), so the `Arguments` object holds the values, and the framework builds a new one for every invocation: `ChatCommand` and `SlashCommand` store a factory `(() -> T)?`, and `ChatCommandParser.parse` and `SlashCommandParser.parse` call `builder.invoke()` [C25]. That is correct for them because their commands are not immutable definitions, and the same object is also their schema, which is why it is instantiated again at registration (slash options from `toSlashOption`) and for every signature render. Kord takes the option name from an explicit translation `Key` on the builder, not from the Kotlin property name, so it does not have the rename hazard described below.
- **Immutable definitions cannot keep values in a delegate.** A `val city by stringOption("city")` declared in a builder lambda would be a local delegated property on shared definition state; its getter has no invocation to read from. A typed key avoids this: the definition holds `Option<String>` (name, description, kind, bounds); the invocation holds the values; `ctx[city]` joins them.
- **Name inference is a hazard.** Taking the option name from the Kotlin property name makes a refactor rename a Discord-visible option (and break users' muscle memory, saved slash commands and help). Options carry explicit names.
- **Reified generics.** `inline fun <reified T> option(name)` would map `T::class` to a Discord option type with a runtime `when`, an unsound mapping (a `Long` could be INTEGER or a snowflake). A public inline function's body is compiled into consumer code, and what it references must be `@PublishedApi`, which "must be treated the same as public declarations" [C15]. Named factories (`stringOption`, `integerOption`, `userOption`…) are typed, reflection-free and not inline.
- **Absence.** An optional option that was not supplied is modelled input state. The key's type carries it (`Option<String>` with a default, or `Option<String?>` declared as absent-able); the dispatcher guarantees required options are bound before the handler runs because binding failures are an `ArgumentError`. The by-name path `ctx.option(name)` is a lookup that can miss and returns `Result` (see Gaps, point 1, for where the organisation's "never nullable" rule ends).

### F4. Identifiers (Consensus on mechanics, Practice on choice)

- **Mechanics (Consensus).** A value class holds one property, is always final, and "inline classes are boxed whenever they are used as another type" (as a type parameter, as an interface, as nullable) [C10]. Reference equality is prohibited. Functions taking value classes are name-mangled on the JVM [C10]; this matters for Java callers only.
- **Boxing is not a differentiator.** `List<GuildId>`, `Map<GuildId, V>`, `Result<GuildId>` and `GuildId?` box one small object, exactly as `List<Long>` boxes a `Long` (outside the small-value cache). Handler-rate traffic (events per second, not millions) makes this a non-issue; the benefit is type safety. **Inference** from [C10].
- **Equality and hashing** derive from the underlying `Long`; `GuildId(1) == UserId(1)` does not compile, and as `Any` the two are unequal because their classes differ. Override `toString` to `Long.toUnsignedString(value)`, which is what JDA's `ISnowflake.getId()` returns [C22]; keep `value` as the serialised and SQLite form.
- **JDA interop.** `ISnowflake.getIdLong()` returns `long`, and `Guild`, `User`, `Member` all extend it [C22]; conversions are one-liners both ways (`GuildId(guild.idLong)`, `jda.getGuildById(id.value)`). The Kotlin guidelines recommend a specialised class for ID abstractions and name inline value classes as the way to do it without a performance cost [C16].
- **Kord (Practice, opposite choice).** `dev.kord.common.entity.Snowflake` is `public class Snowflake : Comparable<Snowflake>` with `value: ULong`, coerced into `0..Long.MAX_VALUE`, one type for every entity kind [C26]. I found no source stating why it is a class. It adds timestamp helpers, which suggests a rich type was wanted, and a value class may not gain a second field later without changing its representation. Neither argues against distinct single-`Long` id types here.

### F5. JDA types in the public API (Practice, Inference)

- **Coupling facts.** JDA ships breaking changes in minor releases (README policy; 6.3.1 and 6.7.0 are examples), per `jda-and-coroutine-bridge.md` F1. JDA 6 introduced detached entities (`Guild`, `Member` extend `IDetachableEntity` at `v6.7.0`). The Kotlin guidelines warn: "Be careful when relying on types from third-party libraries or platform-specific types, as they can tie your library to these elements" [C14].
- **Live versus data.** `Guild`, `Member`, `User`, `MessageChannel` are interfaces, and `Guild` exposes `JDA getJDA()`: they are views of a connected session whose mutating methods are `RestAction`s [C22]. `SlashCommandInteractionEvent` is a concrete class. `EmbedBuilder` and `MessageCreateData` are plain classes with public factories (`MessageCreateData.fromContent`, `fromEmbeds`) that need no `JDA` instance [C22]. **Inference:** a fake that records replies can hold JDA *data* objects without a connection, but cannot construct a live `Member`; that is the testing line.
- **What peers do.** BotCommands exposes JDA throughout (`GuildSlashEvent` extends JDA's slash event; JDA is `compileOnly`) and ties itself to a JDA range (README badge "JDA 6.6.0+") [C24]; Chewtils and DIH4JDA do the same. Kord Extensions builds on Kord's types the same way (its contexts return Kord's `GuildBehavior` and `MemberBehavior`; CFP-C32 in `command-framework-prior-art.md`). Nobody ships a JDA-free handler surface; `command-framework-prior-art.md` F11 found none with a Discord-free handler test harness.
- **A full wrapper layer is not viable here.** The event registry, reaction roles (add a role to a member), the welcome message and admin plugins all act on live entities; re-wrapping them would build a second JDA. Ports and parsers do not need them, which is where a JDA-free surface pays off: the typed parser takes a resolver port, storage keys by value-class ids, stats providers take ids.

### F6. Failures: `Result` with typed stackless exceptions (Consensus on the facts; the sources disagree with the organisation's rule)

- **Organisation precedent (Practice, in-repo).** MyGameTools returns `Result<Zone>` from `zoneOf(entityId)` and `Result<WorldSystem>` from `systemOf`, with failures `UnzonedEntityException` / `MissingWorldSystemException`, "Stackless by design … a miss costs two small objects … and no stack walk", implemented as `override fun fillInStackTrace(): Throwable = this` on a `NoSuchElementException` subclass. GKB2's `Database` already returns `Result<Unit>`.
- **Mechanism for stackless (Consensus).** `Throwable`'s protected four-argument constructor takes `enableSuppression` and `writableStackTrace`; with `writableStackTrace = false` it "will not call `fillInStackTrace()`", `getStackTrace` returns an empty array, and the JDK docs name rethrown, control-flow-style exceptions as the use case for immutable throwables [C20]. Kotlin subclasses can call it in the supertype initialiser; the in-repo override is the other way and carries a comment about initialisation order.
- **Where the Kotlin sources disagree.**
  - Kotlin's API guidelines: "When data cannot be fetched or calculated, use a nullable return type and return `null` to indicate missing data. In other cases, throw an exception or return a `Result` type." and recommend a `Catching` suffix for the non-throwing variant [C12].
  - The `Result` KEEP: `fun findUserByName(name: String): Result<User> // ERROR`, "The `Result` class is not designed to represent domain-specific error conditions", and for failures that need local handling use nullable types or "domain-specific data types" such as a sealed class [C13]. It rejects `Result<T, E>` as an open issue and explains why the stdlib will not have one.
  - The organisation's rule is `Result` for expected failures and misses, never nullable. The axis of disagreement is *what the failure value is*: the stdlib wants lightweight nullable or sealed outcomes for locally handled failures; the organisation wants one envelope with a typed exception. The rule is a settled requirement, so the design adopts it and removes its cost where it can: stackless typed exceptions, narrow helpers, sealed sets only for closed protocols.
- **Costs of the envelope.**
  - The error side is `Throwable`, so `when (e)` over subtypes is never exhaustive without an `else`; a helper that narrows to the library's error base and rethrows anything else restores the discipline (inference).
  - Mocking frameworks mishandle `suspend fun …: Result<T>`: MockK issue #1073 (value classes as `coEvery` answers; "class java.lang.String cannot be cast to class kotlin.Result") is still open with reports through MockK 1.14.6 (October 2025); #777 was a Kotlin 1.5-era variant that disappeared in Kotlin 1.6.10 [C27]. Hand-written fakes for ports avoid it and suit the Level 2 approach.
  - `kotlin.Result` as a return type is a value class: the same boxing and mangling as F4.
- **Where sealed outcomes are right (Consensus).** The guidelines recommend sealed types for closed sets and note they give exhaustive `when` [C12 predictability]. Use them for protocol sets: the node kinds `Group/Leaf/UserMenu/MessageMenu`, `Invocation` (slash, typed, user menu, message menu), `InvocationLocation` (guild or direct message), the acknowledgement state, and the *kinds* of `ArgumentError` (a `Throwable` subtype hierarchy, so it travels in `Result`). A sealed set that can grow is source-breaking for consumers' exhaustive `when` (community consensus, no official guideline found), so it is part of the contract, not a convenience.
- **Open sets stay open.** `Denial` (a precondition's reason) must be extensible by plugins, and sealed subclasses must live in the same module and package, so it is an open class with the built-in denials as subclasses.

### F7. Result, cancellation and coroutines (Consensus)

- Cancellation is a `CancellationException`; "these exceptions are ignored by all handlers", and "If a coroutine encounters an exception other than `CancellationException`, it cancels its parent" [C18]. Swallowing one stops cancellation from working. Android's coroutine guidance: "don't consume exceptions of type `CancellationException` (don't catch them, or always rethrow them if caught)" [C17].
- `runCatching` catches every `Throwable`, so wrapping a suspend call in it swallows cancellation. The stdlib change request "Provide a `runCatching` that does not handle a `CancellationException` but re-throws it instead" (kotlinx.coroutines #1814, opened 2020-02-18) is still open [C17]; detekt ships a `SuspendFunSwallowedCancellation` rule, inactive by default [C28]. The library therefore needs its own internal `suspendCatching { }` that rethrows `CancellationException`, plus the lint rule enabled.
- **Timeout trap.** `withTimeout` throws `TimeoutCancellationException`, a subclass of `CancellationException` [C19]. A provider that wants "the API timed out" to be an expected failure must catch that exception specifically *inside* its own `withTimeout` block and convert it, then check `ensureActive()` (inference) so a real parent cancellation still propagates; a blanket "rethrow every `CancellationException`" helper would let the timeout kill the handler.
- `CoroutineExceptionHandler` runs only for uncaught exceptions of *root* coroutines; children delegate to their parent, and `async` never uses it [C18]. A per-invocation `scope.launch` is a root under the supervisor, so the handler on the scope is the last-resort net; the dispatcher still catches `Exception` around the handler body and rethrows cancellation.

### F8. Stability tiers, explicit API mode, ABI validation (Consensus on facts)

- **Opt-in markers (Consensus).** A marker is an annotation class annotated `@RequiresOptIn`; it must have `BINARY` or `RUNTIME` retention, no `EXPRESSION/FILE/TYPE/TYPE_PARAMETER` target and no parameters; level `ERROR` (default) or `WARNING` [C7]. A graduated marker's class is kept (deprecated) so consumers' `@OptIn` still compiles [C7]. The Kotlin guidelines say to use the mechanism "to manage expectations concerning source and behavioral compatibility" and "Avoid using the opt-in mechanism to deprecate already existing declarations" [C6].
- **Levels in practice (Practice).** Ktor 3.6.0: `InternalAPI` is `ERROR`; `ExperimentalKtorApi` is `WARNING`; the old `KtorExperimentalAPI` is kept as `@Deprecated(level = ERROR)` [C23]. kotlinx.coroutines 1.10.2: `ExperimentalCoroutinesApi` and `DelicateCoroutinesApi` are `WARNING`; `InternalCoroutinesApi` is `ERROR`. BotCommands: `ExperimentalCoreApi` is `ERROR`. MyGameTools: `ExperimentalGameToolsApi` is `ERROR`, deliberately, "an unintentional touch should fail to compile". The axis is how much casual contact the surface gets; `ERROR` suits a small, deliberate Experimental seam.
- **`@SupportedExtension`.** MyGameTools' version is `@MustBeDocumented`, `@Retention(BINARY)`, a target set (class, function, property, constructor, typealias), no `@RequiresOptIn`, and its KDoc states "the same semver guarantee as Stable Core". It is purely documentary. The compiler-enforced form would be wrong because the tier promises stability.
- **Stable to call, not to implement (Consensus).** `@SubclassOptInRequired(Marker::class)` requires opt-in to implement an interface or extend a class; it arrived in Kotlin 2.1.0 and kotlinx.coroutines' `SharedFlow` uses it with `ExperimentalForInheritanceCoroutinesApi` [C8]. This fits `CommandContext`: consumers call it and tests fake it, while the library adds members in feature releases. System interfaces meant to be implemented (`Precondition`, `CommandMessages`, `HelpRenderer`, option converters) stay freely implementable.
- **Interface evolution on the JVM.** Since Kotlin 2.2.0 interface functions with bodies compile to JVM default methods (`-jvm-default=enable` is the default and includes compatibility bridges) [C21]. Do not set `-jvm-default=disable`. Adding a defaulted member is then binary-compatible for existing implementers (inference from [C21]). Adding an abstract member, a `data class` field or a constructor parameter is not: the guidelines say a data class "strength becomes a weakness" for API (`copy` and `componentN` change) and that default arguments are not binary-safe either, with `@JvmOverloads` not preserving binary compatibility for Kotlin callers [C6].
- **Explicit API mode (Consensus).** `kotlin { explicitApi() }` requires visibility modifiers and explicit types on public declarations; it exempts primary constructors, data-class properties, accessors and `override`s, and analyses production sources only [C5]. The guidelines recommend it [C16]. It does not check KDoc; Dokka's `reportUndocumented` plus `failOnWarning` does ("works well with `failOnWarning`") [C29].
- **ABI validation, status as of 2026-10-20.**
  - **KGP built-in, Kotlin 2.2.0 (the build compiler):** experimental; "You can try it out in toy projects, but we don't recommend using it in production yet. The original binary compatibility validator continues to be maintained during this experimental phase."; enabled by `abiValidation { enabled.set(true) }` under `@OptIn(ExperimentalAbiValidation::class)`; task `checkLegacyAbi` [C3].
  - **KGP built-in, Kotlin 2.4.0:** "streamlines the DSL … and deprecates some parts" [C4]; the current page documents `abiValidation()`, `checkKotlinAbi`/`updateKotlinAbi` and `filters { excluded { annotatedWith … } }`, still behind `ExperimentalAbiValidation`. It is therefore a moving target across the toolchain bumps this library will make.
  - **binary-compatibility-validator:** README: "This plugin is in maintenance mode. Fixes for critical bugs and support for current versions of Kotlin continue to be delivered."; Alpha badge; requires Kotlin 1.6.20+; 0.18.2 is the latest on Maven Central (metadata `lastUpdated` 2026-09-02) [C30]. Tasks `apiDump`/`apiCheck`, wired into `check`; `nonPublicMarkers` excludes annotated declarations from the dump [C30].
  - **Adoption (Practice).** kotlinx.coroutines 1.10.2 uses the standalone plugin (`0.16.2`) with `ignoredPackages += "kotlinx.coroutines.internal"` [C31]; Ktor 3.6.0 (Kotlin 2.3.21) has moved to the built-in `abiValidation` with `@OptIn(ExperimentalAbiValidation::class)` and uses `explicitApi()` [C23].

### F9. Systems as interfaces, domain types as classes, sealed versus open (Consensus, in-repo rule)

- The organisation's rule places systems and infrastructure behind interfaces with a shipped default and domain types under inheritance, reserving `sealed`/`final` for closed protocol sets. The Kotlin guidelines agree on the sealed case: "Users should not be able to extend your library in ways that violate its original design" and sealed enables exhaustive `when` [C12 predictability].
- Applied: `CommandContext`, `CommandMessages`, `HelpRenderer`, `Precondition` (`fun interface`), option converters, `PrefixPolicy`, `AliasResolver`, storage and provider ports are interfaces with defaults. `Bot`-level domain types users extend (plugins, game and account models in `bottools-stats`) are `open`/`abstract` with invariants `final`. The tree nodes, `Invocation`, `InvocationLocation`, `AckState`, `ArgumentError` kinds are `sealed`. The immutable `AliasTable` and `CommandPath` are final value-like classes with hand-written `equals`/`hashCode`, not `data classes`, so fields can be added.
- Sealed hierarchies cannot be extended from another module, so anything a plugin must extend (`Denial`, `PluginEvent` kinds, option kinds if converters are open) is not sealed.

### F10. Today's operator-heavy style: what to keep (Opinion backed by official conventions)

- The Kotlin conventions: "Declare a function as `infix` only when it works on two objects which play a similar role. Good examples: `and`, `to`, `zip`." and "Do not declare a method as `infix` if it mutates the receiver object." [C16]. To minimise API pollution, prefer member extension functions scoped to where they are needed [C16].
- **Keep (pure, value-building, scoped).** The alias phrase `get and "city" becomes "getcity"` constructs a value (`AliasRule(path, target)`) and registers it with the enclosing `aliases { }`; define `and` and `becomes` as member extensions of that block so `"x" and "y"` exists nowhere else. A path-join `/` on a `CommandPath` follows the stdlib's `Path.div` ("Resolves the given other path string against this path.") [C32].
- **Drop (mutating, stateful or semantically unrelated).** `Bot say x in channel` is a chain of infix calls on a global singleton that sends; replace with `ctx.reply(…)` or a channel port. `D / guild / member / "Games" - "id"` uses `div` as navigation and `minus` as a read on an untyped string store and returns `String`; replace with typed ports returning `Result`. `this + Option(...)` as `plus` mutating the receiver breaks the infix/operator expectation; options are declared in the builder. The `Responder newGuildJoinAction …` infix family disappears with the typed event registry.

## 5. Pitfalls and regrets

- **Exposing the machinery as the receiver.** Ktor's 2.x handler receiver was the pipeline context; 3.x needed a new type, a changed `Route`, and still has an annotation it could not add (`KTOR-8809`). Expose a purpose-built `CommandContext` and mark it `@DslMarker`.
- **`runCatching` around suspend calls.** Silent loss of cancellation; the fix has been open in the stdlib since 2020 [C17]. A `Result`-returning port such as `suspend fun find(id): Result<Link>` is exactly where this is written by reflex.
- **Reflection-bound option names.** BotCommands' name binding puts `kotlin-reflect` on the consumer's API, depends on parameter names being available (its KDoc points to a wiki page on parameter names), and fails at start-up [C24]. A typed key fails at compile time.
- **`data class` for evolvable API.** Generated `copy` and `componentN` freeze the field list [C6]. Today's `data class orgData` would not survive.
- **Public inline and reified.** Bodies end up in consumer bytecode and force `@PublishedApi` on what they touch [C15].
- **Sealed hierarchy growth.** A new subtype breaks consumers' exhaustive `when` at compile time; treat the sealed sets in F6 as contract.
- **Mock-based tests of `suspend … Result<T>` ports.** MockK #1073 is open [C27]. Use hand-written fakes.
- **Stackless exceptions lose diagnosis.** `getOrThrow()` on a stackless failure throws without a trace. Put the identifying data in properties and the message, and log at the catch site; do this only for expected failures, never for bugs.
- **Deleting a graduated marker.** Breaks every consumer's `@OptIn`; keep and deprecate [C7].
- **Value-class traps.** Mangled names appear in stack traces; a value class cannot later gain a second field; `GuildId?` and `List<GuildId>` box. None matters at bot scale.
- **Aggressive default scope in the bridge.** jda-ktx's default event scope is not cancelled by `JDA.shutdown()` (`jda-and-coroutine-bridge.md` pitfall 5); the library supplies its own scope.
- **Blocking on the gateway thread.** JDA runs events "on the calling thread by default" [C33] and marks `RestAction.complete()` `@Blocking`; any `complete()` or JDBC call in a handler stalls the gateway.

## 6. Recommendation for this repo

The recommended shape, in code (illustrative signatures, not final names):

```kotlin
@DslMarker public annotation class BotToolsDsl

// Definition: builder -> immutable, sealed tree. Required values are parameters.
public fun commandTree(block: CommandTreeBuilder.() -> Unit): Result<CommandTree>   // validates; Catching-style envelope

commandTree {
    group("dota", "Dota 2 commands") {
        val player = userOption("player", "Whose profile").orInvoker()           // Option<UserRef>
        leaf("profile", "Show a profile", response = Public) {
            options(player)
            handler {                                                              // suspend CommandContext.() -> Unit
                val p = this[player]
                reply(profileFor(p))
            }
        }
    }
    aliases { (dota and "setid") becomes (dota / "id" / "set") }                    // pure phrases, member extensions
}

@BotToolsDsl @SubclassOptInRequired(ImplementsCommandContext::class)
public interface CommandContext {
    public val invocation: Invocation               // sealed: Slash | Typed | UserMenu | MessageMenu
    public val invoker: UserId
    public val location: InvocationLocation         // sealed: Guild(guildId, channelId) | DirectMessage(channelId)
    public operator fun <T> get(option: Option<T>): T
    public suspend fun option(name: String): Result<OptionValue>      // dynamic lookup that can miss
    public suspend fun reply(message: MessageCreateData, ephemeral: Boolean? = null)
    public suspend fun defer(): Unit
}

@JvmInline public value class GuildId(public val value: Long) { override fun toString(): String = value.toULong().toString() }
```

Reasoning and the parts that depart from the obvious:

1. **DSL, not annotations or subclassing.** The DSL gives compile-time option wiring, an immutable result, validation in one place and no reflection. `build()`-style validation returns `Result` because invalid definitions can be data-driven (plugin loops); a throwing top-level wrapper is the `Catching`-pair convention [C12]. Plugins contribute through `fun CommandTreeBuilder.register()` extension modules, not subclasses.
2. **Receiver handler, typed keys, no delegates, no reified, no context parameters.** Each rejected option has a concrete failure above (F1-F3).
3. **Separate guild-only commands by type, not by a nullable.** `guildLeaf { }` hands the handler a `GuildCommandContext` with non-null `guildId`; the plain `leaf` exposes `location` as the sealed `InvocationLocation`. This mirrors BotCommands' `GuildSlashEvent` and keeps `ctx.guild!!` out.
4. **JDA surface, stated.** Library-owned and JDA-free: `CommandContext`, ids, `CommandTree`, `AliasTable`, `ArgumentError`, `HelpRenderer`, `PrefixPolicy`, all ports in `bottools-core`, everything in `bottools-data-sqlite` and the providers in `bottools-stats`. JDA-visible and documented as "follows JDA, exact version pinned": the event registry's event types, entity-valued option values and the explicit native accessor on the context (declare it `@SupportedExtension` or Experimental, not Stable Core, because JDA minors can break it). JDA data types (`MessageEmbed`, `MessageCreateData`, `FileUpload`, `Permission`) are allowed in signatures. The semver rule is: a JDA major bump is a bottools major; a JDA minor that breaks a JDA-visible signature ships as a feature release with the exact JDA pin recorded in the changelog.
5. **Result discipline.** Misses and expected failures return `Result<T>` whose failure is a stackless subclass of one open `BotToolsException` base (open, so `bottools-data-sqlite` and plugins add their own); ship `inline fun <T, R> Result<T>.foldFailure(...)` narrowing to the base and rethrowing others; an internal `suspendCatching` that rethrows `CancellationException`; detekt `SuspendFunSwallowedCancellation` on; hand-written fakes at Level 2.
6. **Tiers and gates.** Add `SupportedExtension` and an `ExperimentalBotToolsApi` (`@RequiresOptIn(level = ERROR)`, `BINARY`) to `bottools-core`, modelled on MyGameTools; `explicitApi()` in the convention plugin; Dokka `reportUndocumented` with `failOnWarning`; BCV `0.18.2` on `apiCheck` in `check`, with the Experimental marker in `nonPublicMarkers` so Experimental changes in a feature release do not fail the build (inference: the plugin's `nonPublicMarkers` exists for exactly "marker" API [C30]). Do not use the KGP built-in validation under Kotlin 2.2.0; reconsider when the toolchain reaches a Kotlin whose docs drop the experimental opt-in. Record the choice in the changelog.
7. **Coroutines.**
   - **Owner.** The bot runtime object owns `CoroutineScope(SupervisorJob(parentJob) + dispatcher + CoroutineName("bottools") + CoroutineExceptionHandler { _, e -> log.error(…) })`, built from an injected `CoroutineContext` (default empty) so MagicBot supplies a parent and tests supply a `TestDispatcher`. The same scope is passed to the jda-ktx event manager so event coroutines are its children. No `GlobalScope`.
   - **Per invocation.** One `scope.launch` per invocation under the supervisor; the dispatcher catches `Exception`, answers with the generic message and rethrows `CancellationException`.
   - **Dispatchers.** Handlers run on `Dispatchers.Default`. Blocking I/O lives in main-safe ports that `withContext` an injected `Dispatchers.IO.limitedParallelism(n)` (elastic views share threads with `Dispatchers.IO` [C14b]); the SQLite adapter owns the limit. `RestAction.complete()` and JDBC never run on a gateway or handler thread.
   - **Scheduled jobs.** Each job is a loop with `delay` inside a `supervisorScope` child of the bot scope; every iteration catches `Exception` (not cancellation), with the clock and dispatcher injectable so `runTest` virtual time drives it.
   - **Shutdown.** `close()` stops intake, drains in-flight handlers for a configurable grace period, cancels the scope (`cancelAndJoin`), then shuts JDA down and closes ports (inference: the reply of an in-flight handler needs JDA still up; JDA's `shutdown()` lets only already-enqueued `RestAction`s finish [C33]; Question 5 owns the runtime sequence).
8. **I would reject** (a) delegate-style `val id by string("id")` on definitions, (b) `reified` option factories, (c) `data class` results, (d) Kotlin context parameters in 1.0.0, (e) a hand-rolled `Result<T, E>`/`Either` (the stdlib rejects it, the organisation's rule is `Result`), and (f) a full JDA wrapper layer.

- **`suspendCatching` and `foldFailure` shapes, the timeout-conversion pattern and the shutdown ordering are my design reasoning**, flagged inference in F7 and section 6; none has been run against JDA 6.7.0 and jda-ktx 0.14.2.
- **Point 1: the boundary of "never nullable".** An optional command option that is absent, and `invocation.location` for a direct message, are modelled input states, not lookups that can miss. The design carries them in types (a default, `Option<T?>`, a sealed `InvocationLocation`), which keeps accessor return types non-null for lookups but does contain `T?` as a *declared option type*. If the rule is meant to forbid even that, optional options must always have a default or the author must supply a `Result`-returning `ctx.optionalValue(...)`; this needs the maintainer's reading of the rule. Recommendation: allow `Option<T?>` as a declared type only.
- **Point 2: where the JDA line sits for entity-valued options and the native accessor.** The recommendation keeps JDA live entities in option values and behind one explicit accessor. A stricter alternative returns only ids and makes handlers resolve entities through a context method returning `Result<Member>`; it is testable without JDA but costs a lookup per entity and a wrapper surface. Recommendation: the lighter line, revisited after the first plugin (reaction roles) is written against it.
- **Mapping to Kotlin 2.4 later.** Moving the build compiler to Kotlin 2.4 (needed for jda-ktx 0.15.0) with `languageVersion`/`apiVersion` held at 2.2 keeps consumers on 2.2.x readable; whether `-language-version 2.2` then also permits context parameters in the library's *internal* code is not established.
