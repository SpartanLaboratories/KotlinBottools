## 1. Question

How should the bot runtime in `bottools-core` dispatch Discord events, install plugins, run scheduled jobs, read configuration, derive gateway intents and caches, prepare for sharding, isolate errors, and start and stop?

Facts about the work that an answer has to meet:

- A plugin adds commands, event handlers, jobs and settings without touching core.
- Gateway intents are the union of what installed features declare. Member caching is minimal. The current code requests every intent and caches every member (`bottools.main.Bot`: `EnumSet.allOf(GatewayIntent::class.java)` and `MemberCachePolicy.ALL`), which a public bot must not do.
- Jobs (the match tracker, the patch-notes feed) survive handler failures and restarts, with state persisted through the storage ports. A job posts once per guild, not once per shard.
- The bot is built through JDA's `ShardManager`. jda-ktx stays internal. One library-owned `CoroutineScope(SupervisorJob + injected dispatcher + exception handler)` is shared with the event manager and cancelled on close.
- The token comes from the environment or a file outside the repository. Startup validation errors are a `Result`. Library code logs through the slf4j API only, with named lifecycle events.
- Lifecycle status and events stay internal or Experimental. There is no management seam, and no UI.
- Kotlin 2.2.x, JDK 21, JVM-only consumers.

Current state, by symbol: `Bot` starts everything in a static initialiser and reads `key.txt`; `Responder` (Java) classpath-scans JDA `Event` subclasses through Spring's `ClassPathScanningCandidateComponentProvider` and calls handlers on JDA's thread; `BotListener` forwards ten event types to it; `CheckValueService.run` loops on a raw `Thread` with `Thread.sleep` and no `try`/`catch`, so any exception ends the service silently; `Bot.CentralProcess` is a daily loop on a raw thread whose last-run date lives in an XML file; GKB2's `CommandFactory` builds a Spring `ClassPathXmlApplicationContext` from `plugins.xml`, and `Plugins` maps names to `Plugin { responder newMessageReactionAddAction ...; listOf(commands) }` lambdas.

## 2. Bottom line

- **Dispatch: build one `jda-ktx` `CoroutineEventManager` per shard from `setEventManagerProvider`, all over the same handler scope, with exactly one registered listener: the library's router.** `injectKTX()` cannot be used for this because it builds each shard's manager with jda-ktx's own default scope and takes no scope parameter. The router looks up an immutable typed registry (a snapshot closed at login), and runs each matching handler as its own child under `supervisorScope`, with a per-handler timeout and try/catch. A failing or slow handler therefore delays and breaks nothing else. A `SharedFlow` per event type is rejected as the dispatch primitive: by default a slow collector suspends the emitter, the drop policies lose events, and a collector that throws silently stops listening.
- **Plugins are installed in code by the application, and only so.** A plugin contributes commands, typed handlers, jobs, settings, declared requirements (intents, cache flags, member policy) and lifecycle and data-erasure hooks while it installs, before login, which is what makes the intent union computable. `ServiceLoader` is rejected: classpath presence would silently widen intents and registrations, the umbrella `bottools` artifact contains every plugin, and fat jars need service-file merging. Plugins named in configuration are a selection the application makes among plugins it compiled in, not a library feature. Per-guild enable/disable is a stored setting consulted by a gate in the router before each handler and command.
- **Jobs are sequential coroutine loops in a supervisor of their own, with a small persisted `JobState`.** Fixed-delay scheduling from completion time, startup jitter, full-jitter exponential backoff, one run on startup if overdue (a cursor owned by the job does the catching up, so missed ticks are never replayed), a per-run timeout, and bot-level ownership so nothing is per shard. Quartz, krontab and cron-utils are rejected. Quartz is thread-based and persists through its own JDBC schema, which would duplicate the storage ports. krontab and cron-utils only compute times. Schedules are `java.time` based; `kotlin.time.Clock` is not stable until Kotlin 2.3.0.
- **Configuration is a typed, dependency-free `BotConfig` loaded from environment variables plus an optional `.properties` file, returning `Result` with every problem listed.** The token is read from `…_TOKEN_FILE` (a path) or `…_TOKEN` and held in a masking `Secret`. Hoplite (`kotlin-reflect` and an old coroutines on every consumer's runtime, user-home sources on by default), Lightbend Config and the kotlinx-serialization formats stay out of `bottools-core`; an application may use any of them to feed the builder.
- **Intents and caches are derived, never listed.** The union is JDA's own `GatewayIntent.fromEvents` over the registry's handler types, plus `fromCacheFlags`, plus explicit declarations that events cannot express (`MESSAGE_CONTENT` for the bare prefix). JDA's `DefaultShardManagerBuilder.create(token, intents)` silently sets `MemberCachePolicy.ALL` and `ChunkingFilter.ALL` whenever `GUILD_MEMBERS` is present, so the runtime must set the member policy and chunking filter explicitly afterwards. Privileged intents need an explicit allowance in configuration; a feature that needs a privileged intent that is not allowed is switched off (optional) or fails startup (required), with a named log event, instead of a 4014 close.
- **Lifecycle: start configuration → storage → plugin install → intent resolution → login → all-shards-ready → command registration → plugin ready hooks → jobs. Stop in this order: close intake → stop jobs → drain handlers (grace) → plugin stop hooks → cancel the scopes (hard timeout) → `ShardManager.shutdown` and per-shard `awaitShutdown` → close storage.** Draining before the gateway closes lets in-flight replies complete. JDA's own shutdown hook is disabled so the library owns the order. Lifecycle state is an internal `StateFlow` that falls out of the sequence.

## 3. Findings

Tiers: **Consensus** = official statement, spec, or several independent sources. **Practice** = what mature libraries visibly do. **Opinion** = one source's view. **Measured** = read directly from source at the pinned version. **Inference** = my reasoning from cited facts, not run. Numbers `[C#]` refer to section 7.

### F1. Event dispatch

**JDA's default (Measured, JDA 6.7.0).** `InterfacedEventManager.handle` calls every listener in turn on the thread that delivers the event, catches `Throwable`, logs it, and rethrows `Error` [C1]. `DefaultShardManagerBuilder.setEventPool` says events run "on the calling thread by default" [C1]. A blocking listener therefore stalls that shard's gateway thread, and `JDA.shutdown()` "will interrupt the default JDA event thread" [C9], so a blocking handler is also interrupted mid-work at shutdown.

**jda-ktx `CoroutineEventManager` (Measured, 0.14.2 sources = master).** `handle(event)` returns immediately after `launch { for (listener in listeners) try { … } catch (ex: Exception) { log.error("Uncaught exception in event listener", ex) } }`. One coroutine per event, listeners one after another inside it, no ordering between events [C2]. Consequences for the design:

- It is a fine seam for freeing the gateway thread, but its per-event listener loop means a slow listener delays the others. The remedy is to register one listener, the router, and do fan-out there.
- The `catch (ex: Exception)` also catches `CancellationException`. When the library force-cancels its scope at shutdown, in-flight events log one spurious ERROR line each. Noise only; see Pitfalls.
- `DefaultShardManagerBuilder.injectKTX(timeout)` is `setEventManagerProvider { CoroutineEventManager(timeout=timeout) }` [C2]: a new manager, with `getDefaultScope()` (own `SupervisorJob`, `Dispatchers.Default`), per shard. It cannot be cancelled by the library. The constructor takes `scope: CoroutineScope`, so `setEventManagerProvider { CoroutineEventManager(scope = handlerScope, timeout = Duration.INFINITE) }` gives every shard a manager over the one library-owned scope.
- `DefaultShardManager.addEventListener` records listeners in `eventConfig` and `buildInstance` re-adds them to every shard it creates, so one router instance registered through the builder reaches shards created later and shards restarted later [C3].

**Event flows (Consensus on the `SharedFlow` contract).** `MutableSharedFlow()` with no buffer is rendezvous: "`emit` … suspends until all subscribers receive it"; with a buffer, overflow either suspends the emitter or drops, and "emitting has O(N) cost, where N is the number of subscribers" [C4]. On JDA's thread an emitter that suspends is not an option, so a lossy overflow policy would be needed, and losing a command or a reaction is worse than a slow handler. A collector that throws terminates that collector, so each plugin would need its own retry wrapper, which is the isolation code the router does once. Flows are also unsuited to the `custom_id`/command lookups that the router does by key. Verdict: not the dispatch primitive; a read-only flow tap for observers could be added later as an opt-in extension without changing dispatch.

**Typed registry (Inference, supported by BotCommands' design).** BotCommands resolves handlers per event class from a registry before running them (`EventDispatcherImpl.onEvent` → `eventListenerRegistry[event.javaClass]`) [C13]. JDA events form a class hierarchy (`MessageReceivedEvent` ⊂ `GenericMessageEvent` ⊂ `GenericEvent`), so the registry resolves a concrete class once to the ordered list of bindings whose declared type is assignable, and caches it per class. The snapshot is immutable after plugin install, which is what lets intents be derived from it and the router run without locks.

**Isolation levels.** Handler exception: caught per handler, logged with plugin id, event type, guild and shard; the command layer owns the user-facing message. Handler timeout: `withTimeout` inside the handler's own `try`, converting `TimeoutCancellationException`, while still rethrowing a real parent cancellation (the `TimeoutCancellationException` is a `CancellationException`; see `idiomatic-kotlin-api-shape.md` F7). Last resort: the scope's `CoroutineExceptionHandler`, which per its KDoc runs only for root-like coroutines, and children of a `SupervisorJob` count as such [C5]. `VirtualMachineError` is rethrown rather than isolated (Opinion).

**Ordering (Inference).** JDA's default delivers a shard's events in order; a coroutine per event does not. Reaction add/remove on one message, or message create/delete, can race. Handlers are written idempotently against stored state; a handler may opt into a per-key serial lane (a keyed `Mutex` or per-key channel) where order matters. No global ordering is promised.

### F2. Gateway intents, caches, member policy

- **JDA provides the mapping (Measured).** `GatewayIntent.fromEvents(Collection<Class<? extends GenericEvent>>)` maps event classes to intents (`GenericGuildMemberEvent`, `GuildMemberRemoveEvent` → `GUILD_MEMBERS`; `GenericMessageEvent` → `GUILD_MESSAGES` and `DIRECT_MESSAGES`; `GenericMessageReactionEvent` → the two reaction intents; presence events → `GUILD_PRESENCES`), `fromCacheFlags` maps `CacheFlag.getRequiredIntent()`, and `from(events, flags)` unions them [C6]. Interaction events map to none. The mapping is conservative (a message handler gets both guild and DM intents), so an explicit declaration may narrow nothing but may add what events cannot say: `MESSAGE_CONTENT`, which is a property of how the bot reads messages, not of an event class.
- **JDA's convenience builder undoes the policy (Measured).** `DefaultShardManagerBuilder.create(token, intents)` runs `applyIntents()`, which sets `setChunkingFilter(enableMembers ? ChunkingFilter.ALL : NONE)` and `setMemberCachePolicy(enableMembers ? MemberCachePolicy.ALL : MemberCachePolicy.DEFAULT)` [C7]. The join feature adds `GUILD_MEMBERS`, so the naive path would turn on cache-everything for a public bot. `build()` rejects the converse (`ALL` without `GUILD_MEMBERS` throws `IllegalStateException`) and warns about chunking without the intent [C7]. The runtime sets both explicitly after choosing intents.
- **`GUILDS` is always on** (JDA: "we currently don't support to disable this one as its required to get a good base cache") [C6].
- **Cache flags** auto-disable when their intent is missing, with a warning listing each flag [C7]; the runtime names the flags it needs so that warning never appears.
- **Failure mode (Measured).** A privileged intent that is requested but not enabled for the application closes the connection with 4014, and `CloseCode.DISALLOWED_INTENTS` is declared non-reconnecting [C8]. Preflight through `ApplicationInfo.getFlags()` is not dependable: JDA's `Flag` documentation still describes the pre-2026-06-10 100-guild semantics (`GATEWAY_GUILD_MEMBERS` "in 100 or more guilds" versus `_LIMITED` "under 100"), and `retrieveApplicationInfo` needs a built JDA. Use an explicit allowance in configuration plus a clear diagnostic when the close arrives.
- **Comparable practice.** Kord Extensions derives intents from extensions: `Extension.event<T>()` records the intents of the event type in `Extension.intents`, and `ExtensibleBot.start()` builds the login intents from `ExtensibleBotBuilder.intentsBuilder`, whose default is all non-privileged intents, plus `MessageContent` when chat commands are enabled, plus every loaded extension's recorded intents; the docs say it enables "any intents your bot's extensions need, based on their event handlers" [C11]. The default is additive over a fixed non-privileged base, not a minimal set, and it does not check what the application has been granted. BotCommands makes the same check explicit: `JDAService` documents "Checking gateway intents, cache flags, and member cache requirements for event listeners and event waiters" and skips listeners whose intents are missing (`EventListenerRequirementsVerifierImpl`: "Skipping JDA event listener … as it is missing intents") [C13]. Both are Practice, and both agree with deriving rather than listing.

### F3. Plugins

**Comparable systems (Practice).**

| System | Unit | Installed by | Lifecycle hooks | Notes |
|---|---|---|---|---|
| Kord Extensions 2.6.0 | `Extension` with `name`, `setup()`, `unload()`, `intents`, and lists of its commands, event handlers and checks | `extensions { add(::MyExtension) }` in code; plus PF4J plugins from `./plugins` by default (`PluginBuilder.pluginPaths`), where a `KordExPlugin.setup()` registers extensions | `setup()` runs from `addExtension` during bot construction, before `start()` logs in; `unload()` plus automatic removal of the extension's event handlers and chat commands in `doUnload`; `ExtensionState` events (`LOADING`, `LOADED`, `UNLOADING`, `UNLOADED`, `FAILED_*`) | `ExtensibleBot.loadExtension`, `unloadExtension` and `removeExtension` work at runtime; slash commands of an unloaded extension stay registered at Discord and simply "will not execute" [C11] |
| BotCommands | `@BService` classes | classpath scan of packages named with `addSearchPath` | `PreLoad`, `Load`, `PostLoad`, `Ready`, `ShuttingDown`, `Shutdown` as `BContext.Status` and events | JDA is created last: "Starting JDA when every other service is ready" [C13] |
| Red-DiscordBot | cog packages | names stored in `Config.packages()` and loaded before connecting | per-cog unload; a package that fails to load is logged and dropped, startup continues | Every cog "should be overridden" to handle `red_delete_data_for_user` [C14] |
| discord.py | extension module with `setup(bot)`; `Cog` | `load_extension(name)` | `cog_load`, `cog_unload`; "Exceptions raised in this method are ignored during extension unloading." | [C15] |
| Ktor server | `Plugin.install(pipeline, configure: TConfiguration.() -> Unit)` | `install(Plugin) { … }` in code | application lifecycle events | the Kotlin convention for in-code installation with a typed configuration lambda [C16] |

The common shape is a named unit that registers its commands and listeners and has start/stop hooks; discovery varies. Frameworks that discover (BotCommands scanning, Red's stored names, Kord's PF4J directory) do so because their users drop in third-party code. Here the application author lists plugins in code, which the Ktor idiom and Kord's `add(::X)` already cover.

**Discovery options.**

- *In code (chosen).* Types are checked at compile time; a plugin that needs providers or a config value takes them as constructor arguments (`install(DotaPlugin(openDota))`), which `ServiceLoader` cannot do because providers need a no-argument constructor or a static `provider()` [C12][C17]. Order is the application's order, so duplicate ids and `dependsOn` are validated, not discovered.
- *`ServiceLoader` (rejected).* "Service providers are loaded and instantiated lazily, that is, on demand", in classpath order, and `ServiceConfigurationError` surfaces at iteration time [C17]. The decisive problems for this library: (1) the `bottools` umbrella and `bottools-plugins` put every plugin on the classpath, so discovery would install all of them and, because intents are derived from installs, would enable privileged intents (`GUILD_MEMBERS` for reaction-role joins) as a side effect of adding a dependency; (2) fat jars need the service files merged (Shadow documents `mergeServiceFiles()`) or one provider list silently wins [C17]; (3) it is exactly the implicit wiring (classpath scan, Spring XML) the rebuild removes. If third-party drop-in plugins are ever wanted, an opt-in `discoverPlugins()` on the builder is additive.
- *Named in configuration (rejected as a library feature).* Red's stored package list works because Red loads modules by name at runtime. A JVM library needs a name-to-factory map, which is application code. MagicBot installs every plugin the library ships; a deployment that wants fewer lists ids in its own configuration and its own `when`.

**Plugin contract (Inference).** A plugin is a value with an id and an `install` block that records contributions into a builder; nothing connects during install. Contributions: command tree fragments, typed handlers, job specs, settings, requirements, `onReady`/`onStop` hooks, `dependsOn`, and a user-data erasure function. Red makes erasure a required override on every cog; the delete-my-data command needs the same guarantee, so the bottools plugin interface requires it, with a default that erases the plugin's private key-value rows through the storage port (plugins that keep data elsewhere override it) and a guild-removal counterpart. Install failures (duplicate id, unmet dependency, invalid declaration) are collected and returned as one failed `Result` before login; unlike Red, which tolerates a broken package because its packages are third-party and hot-loaded, a bot whose author lists its plugins in code should fail fast: intents derive from the installed set, so a half-installed set is a half-explained one.

**Per-guild enable/disable (Inference).** Stored as a guild setting `plugin.<id>.enabled`, default on, read through a gate in the router (before each handler of that plugin) and in command resolution (typed rejection and help filtering). Slash registration is global, so a disabled plugin's slash commands are still listed in that guild and answer "disabled on this server". The gate caches the per-guild disabled set in memory, loaded lazily through the settings port on a limited IO dispatcher and invalidated on write, so the hot path never touches SQLite. Events with no guild (DMs) pass the gate when the handler declares itself guild-agnostic. Guild id extraction is one `when` over JDA's `GenericGuildEvent`, `GenericInteractionCreateEvent` and `GenericMessageEvent`/reaction interfaces; unknown event types are treated as unscoped.

**Declared needs (Practice).** Kord Extensions (which unions each extension's recorded `Extension.intents`) and BotCommands (which checks listeners against the granted intents) both let features state needs that the host acts on; the bottools plugin states them as data: `requires { intent(…); cacheFlag(…); memberCache(policy); chunking(…) }` for what events cannot express, and a `Required` or `Optional(feature)` marker. The reaction-role plugin declares its join feature (welcome message, default role) as a separate optional feature, since it is the only 1.0.0 feature that needs a privileged intent (`GUILD_MEMBERS`; see `discord-platform-rules.md` §3.4).

### F4. Scheduled jobs

**What the comparable systems offer.**

- *discord.py `ext.tasks.Loop` (Practice).* A sequential loop with `before_loop` (typically `wait_until_ready`), `after_loop`, `error`, and `reconnect=True` documented as "using an exponential back-off algorithm"; `ExponentialBackoff` returns a uniform random delay up to `base * 2^exp` with exponent capped at 10 and reset after a quiet period [C15]. Retried exceptions are limited to a list of transport errors, so a logic bug stops the loop and calls `error`. No persistence: after a restart the loop starts again from zero.
- *Quartz 2.5.2 (2025-12-01) (Practice).* The only candidate with misfire and persistence, and its own docs state the hazard of replaying: with `MISFIRE_INSTRUCTION_IGNORE_MISFIRE_POLICY` "a SimpleTrigger that fires every 15 seconds which has misfired for 5 minutes will fire 20 times once it gets the chance to fire" [C18]. It runs blocking `Job.execute` on its own thread pool, persists through its own JDBC schema (the repository's `jdbcjobstore` resource directory ships DDL for Derby, H2, MySQL and PostgreSQL, and no file for SQLite; the Quartz documentation host was unreachable, so its list of supported databases is unverified), and would duplicate the storage ports. Rejected.
- *krontab 3.1.0 (2026-10-09).* Cron syntax and a DSL for coroutine tasks (`doInfinity`); the README is about launching "things from time to time according to some schedule" and says nothing about persistence or missed runs [C19]. Its module requires `kotlinx-coroutines-core` 1.11.0, `kotlinx-serialization-core` and `korlibs-time`. It only computes times. Rejected.
- *cron-utils 9.2.1 (2023-03-26).* Parsing and next-execution computation; not maintained recently, no scheduling or persistence. Rejected.

**Design that falls out (Inference, with the above as support).**

- A job is an immutable spec: stable `JobId`, a `Schedule` (sealed: `Every(interval, jitterFraction)`, `DailyAt(time, zone)`), `timeout`, a backoff policy, and `suspend JobContext.() -> JobOutcome`. `Every` is fixed-delay from completion, so a long run never queues a burst.
- Persisted `JobState` (one row per job through a `JobStateStore` port): `nextDueAt`, `lastStartedAt`, `lastSucceededAt`, `consecutiveFailures`, and an optional opaque `cursor` for jobs with one global position (the patch-notes feed). Per-subject positions (the last match posted for each subscription) belong to the owning feature's tables, updated after each successful post, because the tracker's unit of delivery is the subscription, not the tick.
- **Misfire policy: one run now, never a replay.** On start, a job whose `nextDueAt` has passed runs once after a startup jitter (so a restart does not fire every job at the same second), then reschedules from completion. Polling jobs read "everything since the cursor", so catching up is a property of the cursor, not of replayed ticks. Quartz's own text shows what replaying costs.
- **Failure handling.** The loop is sequential and single-flight. Each iteration catches `Exception` (never swallowing `CancellationException`, and converting only its own `TimeoutCancellationException`), records the failure in `JobState`, and waits a full-jitter exponential delay capped at the interval; success resets it. A provider's rate-limit answer maps to a `RetryAfter(duration)` outcome. The first failure and the crossing of a threshold log at WARN once (`job.degraded`), later failures at DEBUG, so a down provider does not flood logs. The loop never exits on its own.
- **At-least-once, therefore idempotent.** State is written after an iteration; a crash mid-iteration repeats it. Delivery to a channel must tolerate repeats: write the per-subscription cursor immediately after each successful post, and pass a deterministic nonce (at most 25 characters, `Message.MAX_NONCE_LENGTH`) built from subscription and match. JDA already sets `enforce_nonce` to true and Discord rejects a second message with the same nonce from the same author "in the past few minutes" [C20]. That covers a fast restart only; it is a mitigation, not a guarantee.
- **Bot-level, not shard-level.** Jobs hang off the library scope, not off any `JDA`. They resolve guilds and channels through the shard manager (`getGuildById`, `getGuildChannelById`) at post time; a subscription whose guild is not currently on a running shard is skipped and retried next tick, and a subscription that returns repeated `MISSING_ACCESS` / `UNKNOWN_CHANNEL` is marked unhealthy and paused (see `discord-platform-rules.md` §3.7). Posting once per guild follows from iterating subscriptions, which are keyed by guild.
- **Between processes.** SQLite is single-host, so 1.0.0 is one process with N shards. A process started with a shard range (below) must not also run bot-level jobs: a configuration flag `jobs.enabled` names the one process that does, which should be the one owning shard 0 because guild-less events (direct messages) go only there. No distributed lease is designed.
- **Clock.** Wall-clock state uses `java.time.Instant` and `InstantSource` (JDK 17+), injected for tests. `kotlin.time.Clock` and `Instant` are only stabilised in Kotlin 2.3.0 [C21], so on the 2.2.x toolchain they would need an opt-in in a public signature.

### F5. Configuration

**Options.**

- *Hoplite 3.0.4 (2026-10-16).* Strong ergonomics and a `ConfigResult` validation monad from `loadConfig<T>` [C22]. Costs for a library on every consumer's runtime: a compile dependency on `kotlin-reflect` 2.2.21 and on `kotlinx-coroutines-core-jvm`/`-jdk8` 1.6.4 (older than the 1.10.2 the rest of the stack uses) [C22]; four sources registered by default, including `~/.userconfig.[ext]` and the XDG config directory, so a public bot's behaviour could change because of a file in the host user's home [C22]; a `Masked` string type for secrets [C22]. Fine for an application, heavy for a library.
- *Lightbend Config 1.4.9 (2026-06-03).* "implemented in plain Java with no dependencies"; HOCON with environment substitution [C23]. Untyped getters that throw `ConfigException`; typed mapping would be hand-written.
- *kotlinx-serialization formats.* `kotlinx-serialization-hocon` 1.12.0 and `kaml` 1.12.0 exist on Maven Central (2026-10-19); they would add the serialization compiler plugin and `@Serializable` annotations to `BotConfig` and a format library to every consumer. Not evaluated further; see Gaps.
- *JDK only.* `System.getenv()` plus `java.util.Properties`.

**Shape.** The runtime's configuration is small and flat: token, sharding, allowed privileged intents, shutdown timeouts, ready timeout, command-registration scope, whether this process runs jobs. A typed `BotConfig` is built by a builder in code and by `BotConfig.load(environment, file)`, which reads keys from the environment and an optional properties file and returns `Result<BotConfig>` whose failure carries every problem (`key`, `message`), not the first. Unknown keys under the library prefix are reported as warnings (typos). Plugin and provider needs are constructor arguments; guild settings are a different thing (stored, per guild, edited through the admin plugin).

**Secrets.** Use the common `NAME` / `NAME_FILE` convention: if `…_TOKEN_FILE` is set, read that file (trim a trailing newline) and fail if it is unreadable or empty; otherwise use `…_TOKEN`; the properties file may not carry the token. It is the Docker-image convention for secrets mounted as files ("`_FILE` may be appended to some of the previously listed environment variables … load passwords from Docker secrets stored in `/run/secrets/<secret_name>`") [C24]; no container is assumed, it is simply a path outside the repository. Kord Extensions' `env(name)` reads a `.env` file in the working directory (loaded once, on first use) before the process environment and throws when the variable is missing [C11]. Values are wrapped in a `Secret` whose `toString` is masked, like Hoplite's `Masked`; the token is never logged, and the `config.loaded` event lists keys and sources, not values.

**Validation that belongs to startup.** Token present; `sharding.total` null (recommended count) or positive; a shard range requires an explicit total, because JDA's `setShards` "does not have any effect if the total shard count is set to -1" [C7], and the range must lie inside the total (JDA checks `id < shardsTotal` at call time, so total must be set first); timeouts positive; privileged-intent allowances are known enum names. JDA's `build()` throws `InvalidTokenException` and `IllegalArgumentException` synchronously, because `login()` builds the first shard on the calling thread [C3]; those become a typed login failure in the same `Result`.

### F6. Sharding

- **`ShardManager` always, no shard abstraction of the library's own.** One code path serves 1 and N shards; `shardsTotal = -1` is JDA's default and fetches Discord's recommended count (`discord-platform-rules.md` §3.8). Sharding is required at 2,500 guilds and each shard serves at most 2,500; discord.py's `AutoShardedClient` is documented for "at least 1000 guilds" [C15], a hint for when MagicBot's configuration matters, not a rule. Behind the runtime sits one small internal `Gateway` port (guild and channel lookup, message posting, shard statuses) implemented over `ShardManager`, so jobs and the dispatcher are testable without JDA classes. `ShardManager` itself is a wide interface of mostly-default methods whose custom implementations "may not support all methods" [C12], which makes it a poor test-double target.
- **One router, many managers.** Each shard has its own `JDA` and its own event manager; all are constructed over the same handler scope and carry the same router instance (F1). Handlers therefore run concurrently across shards and must not keep per-shard state. Logging context carries `shard` and `guild`.
- **Ready is a bot-level fact.** `ReadyEvent` fires per shard and `ShardManager` has no await-ready; only `JDA.awaitReady` per shard exists (Measured, `ShardManager` has no `await*` method at `v6.7.0`). The runtime counts distinct shard ids that raised `ReadyEvent` against `shardManager.getShardsTotal()` (queued plus running) and emits `bot.ready` once, with a configured timeout. A later shard restart raises a new `ReadyEvent` but not a second `bot.ready`. This count-equals-total rule is Inference and needs a spike. Everything that must happen once (command registration, plugin `onReady` hooks, jobs, the legacy import) hangs off `bot.ready`, never off `ReadyEvent`.
- **Command registration once.** One REST call through any running shard (`JDA.updateCommands()`), hash-skipped when unchanged, after `bot.ready`. `retrieveApplicationInfo` follows the same pick-any-shard rule (JDA documents that it picks the call from any shard because the result is identical) [C3].
- **Multi-process.** `setShards(min, max)` with an explicit total runs a subset per process (`discord-platform-rules.md` §3.8). The runtime's `sharding.range` maps to it. Out of scope for 1.0.0 beyond validation: SQLite is single-host, and bot-level jobs are pinned to one process by `jobs.enabled`.
- **Unexpected shard loss.** `DefaultShardManager` shuts itself down when a later shard hits `InvalidTokenException` ("the ShardManager will shutdown!") [C3], and a 4014 close is non-reconnecting [C8]. The router also observes `ShutdownEvent` from shards the library did not stop and moves lifecycle state to `Failed`, with the shard id and close code in the log event.

### F7. Lifecycle, shutdown and error isolation

- **JDA shutdown semantics (Measured).** `JDA.shutdown()`: "Already enqueued RestActions are still going to be executed"; `shutdownNow()` cancels them [C9]. `DefaultShardManager.shutdown()` runs per-shard `shutdown()` asynchronously on its own executor and returns; there is no await on `ShardManager`, only `JDA.awaitShutdown(long, TimeUnit)` and a `Duration` overload per shard [C9]. Capture the shard list before shutting down. The builder installs a JVM shutdown hook by default [C10]; the library turns it off (`setEnableShutdownHook(false)`) so the order below is not preempted.
- **Draining needs the gateway still up.** An in-flight handler's reply is a REST call. If `JDA.shutdown()` came first, a handler would race a closing client. This ordering is Inference: the effect of calling a `RestAction` after shutdown is not established (Gaps). BotCommands does the reverse (shuts JDA first, waits for all shards' `ShutdownEvent`, dispatches its own shutdown event, and shuts its coroutine pools last: "Shutdown the pools *after* dispatching") [C13]; that suits a framework whose services use shard events at shutdown. Ktor's two-phase stop (`shutdownGracePeriod` default 1000 ms, then `shutdownTimeout` default 5000 ms) is the closest precedent for grace then hard stop [C16].
- **Scope structure (Inference).** `botJob = SupervisorJob(parent from the injected context)`; two children of it, `handlerJob = SupervisorJob(botJob)` (the scope given to every event manager) and `jobsJob = SupervisorJob(botJob)` (jobs). Draining is "close intake, then join `handlerJob.children` under a timeout"; `Job.children` is public API and "Parent cannot complete until all its children are complete" [C5]. `coroutineScope`/`supervisorScope` inside the router make each event's coroutine wait for all its handlers, so the event coroutine is the unit of drain. KDoc: "The key part of custom usage of `CoroutineScope` is cancelling it at the end of the lifecycle." [C5]
- **Named lifecycle events (Inference).** slf4j 2's fluent API (`atInfo().addKeyValue("shard", id).log("shard.ready")`, `LoggingEventBuilder.addKeyValue`) [C25] carries structured fields without a logging backend in the library. A closed internal list: `config.loaded`, `config.invalid`, `storage.opened`, `plugin.installed`, `plugin.failed`, `intents.resolved`, `gateway.connecting`, `shard.ready`, `bot.ready`, `commands.registered` / `commands.unchanged`, `job.started`, `job.degraded`, `job.recovered`, `bot.stopping`, `handlers.drained`, `scopes.cancelled`, `gateway.closed`, `storage.closed`, `bot.stopped`, `bot.failed`.
- **Status that falls out.** The sequence is a state machine: `Created → Starting(phase) → Ready → Stopping → Stopped | Failed(cause)`, held in a `StateFlow` the runtime needs anyway for `awaitReady` and for the idempotent `stop`. BotCommands exposes the same idea publicly as `BContext.Status` and `BStatusChangeEvent` [C13]. Here it stays `internal`, with at most an accessor behind the Experimental marker. Per-job status is the persisted `JobState` and needs no extra surface.

## 4. How comparable projects do it

- **BotCommands `v3.4.0` (`c23a9e4`).** Services are discovered by scanning packages added through `BConfigBuilder.addSearchPath`. The framework owns the `IEventManager`: `CoroutineEventManagerImpl` first runs annotated listeners via `EventDispatcherImpl` on the caller thread (blocking mode), then its own `launch` per event for "regular" listeners, with an optional timeout; `BCoroutineScopesConfig` supplies named scopes (`eventManagerScope`, `eventDispatcherScope`). `JDAService` is the single place that builds JDA (or a `ShardManager`) with `intents` and `cacheFlags` declared up front and "Starting JDA when every other service is ready". `BContext.Status` is `PRE_LOAD, LOAD, POST_LOAD, READY, SHUTTING_DOWN, SHUTDOWN`; `shutdown()` sets `SHUTTING_DOWN`, shuts JDA, and `scheduleShutdownSignal` waits for every shard's `ShutdownEvent` before dispatching `BShutdownEvent` and closing the scopes [C13]. License MPL-2.0 (see `jda-and-coroutine-bridge.md`).
- **Kord Extensions `v2.6.0` (`f86bef8`, Codeberg).** `Extension.name`/`setup()`/`unload()` and `extensions { add(::MyExtension) }`. Intents are derived from `Extension.event<T>()` registrations (`intents += fakeBuilder.build().values`) and unioned at login with the non-privileged base. Sharding is configured as `sharding { recommended -> Shards(recommended) }` and handed to Kord's builder ("shard your bot across multiple `Gateway` objects in a single process"). PF4J plugins load from `./plugins` by default through `ExtensibleBotBuilder.loadPlugins`: `PluginManager` extends PF4J's `DefaultPluginManager` with a `PropertiesPluginDescriptorFinder`, a plugin is a `KordExPlugin` whose `extension { }` registrations become extensions and whose `settings { }` callbacks mutate the bot builder, and the whole mechanism switches off with `pluginBuilder.enabled = false` [C11]. The scheduler (`Scheduler`, `Task`) is an in-memory, polling, delay-from-start scheduler on `Dispatchers.Default + SupervisorJob()`: `schedule(delay, pollingSeconds = 1, repeat)` wakes every `pollingSeconds` to compare a monotonic elapsed time with the delay, runs the callback, logs an exception from it, and, for a repeating task, starts the delay again after the callback returns, so the period drifts by the callback's run time; there is no cron expression, no persistence and no catch-up of missed runs [C11].
- **Red-DiscordBot (`004a160`).** `Bot._pre_connect` loads the persisted package list, one `load_extension` per package under a 30-second `asyncio.wait_for`, logging and dropping any that fail; `Cog.red_delete_data_for_user(requester, user_id)` is documented as required for every cog [C14].
- **discord.py `v2.7.1`.** `ext.tasks.Loop` with `ExponentialBackoff`; `Cog.cog_load`/`cog_unload`; `AutoShardedClient(shard_ids=…, shard_count=…)` where `shard_count` "must be provided" with `shard_ids` [C15].
- **Ktor `3.6.0`.** `Plugin<TPipeline, TConfiguration, TPlugin>.install(pipeline, configure)` and two-phase `EmbeddedServer.stop(gracePeriodMillis, timeoutMillis)` [C16].
- **This repository.** `Bot` initialises everything inside a static initialiser; `Responder` reflects over every JDA event class at construction and invokes handlers on JDA's thread with no per-handler isolation (one exception in `forEach` skips the remaining handlers for that event); `CheckValueService` and `CentralProcess` are raw threads. GKB2 adds Spring and `plugins.xml`, with `Plugin` lambdas that mutate a static `responder`. None of these has a stop path other than `Bot.stop()` (JDA shutdown plus a console thread).

## 5. Pitfalls and regrets

1. **`injectKTX()` on a `DefaultShardManagerBuilder` looks like the supported path and defeats ownership.** One unowned default scope per shard; nothing cancels them when the library closes. Use the constructor with the library scope.
2. **JDA's `create(token, intents)` re-enables member caching.** With `GUILD_MEMBERS` it chooses `MemberCachePolicy.ALL` and `ChunkingFilter.ALL`. Set both explicitly after it. `build()` also throws on `ALL` without the intent.
3. **A forced scope cancel produces ERROR log lines from jda-ktx.** Its `catch (ex: Exception)` catches `CancellationException` and logs "Uncaught exception in event listener". Cosmetic, bounded by grace and the number of stuck handlers. If it matters, the router is the only listener, so replacing the manager with a roughly 40-line `IEventManager` (BotCommands' route) is a single-class change.
4. **Losing event order.** A coroutine per event removes JDA's per-shard ordering. Handlers must be idempotent against stored state.
5. **Intents silently widened by a handler type.** `fromEvents` is conservative: a `GenericMessageEvent` handler asks for both guild and DM message intents, and guild message intents deliver an event for every message in every guild. Register the narrowest event type, and filter mentions early.
6. **Registering from `ReadyEvent`.** It fires per shard, again on shard restart, and was the trap in the old one-JDA code; hang once-only work off `bot.ready`.
7. **Replaying missed ticks.** Quartz's own documentation shows 20 fires after five minutes of downtime under the ignore policy. A cursor-based "since last seen" read avoids it.
8. **A job that exits on its first exception.** `CheckValueService.run` does exactly this today. Every iteration catches `Exception`; only `VirtualMachineError` and cancellation escape.
9. **Treating `withTimeout` as just another cancellation.** `TimeoutCancellationException` is a `CancellationException`; a blanket rethrow turns a provider timeout into a silently killed handler, and a blanket catch swallows real shutdown. Catch it inside the `withTimeout` block and check `ensureActive()`.
10. **ServiceLoader and `kotlin-reflect` weight on consumers.** Both appear tempting for "no wiring" and both change what is on every consumer's runtime or what gets enabled by adding a dependency.
11. **The token in a properties file or a logged config dump.** Keep the token out of the file source and out of `toString`.
12. **Login retry loops.** A crash-restart loop spends the 1,000 Identify calls per 24 hours (`discord-platform-rules.md` §3.8). The runtime fails fast with a classified error and leaves restart policy to the host; it does not retry login in-process.
13. **Shard counts that change.** JDA fixes the total at login; growth past the recommended count needs a restart (`discord-platform-rules.md` §3.8). Document it; do not build resharding.

## 6. Recommendation for this repo

Build `bottools-core`'s runtime as the following internal components, with public surface owned by the API-shape research (names are illustrative). Reject the obvious "JDA listener + `ListenerAdapter` per feature" and "ServiceLoader plus Hoplite" because they reproduce the implicit wiring and widen what a dependency does.

**Startup (each step a named log event; a failure before step 6 returns `Result.failure` with every problem, closes what was opened in reverse, and connects nothing):**

1. Load and validate `BotConfig` (F5).
2. Open storage through the ports, migrate.
3. Install plugins in declared order: validate ids and `dependsOn`, collect handlers, commands, jobs, settings and requirements; freeze the registry snapshot.
4. Resolve gateway needs: `fromEvents(handler types) ∪ fromCacheFlags ∪ declared`; add `MESSAGE_CONTENT` only if the bare-prefix mode is configured and allowed; compare privileged intents with the allowance, switching optional features off or failing on required ones; build the command registration payload and validate it (`discord-platform-rules.md` §6).
5. Create `botJob`, `handlerJob`, `jobsJob`; the dispatcher and `Dispatchers.Default` come from the injected context.
6. Build `DefaultShardManagerBuilder` (not `createDefault`): intents, cache flags, `MemberCachePolicy` = OR of declared policies (default `NONE`), `ChunkingFilter.NONE` unless a feature declared chunking, `setEnableShutdownHook(false)`, `setShardsTotal(total ?: -1)` before `setShards(range)`, `setEventManagerProvider { CoroutineEventManager(handlerScope, INFINITE) }`, `addEventListeners(router)`. `build()` returns after the first shard is built on the calling thread, so token errors are caught here.
7. Wait for all shards' `ReadyEvent` (count vs `getShardsTotal()`), with a timeout; emit `bot.ready`.
8. Register commands (hash-skip). Run plugin `onReady` hooks once. Start jobs with startup jitter, if `jobs.enabled`.

**Stop (idempotent `stop()`, also what `close()` calls; no JDA shutdown hook):**

1. `Stopping`: the router closes intake (new events are dropped and counted, one log line).
2. Cancel `jobsJob` and join it within the grace period; iterations are cancellable and idempotent.
3. Drain: join `handlerJob.children` within `shutdown.grace` (proposal: 10 s).
4. Plugin `onStop` hooks in reverse install order, each bounded; a failing hook is logged and does not stop the rest.
5. Cancel `handlerJob` and `botJob`; join within `shutdown.cancelTimeout` (proposal: 5 s).
6. `ShardManager.shutdown()`; `awaitShutdown(shutdown.jdaTimeout)` on each shard captured beforehand (proposal: 10 s); `shutdownNow()` on stragglers.
7. Close storage and library-created executors, in reverse of opening. `Stopped`.

**Components.**

- `EventRegistry` (immutable snapshot, per-class resolved lists), `EventRouter` (the only listener; intake flag; guild gate; `supervisorScope` fan-out; per-handler timeout and isolation).
- `PluginHost` (install, ordering, hooks, `eraseUserData`/`eraseGuildData` fan-out); `GuildFeatureGate`.
- `JobRunner` per spec under `jobsJob`; `JobStateStore` port with `JobState` (F4) for the storage research to implement.
- `BotConfig` loader and `Secret`; `GatewayResolver` (intents, caches, member policy); `Gateway` port with a `ShardManager` implementation; `Lifecycle` (state flow, ready counter, named events).

**Reasoning.** The router-over-one-listener shape keeps jda-ktx to the single role it was settled for (get off the gateway thread, give the library the scope), puts all isolation and gating in one tested class, and makes swapping the manager a one-class change. In-code plugin installation is the only discovery mechanism under which the intent union is exact and visible to the application author. Persisted fixed-delay jobs with a cursor give restart safety without a second persistence system. A dependency-free config loader returning `Result` fits the organisation's rule and the lean-classpath requirement, and costs about a hundred lines.

**Rejected:** SharedFlow dispatch; `injectKTX()` on the shard manager builder; `ServiceLoader`; plugin names in library configuration; Quartz, krontab, cron-utils; Hoplite and Lightbend Config inside `bottools-core`; an own `Shard` abstraction; in-process login retry; automatic circuit-breaking of plugins (hidden state; the per-guild gate and logs are the control).

**Not run (all behaviour is read from source, nothing was built or executed).** A one-module spike under Kotlin 2.2.0 should settle:

- `CoroutineEventManager(scope = handlerScope)` per shard through `setEventManagerProvider` with `addEventListeners(router)`, including that a shard created or restarted later gets the same router; and the forced-cancel log noise.
- The all-shards-ready rule (distinct `ReadyEvent` shard ids equal `getShardsTotal()`), including a shard restart. The rule is my inference.

**Open choices, with a recommendation each (not blockers).**

- *Privileged intent not allowed:* optional features switch off with a named log event; required features fail startup. Recommended default for the reaction-role join feature: optional.
- *Plugin install failure:* fail startup with all problems (recommended) versus isolate the plugin as Red does. Failing fast is chosen because plugins are listed in code.
- *Multi-process deployments:* validated in configuration but not supported beyond pinning bot-level jobs to one process, because the storage target is single-host SQLite. A shared-store lease would be a later, additive design.
- *Event ordering:* none guaranteed; a keyed serial lane is available per handler. Whether reaction roles needs it is decided when that plugin is written.
- *`ServiceLoader` as an opt-in later:* not rejected forever, only not the default; decide if third-party drop-in plugins ever appear.
- *Where `JobStateStore` and the plugin key-value store are specified:* the storage research owns the ports; this document only states the fields the scheduler needs.
