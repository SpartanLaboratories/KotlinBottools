## 1. Question

How do established Discord bot frameworks give one command both a slash form and a typed (prefix or mention) form, and what should `bottools-core`'s command model take from them? The model must meet these facts about the work:

- Definitions are immutable, and one definition serves many concurrent invocations through a per-invocation context.
- Slash is primary; the typed form reaches the same handler. The typed form is always available by @-mention and in DMs, and the bare `!` prefix in guild channels is an opt-in mode that needs the privileged `MESSAGE_CONTENT` intent.
- Context-menu commands are supported. Help is generated from the tree.
- The alias DSL (`get and "city" becomes "getcity"`) and the Dota 2 names `setid`, `getid`, `lastgame`, `showstats` survive as typed aliases of new canonical paths.
- Discord's command limits apply when the tree becomes slash registrations.

## 2. Bottom line

- **Only discord.py unifies the two forms behind one handler and one context.** Sapphire, BotCommands, JDA-Chewtils and Kord Extensions share at most the class (Sapphire), the argument schema (Kord) or nothing (BotCommands, Chewtils), and give the handler a different event type per form. DIH4JDA has no typed form at all. The library's goal is therefore discord.py's shape (one callback, one context), built on an option schema that is declared once and used by three consumers: the slash registration, the typed parser and the help renderer.
- **Every framework that unifies even partly pays for it with a second dispatch pipeline that drifts.** discord.py re-implements its check order for the slash side, and its issue tracker holds closed reports of checks and hooks behaving differently between the two forms. BotCommands compiles each text command into a regex and refuses commands it deems "too complex". The model should have one dispatcher: normalise any invocation to a `CommandContext`, then run path resolution, argument binding, preconditions, handler and error presentation once.
- **Typed-only aliases are universal, and none of the six frameworks maps a multi-token alias to a different path.** discord.py, Kord Extensions and BotCommands register aliases for typed dispatch only; Sapphire has no slash alias. The relation the alias DSL needs (`[get, city]` is an alias of `[getcity]`) has no prior art, so the library has to build a path-alias table itself. It excludes aliases from slash registration by default.
- **Typed grammar: take a pull-based binder over the declared options, not a regex.** Quote-aware tokens (including the smart-quote set), positional binding in declaration order, `name=value` and `--name value` for any option (Kord Extensions) to skip optionals, one final greedy "rest" string (discord.py, Sapphire), mentions kept as single tokens, and a sealed `ArgumentError` kept apart from its wording (Sapphire identifiers, Kord `FailureReason`, BotCommands' replaceable messages interface). Today's `Parser` lowercases the whole message and drops tokens starting with `@` or `#`, so it cannot be carried over.
- **No surveyed framework auto-defers on a timer.** discord.py, Sapphire, BotCommands, Chewtils and DIH4JDA leave `defer` to the handler. Kord Extensions removed its `autoAck` in 1.5.0 (2021) and instead declares each slash command `ephemeral` or `public` up front. A timer-driven deferral, as proposed in the platform findings, is new ground: it needs an atomic acknowledgement state in the context and the ephemerality declared on the definition (a deferral cannot change it).
- **Component handlers are routed by `custom_id` in every framework that survives restarts.** The routes are registered at startup and state lives in the id or in storage; BotCommands splits components into persistent (database-backed) and ephemeral (in-memory) lifetimes, and discord.py added regex-templated `DynamicItem` ids for state in the id. DIH4JDA's `:`-joined ids with `split(":")` show the escaping pitfall.
- **No surveyed framework ships a Discord-free test harness for handlers.** discord.py's own tests build a `MockCommandInteraction` from payload dicts; Sapphire, BotCommands, Chewtils and DIH4JDA test only parsers, resolvers and ids. A `CommandContext` interface is what makes handlers testable here.

## 3. Findings

Tiers: **Consensus** = several independent mature frameworks or a spec; **Practice** = what one or two mature libraries visibly do; **Opinion** = one source's view; **Unverified** = source unreachable. Quotes for the numbered claims are in section 7 (`[C#]`).

### F1. Definitions: what defines a command, and whether it is shared immutably

|---|---|---|---|

| Sapphire 5.5.1 | `Command` class with optional `messageRun`, `chatInputRun`, `contextMenuRun`, `registerApplicationCommands(registry)` | Class hierarchy, loaded as "pieces" from files; options built separately with discord.js builders | Yes. ### F2. One definition, two forms

- **discord.py (Practice; the only true unification).** `HybridCommand` "is both an application command and a regular text command", with the restriction that "the callbacks must have the same subset that is supported by application commands" [C2]. The signature is rewritten into slash options by `replace_parameter(s)`: converters become `ConverterTransformer`, `Greedy[T]` becomes `GreedyTransformer`, flag converters are flattened into separate options, `Range` maps to `app_commands.Range`. At invocation, a `HybridAppCommand` wraps the interaction into a `Context` and calls the same callback ("This lies and just always passes a Context instead of an Interaction", in `HybridAppCommand._invoke_with_namespace`) [C1].
  - **The typed form can do what the slash form cannot:** variable-length arguments, deeper group nesting, most `Union` annotations, converter lookup by name, and `Greedy`. The docs list the hybrid exclusions: "Variable number of arguments", "Group commands with a depth greater than 1" and most `Union` types [C3].
  - **The slash form can do what the typed form cannot:** autocomplete, choice pickers, client-side ranges, `ephemeral` replies (`Context.send` documents the flag as "only applicable in contexts with an interaction") and the 3-second ack/defer model.
  - **Groups cannot be invoked as slash commands**, so a hybrid group needs a `fallback` subcommand bound to the group's callback [C4]. The same Discord rule is why the old Dota 2 command needs a defined meaning for a bare `!dota`.
- **Sapphire (Practice).** One class, two methods: `messageRun(message, args, context)` and `chatInputRun(interaction, context)`; slash registration is a third, hand-written step, `registerApplicationCommands(registry)` [C13]. Nothing links the typed `Args` calls to the declared slash options. `supportsMessageCommands()` and `supportsChatInputCommands()` test which handlers a class has, and the typed dispatcher emits `CommandDoesNotHaveMessageCommandHandler` "maybe an application command variant exists" when the command is slash-only. Subcommands are a plugin (`@sapphire/plugin-subcommands`) that maps one subcommand name to a pair of method names (`messageRun: 'messageAdd', chatInputRun: 'chatInputAdd'`) [C16].
- **BotCommands (Practice).** Two separate declarations per command, `@JDASlashCommand` and `@JDATextCommandVariation`, with options declared twice (`@SlashOption`, `@TextOption`) and different event types (`GuildSlashEvent` vs `BaseCommandEvent`). The README example shows both for `ban` [C18]. Text commands are built from "variations": each variation has its own parameters and "the first variation that has a full match against the user input gets executed" [C20].
- **Kord Extensions (Practice, docs only).** `chatCommand(::MyArguments)` and `publicSlashCommand(::MyArguments)` take the same `Arguments` class, so one option schema feeds both parsers. Handlers differ (`ChatCommandContext` vs the slash contexts) [C28].
- **JDA-Chewtils (Practice).** `SlashCommand` extends `Command`. The slash body is `protected abstract void execute(SlashCommandEvent event)`; the typed body `execute(CommandEvent)` is overridden to do nothing, and its docs say that "Because this is a SlashCommand, this is called, but does nothing" [C26]. The typed form receives one raw argument string through `CommandEvent.getArgs()`; there is no typed-argument mapping. `buildCommandData()` produces the slash registration, including subcommand groups, `DefaultMemberPermissions`, `setNSFW`, contexts and integration types.
- **DIH4JDA (Practice).** Slash and context commands only; included as the baseline for a tree that maps directly to JDA data classes, and for component routing.

### F3. Typed-argument grammar

| Aspect | discord.py 2.7.1 | Sapphire 5.5.1 | BotCommands 3.4.0 | Kord Extensions (docs) |
|---|---|---|---|---|
| Binding | Positional, by function parameter order; keyword-only parameter takes the rest; `FlagConverter` for named | Imperative and pull-based: the handler calls `args.pick`, `args.rest`, `args.repeat`, `args.peek`; flags and options via the lexer strategy | Declared `@TextOption` parameters compiled into one regex per variation | Parsed "in the order you defined them"; keyword arguments are removed first |
| Named form | `FlagConverter` (`name: value` by default; delimiter and prefix are configurable) | `args.getFlags`, `getOption` | None | `--name value` and `name=value` [C29] |
| Quoting | `StringView` accepts `"` and 17 other open/close pairs (`“ ”`, `« »`, `「 」`…); backslash escapes | Lexer default quotes `" "`, `“ ”`, `「 」`, `« »` | `QuotableTextParameterResolver` for quotable strings when a command has more than one quotable parameter | Double-quoted values, with escaped quotes inside |
| Rest string | Keyword-only parameter, or `rest_is_raw` | `args.rest(type)` | A string option, but two strings side by side make the pattern "too complex" | Coalescing converters (consume as many tokens as possible) |
| Lists | `Greedy[T]` | `args.repeat` | `@VarArgs` | List converters (typed form only: "they can only process and return a single value" in slash) [C30] |
| Mentions and ids | Converters: `MemberConverter` tries id, mention, name#discriminator, name, global name, nickname [C5]; channel and role converters likewise | Resolvers parse mention or snowflake then fetch (`resolveUser`) | Resolver `pattern` per type; `User`, `Member`, `Role`, `GuildChannel`, `IMentionable` "only when mentioned" | Converters per entity type |
| Errors | `UserInputError` family: `MissingRequiredArgument`, `BadArgument`, `TooManyArguments`, `BadUnionArgument`, and the parsing trio `UnexpectedQuoteError`, `InvalidEndOfQuotedStringError`, `ExpectedClosingQuoteError` | `ArgumentError` extends `UserError`, with an `identifier` string (`memberError`, `userError`…); the result API is `pickResult` returning a `Result` | A resolver returns `null` on failure and the dispatcher moves to the next variation; a final miss shows help | `FailureReason`, a sealed type, passed to a replaceable `errorResponse { }` builder [C31] |

Tier: Consensus that positional-in-declaration-order with a final rest string is the core grammar; Practice for the extras. Two grammar facts matter for this repository:

- **Optionals in the middle are ambiguous for a positional binder.** `setid <id> [tagline] [person]` has two optional arguments of different types; only Kord's named form and BotCommands' backtracking over variations resolve this, at the cost of the "too complex" failure or a second syntax. Type-directed matching of the remaining tokens (a mention can only be the user option) is what today's `GameStatsCommand` does implicitly by reading `targetMember` from the message mentions.
- **Typed form for a context-menu command does not exist.** Kord's docs say context commands do not take arguments and use modals instead [C28].

### F4. Aliases and Discord's depth limit

- **discord.py:** aliases are only typed. `HybridGroup.add_command` copies `command.app_command` into the slash group by its `name`, and aliases are added only to the typed `all_commands` map (`self.all_commands[alias] = command`) [C6]. Hybrid groups are limited to one level, matching Discord: "groups can only be nested at most one level" [C6].
- **BotCommands:** a path fragment can have `aliases`: "Alternative names for this command's path fragment, **must not contain any spaces**", and the path is "limited to three components" [C21], the same limit as slash. Aliases are text-only.
- **Kord Extensions:** `aliasKey` on `chatCommand` is a translation key resolving to a comma-separated alias list; slash commands have no alias property [C28].
- **Sapphire:** `aliases` on a `Command` feed `store.aliases`, used by the typed dispatcher only; `generateDashLessAliases` and `generateUnderscoreLessAliases` derive aliases from names.
- **None** maps several typed tokens to a different command path. All aliases are single-token names for a node, so `!setid` -> `dota id set` has no precedent.

### F5. The invocation context

- **discord.py is the only framework with one context type for both forms.** `Context.send` "does one of the following: `InteractionResponse.send_message` if no response has been given; a followup message if a response has been given; regular send if the interaction has expired" [C7]. `Context.defer` defers an interaction and, in the source, "If this isn't an interaction based context then it does nothing" [C8]; the narrative docs contradict the source and say it "shows typing indicator for text commands" (the docs and the code disagree; the code is what runs). Context exposes `guild`, `author`, `channel`, `message`, `interaction`.
  - **Pitfall in its design:** for a message context menu, `Context.author` is "the author of the message being targetted", not the invoker [C9]. The invoker has to be read from `interaction.user`.
- **BotCommands:** `GlobalSlashEvent` and `GuildSlashEvent` extend JDA's `SlashCommandInteractionEvent` (plus rate-limit cancellation and localisation); text commands get `BaseCommandEvent`/`CommandEvent`. `GuildSlashEvent` proves a guild-only variant: handlers that need a non-null guild declare it in the event type.
- **Kord Extensions:** `EphemeralInteractionContext` vs `PublicInteractionContext` "provide an identical API surface", and the docs warn that mixing response types "after you make an initial response" gives unexpected results [C32]. The ephemeral/public choice is part of the command declaration.
- **Sapphire, Chewtils, DIH4JDA:** the handler receives the raw library event; there is no wrapper.

### F6. Acknowledgement and deferral

- discord.py: manual `ctx.defer(ephemeral=…)`; `ctx.typing()` becomes a `defer` in interaction contexts (`DeferTyping`). No timer.
- Sapphire: for typed commands, a typing indicator (`channel.sendTyping()`) is sent before the run when the client option `typing` is enabled (the listener defaults it to off); `Command.typing` overrides it per command. Slash is manual.
- BotCommands 3.4.0: I found no automatic deferral in `BotCommands-core` source (the only `defer` mentions are in localisation, pagination and the event dispatcher). The slash events extend JDA's, so `deferReply` is manual.
- Kord Extensions: slash commands no longer have `autoAck` since 1.5.0 (Sept 2021); the replacement is the `initialResponse` DSL or editing the acknowledged response [C33]. Component builders have `deferredAck`, default true.
- Chewtils and DIH4JDA: manual; no `deferReply` appears in their sources.
- **No framework runs a "defer if the handler has not replied by 2 seconds" timer.** That design (platform findings, section 6.5) is original. It is sound only if the context owns an atomic acknowledgement state; see the recommendation. Because Discord fixes ephemerality at deferral, the Kord split (declare `public` or `ephemeral` on the definition) is the part to take.

### F7. Preconditions, permissions, per-guild enablement

- **discord.py:** `has_permissions`, `guild_only`, cooldowns, `max_concurrency`, bot-wide `Bot.check`. For hybrids the order is spelled out in `HybridAppCommand._check_can_run` ("Bot global check once … Local command checks") [C10]; maintainers closed as "as designed" that group checks are not inherited by hybrid subcommands (issue #8437), and fixed a bug where `after_invoke` ran for slash invocations of a command whose `before_invoke` had aborted it (issue #8276) (both summarised by the fetch tool, not quoted; see Gaps).
- **Sapphire:** `preconditions`, `requiredUserPermissions`, `requiredClientPermissions`, `runIn`, `nsfw`, `cooldown*`, with `PreconditionContainerArray` composing AND/OR. Denials are events (`messageCommandDenied`), not replies.
- **BotCommands:** `@UserPermissions` and `@BotPermissions` apply to "this text / application command" [C22]; `@Filter` takes a `TextCommandFilter` or `ApplicationCommandFilter`; `@RateLimit`/`@Cooldown`; `@RequireOwner` and `@NSFW` for text. A single `TextPrefixSupplier` returning an empty list disables typed commands in a guild [C23].
- **Kord Extensions:** `check { … }` blocks per command and per command type; `requirePermission` only sets Discord's default permission and "Kord Extensions doesn't enforce the permissions you specify here", because staff can change them [C34]. This is the same conclusion as the platform findings.
- **Chewtils:** the same permission and role checks are written twice (`Command.run` and `SlashCommand.run`), each with hard-coded user-facing strings.
- Per-guild enable/disable is a precondition or filter in every framework (BotCommands' filters and prefix supplier, Sapphire preconditions, Kord checks, Chewtils `GuildSettingsManager`), not a re-registration.

### F8. Error handling and presentation

- Sapphire separates identifiers from wording: `UserError` carries an `identifier`; `ArgumentError` adds `argument` and `parameter`; denials and errors are events that user code answers. Default replies exist only for the listeners a bot installs.
- BotCommands has one replaceable interface for framework messages, `BotCommandsMessages` (`uncaughtException`, `missingUserPermissions`, `userRateLimited`, `commandNotFound(event, suggestions)`, `resolverUserNotFound`, `componentExpired`, `modalExpired`…) produced by a `BotCommandsMessagesFactory` [C24].
- Kord Extensions has `errorResponse { message, type -> … }` with a sealed `FailureReason` [C31].
- discord.py routes everything to `on_command_error` / `Command.error`, with `HybridCommandError` wrapping app-command errors so that the text handlers see one error family (issue #9205 reports the traceback missing there).
- DIH4JDA fires `onCommandException`, `onComponentException`, `onAutoCompleteException`, `InsufficientPermissionsEvent`, `CommandCooldownEvent` on a listener interface `DIH4JDAEventListener`.

Tier: Consensus that failures are data (sealed type or identifier) separated from a replaceable presentation.

### F9. Generated help

- discord.py: `Command.brief`, `help` (docstring), `usage`, and `Command.signature`, "a POSIX-like signature useful for help command output" [C11], generated from the parameters (`<required>`, `[optional]`, `[attachment (upload a file)]`, `"a"|"b"` for literals) [C11].
- BotCommands: a built-in help command and "help content" when a command is misused; each variation "will display separately in the built-in help content"; `usePingAsPrefix` and `TextPrefixSupplier.getPreferredPrefix` feed the example prefix; `showSuggestions` defaults true.
- Kord Extensions: `getSignature` "usually generated by the chat command parser, but you can provide one manually"; a `help { }` extension replaceable through `HelpProvider`.
- Sapphire: `description` and `detailedDescription` are hand-written; no generated usage, since typed arguments are not declared.
- Chewtils: `help` string plus a hand-written `arguments` string.

Tier: Consensus that usage lines come from the declared options and that a brief description and a detailed description are separate fields. GKB2 already has `brief`/`details`.

### F10. Components (buttons, selects, modals)

- **discord.py:** `View` has `timeout=180.0` by default and callbacks in memory; a view is persistent only when every item has a `custom_id` and `timeout` is `None`, and it must be re-registered at start-up with `Client.add_view` [C12]. Since 2.4 `DynamicItem` stores state in the id itself, parsed with a regex template [C12].
- **Sapphire:** `InteractionHandler` pieces typed Button, SelectMenu, ModalSubmit, MessageComponent or Autocomplete; the `parse(interaction)` hook decides whether a handler applies and can load data by id, returning `Option`'s `some(data)` or `none()` [C14].
- **BotCommands:** persistent components ("Database-backed components, can be used with callbacks, or bound to a method, optionally with passed data") with a handler bound by name (`@JDAButtonListener`), and ephemeral components kept in memory (`LifetimeType.PERSISTENT` / `EPHEMERAL`); expired ones answer with `componentExpired` [C24, C25].
- **DIH4JDA:** a handler interface (`ButtonHandler.handleButton`) registered with `IdMapping.of(handler, "prefix")`; ids built by `ComponentIdBuilder.build(identifier, args…)` joined with `defaultSeparator = ":"` and split with `split` [C27].
- **Kord Extensions:** components are centralised; persistence across restarts is not described in the pages I read (Unverified).

### F11. Testing without Discord

- discord.py is the only framework that tests invocation: `tests/test_app_commands_invoke.py` defines `MockCommandInteraction(discord.Interaction)` and builds option payloads from keyword arguments [C15].
- Sapphire's `tests/` cover application-command diffing, flags, precondition resolvers and resolvers; BotCommands' tests cover resolvers, components against H2, architecture rules; DIH4JDA tests `ComponentIdBuilder`; Chewtils has no tests. None tests a handler through a fake context.
- Kord Extensions' documentation has no testing page.

Prefix and mention policy, the split this library has to implement:

- **Sapphire:** mention prefix is on by default (`disableMentionPrefix` switches it off), checked before the configured prefix; a message that is only the mention emits `MentionPrefixOnly`; `fetchPrefix(message)` is the per-guild hook and may return a list, a string or `null` [C17].
- **BotCommands:** `usePingAsPrefix` defaults to `false`; `TextPrefixSupplier.getPrefixes(channel)` overrides everything per guild and "Returning an empty list means the bot will not respond to commands in that guild" [C23].
- **Kord Extensions:** chat commands are off by default; `defaultPrefix = "!"`, `invokeOnMention = true`; `prefix { }` is the per-context callback. Its pages state "Chat commands require the "message content" privileged intent", a blanket statement that is more conservative than the platform rule in `discord-platform-rules.md` (mention messages arrive with content) [C28].
- **discord.py:** `when_mentioned_or(*prefixes)` as a prefix callable (from the platform findings).

None of them models "mention and DM always, bare prefix only if the deployment holds the intent" as a first-class setting. All of them let the prefix be a per-message callback, which is the extension point to copy.

## 5. Pitfalls & regrets

- **Two pipelines for one definition drift.** discord.py's hybrid commands re-implement the check ordering (`_check_can_run`), the hook calls and error wrapping (`HybridCommandError`); the closed issues #8276 (hooks ran differently) and #8437 (parent checks not applied to hybrid subcommands) show it. Sapphire's `CommandDoesNotHaveMessageCommandHandler` and Chewtils' empty `execute(CommandEvent)` show the other failure: a command that silently has only one form.
- **Subset-of-both.** Hybrid commands can only use what slash supports, and discord.py's docs list what that costs (no varargs, no group depth above one, no most unions). Decide per option which features degrade in typed form (choices become validated tokens; autocomplete does not exist) rather than shrinking the typed form to the slash subset.
- **Regex-compiled grammars.** BotCommands builds one regex per variation and throws "Failed building text command pattern … or, use slash commands" when an example string does not match; its documentation warns of "Too many optionals" and "Options with a dynamic number of spaces (such as strings)" [C19, C20]. A left-to-right binder over the declared options has no such cliff.
- **Mixed response types after the first response.** Kord Extensions' docs: "Responding to an Interaction using the wrong response type, after you make an initial response" [C32]. Ephemeral/public must be a property of the definition and of the first acknowledgement.
- **Message context menus invert who the author is** (discord.py `Context.author`). Keep `invoker` and `target` as separate context properties.
- **Text commands are second-class in the frameworks that grew up with slash.** Kord Extensions: "Kord Extensions' users and developers don't regularly use or test chat commands" [C35]. The typed path here is a fallback, but MagicBot's mention mode makes it a real path, so it needs its own Level 2 tests.
- **Ids joined with a separator.** DIH4JDA's `ComponentIdBuilder` joins with `":"` and splits with `String.split`; an argument containing the separator corrupts routing. Component ids are capped at 100 characters, so state belongs in storage keyed by a short id when it will not fit.
- **Dropped state at restart.** discord.py views default to a 180-second timeout and need explicit re-registration; a routed `custom_id` handler registered at start-up survives restarts because Discord keeps the message (sibling findings, section 3.2).
- **Today's defects, by symbol, that the rebuild must not reproduce:**
  - `bottools.commands.Command` keeps the current invocation in instance fields (`guild`, `member`, `channel`, `message`, `args`, `eb`, `reply`, the private `scEvent`, `messageEvent`) on singletons held by `Bot.commands`. Two simultaneous invocations of one command overwrite each other, and `Command.reply` calls `complete()` on a single-use `ReplyCallbackAction`, blocking the event thread.
  - `Command.invoke(CommandContainer)` runs the sub-command and then falls through to `this(args)`, running the parent as well.
  - `SubCommand.getParent(steps)` has no base case for `steps <= 1`.
  - `Command`'s `init` block calls the open `description` and `helpMessage` before subclass initialisation completes.
  - `Parser.parse(raw)` uses a global `triggers` list, lowercases the whole message, collapses spaces and drops every token starting with `@` or `#`; `Parser.parse(SlashCommandInteractionEvent)` flattens options to `asString` values, losing option names. `Option(type: String)` maps unknown type names to STRING and handles only user, role, integer and channel besides string (Discord has nine non-structural option types).
  - GKB2 `CommandFactory.getCommand` casts every event to `GenericCommandInteractionEvent`, stores it in the companion's `lateinit var event`, defers every reply unconditionally, and returns a Spring singleton.
  - GKB2's `PropertyCommand` and `DataAccessCommand` share one mutable `path` field across invocations (`DataAccessCommand.path`), so concurrent admin `get`/`set` calls race.

## 6. Recommendation for this repo

Take discord.py's shape (one handler, one context, `defer` that knows its origin), Kord Extensions' shared option schema and ephemeral/public declaration, Sapphire's identifier-plus-presentation errors and per-message prefix hook, and BotCommands' replaceable messages interface and persistent/ephemeral component split. Do not take BotCommands' regex grammar, Sapphire's pull-based argument API (it prevents generated help), or discord.py's "typed form is the slash subset" rule.

1. **Tree.** Sealed `CommandNode` (`Group`, `Leaf`, `UserMenu`, `MessageMenu`), immutable, built by DSL builders whose `build()` returns `Result`. The builder is the only mutable object. The leaf holds `brief`, optional `details`, an ordered `List<Option<*>>`, the response mode (public or ephemeral), the acknowledgement mode (auto after a deadline, or manual), the preconditions, and a `suspend (CommandContext) -> Unit` handler. `build()` runs the platform validator (depth three, 25 per level, names, sizes, counts). The slash projection is a pure function from the tree to JDA `CommandData`. A group has no handler; a typed `!dota` alone renders help for the group (discord.py's `fallback` is the slash-only workaround and is not needed).
2. **Options.** One declared schema per leaf, usable as a typed key: `val person = userOption("person", "…", required = false)`, read in the handler as `ctx[person]`. The definition holds the option; each invocation holds the values (this is Kord's `Arguments` idea without the per-call object). Option kinds are a sealed type covering Discord's types plus an optional `greedy` flag for a trailing string. The existing `Option` helpers stay as factories.
3. **Typed parser.** A pure function `(tree, aliasTable, text, resolver) -> Result<ParsedInvocation, ArgumentError>`. The resolver is a port so tests supply fakes.
   - Path resolution: match the longest sequence of leading tokens against canonical paths and aliases, case-insensitively.
   - Arguments: quote-aware tokens (with smart quotes), positional binding in declaration order, `name=value` and `--name value` accepted for any option, one trailing greedy string, mentions and snowflakes for user/role/channel options, message attachments for attachment options. Do not lowercase arguments and do not strip `@`/`#` tokens. When an optional user option is omitted, default to the invoker, as `targetMember` does today.
   - Choices are validated and the error lists them; autocomplete has no typed counterpart.
   - `ArgumentError` is a sealed hierarchy (missing, unparseable with expected kind, out of range, not in choices, too many, unclosed quote, unknown sub-command with candidates).
4. **Prefix policy.** A `suspend (Message) -> TypedTrigger?` hook, with three built-in modes: mention (always), DM bare prefix (always), guild bare prefix (opt-in, per-guild prefix, warns at start-up when the intent is missing). This is Sapphire's `fetchPrefix` and BotCommands' `TextPrefixSupplier` with the platform split built in.
5. **Aliases.** An immutable alias table `Map<List<String>, CommandPath>`; the `x and "y" becomes "z"` DSL becomes sugar that adds `[x, y] -> [z]`. Aliases are typed-only by default and excluded from registration; a slash-visible alias is an explicit per-alias flag that counts against the validator. The old Dota 2 names are typed aliases (`[dota, setid]` -> `[dota, id, set]`, and so on). Help lists each alias under its canonical path.
6. **Context.** `CommandContext` is an interface created once per event and never shared. It carries an `Invocation` sealed type (slash, typed, user menu, message menu), `invoker`, nullable `member`/`guild`, `channel`, `target` (menus only), the resolved path and the alias used, the bound values and the locale. Its reply surface is `reply`, `defer`, `edit` and `followUp`, with the rules discord.py's `Context.send` documents: first response is the initial response; after a deferral, the first reply edits the loading message; later replies are follow-ups; after the token expires, a channel message. State is an atomic acknowledgement state (unacknowledged, deferred, responded) so a handler reply and a deadline timer cannot both acknowledge. In typed invocations `defer` sends a typing indicator, and `ephemeral` cannot be honoured (see Gaps).
7. **Acknowledgement.** The leaf declares `response = Public | Ephemeral`. Under the automatic mode, the dispatcher starts a timer against the platform's 3-second limit that calls `ctx.defer()` with the declared mode if the handler has not responded; under the manual mode the handler is responsible. Because no surveyed framework does this, it needs a Level 2 test with a controllable clock before it is relied on.
8. **Preconditions.** An immutable list on the definition, each `suspend (CommandContext) -> Result<Unit, Denial>`, run once by the dispatcher for slash and typed alike. Built-ins: guild-only, user permissions, bot permissions, owner, cooldown, guild-enabled (reads the guild settings port). `UserPermissions` also feeds `default_member_permissions` at registration, but enforcement never relies on it. Per-guild enable/disable is a precondition and a help filter; it does not re-register commands.
9. **Errors.** `Denial` and `ArgumentError` are data. A single `CommandMessages` interface with an English default turns them into message specs (BotCommands' `BotCommandsMessages` shape), including unknown command (with suggestions in mention mode, silent in bare-prefix mode so a shared `!` does not generate noise), missing permissions, cooldown and component-expired. Handler exceptions are caught at the dispatcher boundary, logged through slf4j, answered with the generic message, and `CancellationException` is rethrown.
10. **Help.** A pure `HelpRenderer` from `(tree, path, ctx)` to a help page: brief and details from the node, the usage line from the options (`<required>`, `[optional]`, `a|b|c`), aliases, and only nodes whose preconditions the invoker passes. Slash `/help [path]` and typed `!help dota id` use it.
11. **Components.** A route registry: `custom_id = route + separator-escaped key` with a codec that rejects ids over 100 characters, handlers registered at start-up by plugins, and short-lived waits kept in memory only for a bounded time. State that does not fit goes to a storage port under a short id. Handlers get a `ComponentContext` with the same reply surface. An unknown route answers with the `componentExpired` message.
12. **Testing.** Handlers and preconditions run against a `FakeCommandContext` that records acknowledgements and replies; the typed parser and help renderer are pure functions; the registration projection is snapshot-tested against JDA's `CommandData` JSON. These are Level 2 tests without Discord. Whether the fake ships as a test-fixtures artifact for plugin authors is a later call.

I would reject two obvious options. One is "hybrid by subset" (discord.py's rule): MagicBot's mention mode is a real path and should keep greedy strings and named arguments. The other is "two handlers per command" (Sapphire, BotCommands, Chewtils): it doubles every plugin command and re-creates the drift in the tracker above.
