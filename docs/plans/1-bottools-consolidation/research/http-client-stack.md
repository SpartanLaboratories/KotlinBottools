## 1. Question

Which HTTP client, JSON library, response cache, call-budget mechanism and feed parser should the game-API providers (OpenDota first, then Marvel Rivals, Path of Exile 2, No More Room in Hell), the weather plugin and the feeds plugin share, and how are they tested against recorded responses?

An answer has to satisfy these facts about the work:

- Every provider call passes through one cache and one per-provider budget, and JSON maps to Kotlin types.
- The library is built with Kotlin 2.2.x on JDK 21, with coroutines 1.10.2, and pins JDA 6.7.0. JDA brings `com.squareup.okhttp3:okhttp-jvm:5.5.0` onto every consumer's runtime classpath.
- A library release must not put a newer Kotlin standard library, `kotlin-reflect` or a second HTTP engine on consumers without need. Exposed and Hoplite were rejected for that reason.
- Library code logs through the slf4j API only.
- Discord's own REST rate limits belong to JDA. The budget here is for third-party game and weather APIs.
- The job scheduler runs fixed-delay loops with full-jitter backoff, and a provider's rate-limit answer reaches it as a `RetryAfter(duration)` outcome. The cache and budget sit underneath that.
- Game data comes only from documented JSON APIs. Unirest, jsoup and skrapeit leave; only a feed parser remains.

## 2. Bottom line

- **HTTP: use OkHttp directly, at the version JDA already brings (`okhttp-jvm` 5.5.0), behind an internal `HttpTransport` port.** It is already on every consumer's runtime classpath as a JDA `api` dependency, so the stack adds no HTTP artifact. The suspend bridge is the 15-line `Call.executeAsync` pattern from `okhttp-coroutines`, copied rather than depended on (that artifact requires coroutines 1.11.0). Ktor 3.6.0's OkHttp engine would add 19 artifacts and force coroutines 1.11.0 and `kotlin-stdlib` 2.3.21 at runtime; the JDK `HttpClient` has no DNS hook, which the feeds plugin needs against admin-supplied URLs.
- **JSON: `kotlinx-serialization-json` 1.9.0, with the serialization compiler plugin at the Kotlin 2.2.x version, on internal `@Serializable` wire types that are mapped to public domain types.** 1.9.0 is the newest release built for Kotlin 2.2 (stdlib 2.2.0, metadata 2.2.0). 1.10.0 and 1.11.0 carry metadata 2.3.0 (readable by a 2.2.x compiler by the next-version rule), and 1.12.0 needs Kotlin 2.4. Jackson is rejected: JDA's copy is a runtime-only implementation detail, and `jackson-module-kotlin` needs `kotlin-reflect`.
- **Cache: Caffeine 3.3.1 `AsyncCache`, one per provider, with per-endpoint TTL through `Expiry`, a `maximumSize` bound, and loads run in a library-owned scope.** Await shared loads with `asDeferred().await()`, never `CompletionStage.await()`, because the latter cancels the shared load when one caller cancels. Failures are not cached (Caffeine removes failed futures); a confirmed miss is cached briefly as a value.
- **Budget: in-house, per provider, shaped as `await`-then-`complete(response)` like Kord's `RequestRateLimiter`.** It holds several token-bucket windows (per-minute and per-day), reserves a slot under a mutex and delays outside it, accepts a pause from `429`/`Retry-After`, and reconciles with server-reported remaining counts. Bucket4j 8.21.0 (single jar, no dependencies) is viable but covers only the token arithmetic. The layering is cache, then budget, then transport, so cache hits cost nothing and coalesced callers share one token.
- **Feeds: Rome 2.1.0 behind an internal `FeedParser` port, fed bytes by the shared client; never `XmlReader(URL)`.** Rome is the incumbent and the broadest-coverage JVM parser, but its last release was 2023-03-12 and its last commit 2023-06-21, so the port keeps it replaceable. The named alternative is `rssreader` 3.12.0 (zero dependencies, MIT, 2025-12-01).
- **Tests: a fake `HttpTransport` at Level 2; OkHttp `MockWebServer` (`mockwebserver3` 5.5.0) at Level 3, serving recorded JSON fixtures; live calls opt-in.** Ktor `MockEngine` does not apply without Ktor. WireMock 3.13.2 is heavier than the need; its 4.x line is still a beta.

## 3. Findings

Tiers: **Consensus** = official documentation, a standard or several independent sources; **Practice** = what mature libraries visibly do; **Opinion** = one source; **Measured** = read or decoded by me from published artifacts, reproducible by anyone.

### F1. JDA fixes OkHttp, and what else it brings (Measured; JDA 6.7.0)

- JDA 6.7.0's POM declares `okhttp-jvm` 5.5.0 and `slf4j-api` 2.0.19 at compile scope and `jackson-databind` 2.22.2 at runtime scope. Its `build.gradle.kts` declares `api(libs.okhttp)` and `implementation(libs.bundles.jackson)`, with `okhttp = "com.squareup.okhttp3:okhttp-jvm:5.5.0"` in `gradle/libs.versions.toml`. (claim 1.)
- So OkHttp is part of JDA's public contract (`JDABuilder.setHttpClient(OkHttpClient)` and `setHttpClientBuilder(OkHttpClient.Builder)` take OkHttp types), while Jackson is an `implementation` detail that reaches consumers only as a runtime artifact.
- The JDA closure resolved from POMs is 17 artifacts. It contains no cache library, no rate-limiting library, no feed parser and no kotlinx-serialization.

### F2. Ktor 3.6.0 against OkHttp-direct (Measured POMs; Consensus for the engine table)

- `ktor-client-okhttp-jvm` 3.6.0 depends on `okhttp-jvm` 5.5.0 (so it unifies with JDA), `okio-jvm` 3.18.2, `kotlinx-coroutines-core-jvm` **1.11.0** and `kotlin-stdlib` **2.3.21**, plus `ktor-client-core-jvm`. (claim 2.)
- Resolving the compile and runtime POM closure of `ktor-client-okhttp-jvm` 3.6.0 gives 22 artifacts. Beyond what JDA already brings (OkHttp, okio, slf4j-api, stdlib), it adds 12 `ktor-*` artifacts (`client-core`, `client-okhttp`, `events`, `http`, `http-cio`, `io`, `network`, `serialization`, `sse`, `utils`, `websocket-serialization`, `websockets`), two `kotlinx-io` artifacts, `kotlinx-coroutines-core-jvm`, `kotlinx-coroutines-slf4j`, `kotlinx-serialization-core-jvm` and `org.jetbrains:annotations` 23.0.0: 19 new artifacts. The OkHttp-direct stack with JSON, cache and feed parser adds nine (F10).
- Ktor releases move the runtime floor with every minor: 3.3.3 uses stdlib 2.2.21, coroutines 1.10.2 and `okhttp-jvm` 5.2.1; 3.4.3 uses stdlib 2.3.0, coroutines 1.10.2 and `okhttp-jvm` 5.3.2; 3.5.0 and 3.6.0 use coroutines 1.11.0. `ktor-client-core-jvm` 3.6.0 carries Kotlin metadata 2.3.0 (readable by a 2.2.x compiler; decoded from `io.ktor.client.HttpClient`). Ktor 3.2.x depends on `okhttp` 4.12.0 and so would sit beside JDA's `okhttp-jvm` 5.5.0 as a different artifact. (claim 2.)
- Ktor's engine documentation: CIO "currently supports HTTP/1.x only"; the Apache5 and OkHttp engines support HTTP/2; the Java engine builds on the JDK client. (claim 3.) CIO has the lowest automatic-selection priority. Choosing among CIO, OkHttp and Java would still leave the question of which pool, DNS and TLS stack runs, and the OkHttp engine answers it with the same OkHttp already present. Ktor's genuine advantage is Kotlin Multiplatform reach, which is not a requirement here.
- What Ktor would add that this work needs: little. Content negotiation replaces one `Json.decodeFromString` call; `HttpTimeout` and `HttpRequestRetry` duplicate OkHttp's own timeouts and the scheduler's backoff; `MockEngine` is covered by F9.

### F3. OkHttp as a direct dependency (Consensus for behaviour; Measured for source)

- OkHttp 5.5.0 states it is "efficient by default": HTTP/2 sharing of a socket per host, connection pooling, "Transparent GZIP", and silent recovery from common connection problems. It also states "Cache is not an interface with alternative implementations", so its disk HTTP cache is not a substitute for the response cache here (claim 4). Its `okhttp-jvm` 5.5.0 classes carry Kotlin metadata 2.1.0, readable by any 2.2.x compiler.
- The suspend bridge is small. `okhttp3.coroutines.executeAsync` in `okhttp-coroutines` 5.5.0 is `suspendCancellableCoroutine` with `continuation.invokeOnCancellation { this.cancel() }` around `enqueue(Callback)`, closing the response if the continuation was already cancelled (claim 5). The artifact itself requires `kotlinx-coroutines-core` 1.11.0 at runtime and `kotlin-stdlib` 2.1.21/2.2.21 (POM and Gradle module), so it is copied, not depended on.
- Defaults that matter for a client: `Dispatcher.maxRequests = 64`, `Dispatcher.maxRequestsPerHost = 5`, `connectTimeout`, `readTimeout` and `writeTimeout` each 10 000 ms, and `callTimeout = 0` (no overall deadline) (claim 6). `callTimeout` has to be set explicitly, and the per-host limit of 5 makes a burst against one provider queue inside OkHttp.
- `okhttp3.Dns` is a `fun interface` whose `lookup(hostname)` result is what OkHttp connects to, so a resolver that refuses loopback, link-local and private addresses guards every connection including redirects (claim 7). `Headers.getInstant(name)` parses an HTTP-date, which covers the date form of `Retry-After`.
- The JDK `HttpClient.Builder` at `jdk-21+35` exposes `cookieHandler`, `connectTimeout`, `sslContext`, `sslParameters`, `executor`, `followRedirects`, `version`, `priority`, `proxy`, `authenticator`: no DNS hook and no interceptors (claim 8). Its `send`/`sendAsync` Javadoc gives cancellation only as best effort ("No guarantee is made as to exactly when the cancellation request may be taken into account"). The Javadoc I read does not mention response decompression; I did not test whether it gunzips (Gap).

### F4. JSON: kotlinx-serialization against Jackson (Consensus for versions; Measured for metadata)

- `kotlinx-serialization-json` on Maven Central: latest 1.12.0 (2026-10-19). The POMs name the stdlib each release was built with: 1.8.1 `kotlin-stdlib` 2.1.20; **1.9.0 2.2.0**; 1.10.0 2.3.0; 1.11.0 2.3.20; 1.12.0 2.4.10. Decoded `@Metadata` `mv` of `kotlinx.serialization.json.Json` in the published jars: 1.9.0 `[2,2,0]`; 1.10.0 and 1.11.0 `[2,3,0]`; 1.12.0 `[2,4,0]` (claim 9). The 1.9.0 changelog says "This release updates Kotlin version to 2.2.0". A 2.2.x compiler reads metadata up to 2.3.0 (the rule stated in `jda-and-coroutine-bridge.md`, claim 3 there), so 1.9.0 to 1.11.0 are readable and 1.12.0 is not.
- The serialization compiler plugin ships with Kotlin: the README says new plugin versions "are released in tandem with each new Kotlin compiler version" and the Gradle line is `kotlin("plugin.serialization") version "<the Kotlin version>"` (claim 10). It is applied to the modules that declare wire types; it adds no runtime dependency beyond `kotlinx-serialization-core`.
- The JSON settings an API client needs are all stable options: `ignoreUnknownKeys` (default is to fail on unknown keys), `explicitNulls = false`, `coerceInputValues` (claim 11). `Json.decodeFromStream(InputStream)` is annotated `@ExperimentalSerializationApi` in both 1.9.0 and 1.11.0 (claim 12), so a library that avoids opt-ins reads the body to a `String` under a size cap and calls `decodeFromString`.
- 1.11.0 adds a public `JsonException` hierarchy and an experimental `exceptionsWithDebugInfo` switch, because exception messages historically "included the input Json itself"; on 1.9.0 a decode failure message can contain the payload, so the library must not log `SerializationException.message` raw. (1.11.0 changelog, claim 12.)
- Jackson: `jackson-databind` 2.22.2 reaches consumers only because JDA declares it at runtime scope. Relying on it from library code would make a JDA internal change a binary break. `jackson-module-kotlin` 2.22.4 requires `jackson-databind` 2.22.4 (above JDA's 2.22.2) and `kotlin-reflect` 2.1.21 (Gradle module). Reflection-based binding also fails at run time rather than compile time, which sits badly with typed providers. Rejected.

### F5. Response cache: Caffeine (Consensus for the library; Measured for the version and source)

- Caffeine 3.3.1: Apache-2.0, Java 11 bytecode (`org.gradle.jvm.version` 11), compile dependencies `org.jspecify:jspecify` 1.0.1 and `com.google.errorprone:error_prone_annotations` 2.50.0 (annotation-only), jar 1.09 MB. It is "a high performance, near optimal caching library" with size-based eviction on frequency and recency, time-based expiration, and a community Kotlin coroutines extension list. (claim 13.)
- `AsyncCache.get(key, mappingFunction)` is documented as: "The entire method invocation is performed atomically, so the function is applied at most once per key. If the asynchronous computation fails, the entry will be automatically removed from this cache." (claim 14.) That is single-flight coalescing and no caching of failures, built in.
- `Expiry` works for async caches: `Async.AsyncExpiry` wraps the delegate, gives an in-flight entry a reserved maximum duration, and asks the delegate for the TTL when the future completes (claim 15). So a per-endpoint TTL can be a function of the key (`CacheKey.endpoint.ttl`) or of the value. Size is a plain `maximumSize(long)`, or `weigher` with a maximum weight; time is injectable through `Caffeine.ticker(Ticker)`; expiry is evaluated "with periodic maintenance during writes and occasionally during reads", and a `Scheduler` is needed for prompt removal (claim 16). The default executor for async work is `ForkJoinPool.commonPool()`, overridable with `Caffeine.executor`.
- Coroutines hazard: `CompletionStage<T>.await()` in kotlinx.coroutines 1.10.2 is "intended to be used with one-shot futures, so on coroutine cancellation the CompletableFuture ... is cancelled. If cancelling the given stage is undesired, `stage.asDeferred().await()` should be used instead." (claim 17.) A cache future is shared by definition, so the first cancelling caller must not cancel it. `CoroutineScope.future` and both awaiters live in `kotlinx-coroutines-core` on the JVM at 1.10.2 (no extra artifact).
- Logging: Caffeine logs through `System.Logger` (`BoundedLocalCache.logger`), not slf4j, so its rare warnings reach slf4j only if the application installs a `System.Logger` bridge. This does not violate the slf4j-only rule for library code (the rule governs code written here), but it is worth a line in the README.
- Aedile 3.0.4 (`com.sksamuel.aedile:aedile-core`, 2026-05-03) wraps Caffeine for coroutines: it depends on Caffeine 3.2.4, coroutines 1.10.2 and stdlib 2.2.21. It works with the pins, but it fixes a Caffeine version below 3.3.1 and wraps a four-line need; not adopted.
- Memory bound: cache decoded, trimmed wire-to-domain values, not raw bodies. With `ignoreUnknownKeys` the retained object holds only the modelled fields, so entries are small and `maximumSize` per cache is an adequate bound. A weigher is the escape hatch for any endpoint that returns a large modelled document (OpenDota's full match document is the likely one).

### F6. Call budget: what the providers publish (Measured from source; hosts for docs unreachable)

- **OpenDota** (`odota/core` @ `449fb7b`, `config.ts`): `API_FREE_LIMIT: "3000"` ("number of api requests per day before 429 is returned. If using an API key, calls over this are charged."), `NO_API_KEY_PER_MIN_LIMIT: "60"`, `API_KEY_PER_MIN_LIMIT: "300"`, `ENABLE_API_LIMIT: ""` (limits enforced only when set) (claim 18). The middleware in `svc/web.ts` keys the counters by API key, or by client IP when there is no key; counts per wall-clock minute and per UTC day (`getStartOfBlockMinutes(1, 1)`, `getEndOfDay` in `svc/util/time.ts`); sets `X-Rate-Limit-Remaining-Minute` always and `X-Rate-Limit-Remaining-Day` for non-key requests; and answers HTTP 429 with a JSON body `{"error": "minute rate limit exceeded"}` or `"daily api limit exceeded"`. It does not set `Retry-After` (a search for `retry-after` under `svc` finds nothing). These are repository defaults; the deployed values and the public documentation (`docs.opendota.com`, `api.opendota.com`) were unreachable, so the production numbers are unverified. A 2018 OpenDota blog post states a 50 000-calls-per-month free tier with no key, which the current source no longer expresses; treat published numbers as moving.
- **Open-Meteo** (weather): the terms page, as returned by a web search excerpt (the host is unreachable from here), gives the free non-commercial tier as fewer than 10 000 calls per day, 5 000 per hour and 600 per minute, requires attribution, and needs no key (claim 19, unverified at source).
- **Path of Exile**: the official developer documentation, as returned by a search excerpt (host unreachable), defines `X-Rate-Limit-Rules` (a comma-delimited list of rules such as ip, account, client), a per-rule `X-Rate-Limit-{rule}` header (max hits, period seconds, restriction seconds) and `X-Rate-Limit-{rule}-State`, and warns that details "may change without notice" (claim 20, unverified at source). A budget for this provider cannot be a constant; it must be adjustable from response headers.
- **`Retry-After`** takes either delay-seconds or an HTTP-date, and is used on `429` and `503` (claim 21; the RFC hosts are unreachable, so this is read from MDN's content repository, which tracks RFC 9110 and 6585).
- Consequence: three shapes of limit exist among the four-plus targets: static per-minute plus per-day windows (OpenDota, Open-Meteo), dynamic header-declared rules (Path of Exile), and unknown or key-based ones (Marvel Rivals, No More Room in Hell: not researched here). A budget abstraction has to take both a configured list of windows and header feedback.

### F7. Token buckets: Bucket4j and Resilience4j against in-house (Measured)

- **Bucket4j 8.21.0** (`bucket4j_jdk17-core`, Apache-2.0, no dependencies in the POM, Java 17 build): `Bucket.builder().addLimit(...)` can stack several bandwidths (minute and day). `tryConsumeAndReturnRemaining(long)` returns a `ConsumptionProbe`; `consumeIgnoringRateLimits(long)` documents that it "describes the amount of rate limit violation in nanoseconds" and lets available tokens go negative, which is a usable reservation (debt) primitive; `forceAddTokens` refunds. The library is Java, blocking by design for local buckets (async is for distributed back-ends), and has no notion of a server-reported remaining count, so the glue for FIFO waiting, wait caps, cancellation refunds, pause-until and header reconciliation is still ours. (claim 22.)
- **Resilience4j `RateLimiter` 2.4.0**: configured by one `limitForPeriod` and one `limitRefreshPeriod` per limiter, with a `timeoutDuration`; two windows need two limiters. It depends on `resilience4j-core` and `slf4j-api` 1.7.30. (claim 23.) It is built for protecting your own code from overuse, not tracking someone else's quota; not adopted.
- **Comparable practice is in-house and header-driven.** JDA 6.7.0 ships `SequentialRestRateLimiter` implementing `RestRateLimiter` and handles `Retry-After` from 429 responses; Kord `main` ships `RequestRateLimiter` (`suspend fun await(request): RequestToken`) with `ExclusionRequestRateLimiter` and `ParallelRequestRateLimiter`, parsing `Retry-After`, `X-RateLimit-Remaining` and `X-RateLimit-Reset-After`. Neither uses Bucket4j. (claim 24.)

### F8. Feed parsing: Rome and the alternatives (Measured; Practice)

- **Rome 2.1.0** (`com.rometools:rome`): the latest on Central (`lastUpdated` 2023-03-12). Apache-2.0. Compile dependencies `rome-utils` 2.1.0, `jdom2` 2.0.6.1, `slf4j-api` 2.0.6 (parent POM); Java 8 target (2.0.0 required Java 11, 2.1.0 reverted it). The repository's latest ten commits (read 2026-10-20) are all dependency bumps and a README polish, the newest dated 2023-06-21. It is not abandoned in the sense of being broken, but it has had no functional change since March 2023. No advisory for Rome 2.1.0 turned up in a search; `jdom2` 2.0.6.1 is the release that CVE-2021-33813 lists as the fix. (claim 25.)
- Security defaults are right: `SyndFeedInput.setAllowDoctypes` Javadoc says "Since ROME 1.5.1 we fixed a security vulnerability by disallowing Doctype declarations by default", and `WireFeedInput` turns off external general and parameter entities and external DTD loading. The README warns that `XmlReader(URL)` "is deprecated and works only for simplest cases. Please consider using a separate library for fetching the feed." (claim 26.) Rome therefore fits a design where the shared client fetches and Rome parses a stream.
- Kotlin fit: a Java API with platform types and mutable beans (`SyndFeed`, `SyndEntry`). It stays behind an internal port that returns an immutable Kotlin `FeedEntry`/`Feed`; the legacy `RssService` in this repository already shows the pattern is only a few lines.
- **Alternatives:** `rssreader` 3.12.0 (`com.apptasticsoftware:rssreader`, 2025-12-01, MIT, "zero 3rd party dependencies", Java 11, reads from an `InputStream`) is the maintained, dependency-free option; its format coverage (RSS 0.9x/1.0 and malformed-feed tolerance) is narrower than Rome's decades of fixtures suggest, which I did not test. `com.prof18.rssparser:rssparser-jvm` 6.1.8 (Kotlin multiplatform) needs `kotlin-stdlib` 2.4.10, coroutines 1.11.0 and `okhttp-jvm` 5.4.0 (its Gradle module), so it is out. An in-house StAX parser for RSS 2.0 and Atom 1.0 avoids a dependency but takes on date-format and encoding tolerance; not recommended while Rome works. (claim 27.)

### F9. Testing: Ktor MockEngine, MockWebServer, WireMock (Practice; Measured)

- The organisation's levels: Level 2 "mock all external calls"; Level 3 "boundary conditions and data exchange with actual or simulated external interfaces". That maps to a fake at the `HttpTransport` port for Level 2 (no sockets; fixtures served by file name) and a loopback HTTP server for Level 3.
- **Ktor `MockEngine`** (Kord uses it: `rest/src/commonTest/.../MessageRequests.kt` builds `HttpClient(MockEngine { ... })`, and Kord's build declares `libs.ktor.client.mock`) tests Ktor code. It has no meaning for an OkHttp transport.
- **OkHttp `MockWebServer`**: `mockwebserver3` 5.5.0 resolves to five artifacts (itself, `okhttp-jvm`, `okio-jvm`, annotations, stdlib), all already on the classpath. Its README: "Because it exercises your full HTTP stack, you can be confident that you're testing everything. You can even copy & paste HTTP responses from your real web server to create representative test cases," including 500s and slow responses. It is what exercises the real adapter: gzip, status handling, `Retry-After` and header parsing, `callTimeout`, redirects. (claim 28.)
- **WireMock**: `org.wiremock:wiremock` 3.13.2 is the latest stable and 4.0.0-beta.40 (2026-10-07) is the latest overall; its README lists "Record/playback of stubs". It brings a web-server stack to the test classpath and adds a second recorded-response format. The recorded-fixture need is met by plain JSON files under `src/test/resources`, so it is not adopted.
- Time: Caffeine takes a `Ticker`, the budget takes an injected clock, and `delay` runs on `kotlinx-coroutines-test`'s virtual time; the three must share one fake clock in tests (Pitfall 7).

## 4. How comparable projects do it

- **Kord (`kordlib/kord`, `main` @ `db459ec`).** A Kotlin Discord library on Ktor 3.4.0, kotlinx-serialization 1.10.0 and coroutines 1.10.2 (`gradle/libs.versions.toml`). Rate limiting is its own: the `RequestRateLimiter` interface (`suspend fun await(request: Request<*, *>): RequestToken`, plus the inline `consume` helper that completes the token with the response), `HttpResponse.globalSuspensionPoint(clock)` reading `Retry-After`, and `X-RateLimit-Remaining` / `X-RateLimit-Reset-After`. Tests use `MockEngine`. Relevance: the `await` / `complete(response)` pair is the shape recommended for the budget; the Ktor choice is justified there by Kord's multiplatform scope.
- **JDA 6.7.0** itself: OkHttp `api` dependency, Jackson `implementation`, in-house `SequentialRestRateLimiter`. A library in the same tree that chose neither Ktor nor a rate-limit library.
- **Bucket4j `master` @ `959d97c`**: `Bucket.tryConsumeAndReturnRemaining`, `consumeIgnoringRateLimits`, `forceAddTokens`; the credible off-the-shelf alternative to the in-house budget (F7).
- **BotCommands** and **jda-ktx** (from `jda-and-coroutine-bridge.md`) both write their own `await` rather than lean on an HTTP framework; the same instinct applies to `Call.executeAsync`.

## 5. Pitfalls and regrets

1. **Awaiting a shared future with `await()`.** `CompletionStage.await()` cancels the future when the awaiting coroutine is cancelled (F5). With a cache this cancels the load for every other caller and removes the entry. Run the load in a library-owned scope (`scope.future { ... }`, with a `SupervisorJob`) and await with `asDeferred().await()`.
2. **`runCatching` around suspend calls.** It swallows `CancellationException` (see `idiomatic-kotlin-api-shape.md`). The provider boundary returns `Result`, so catch only the transport and decode failures it maps (`IOException`, `SerializationException`, and the library's own failures) and let cancellation propagate.
3. **Caching failures or confirmed misses wrongly.** Caffeine drops failed futures, which is right for 5xx, timeouts and 429 (retrying later is the scheduler's job). A confirmed "no such account" is a legitimate value; cache it for a short time (tens of seconds to a few minutes) as `Missing`, or repeated `setid` guesses spend the budget. Do not cache `RateLimited`.
4. **Counting coalesced and cached calls.** The budget must be acquired inside the load, after the cache miss, so a hit costs nothing and N concurrent callers for one key cost one token. Subscriptions are per guild and account links are global per user, so one player tracked by many guilds is one call per tick; the cache key must be `(provider, endpoint, canonical params)` with no guild in it.
5. **Local windows do not match the server's.** OpenDota counts per wall-clock minute and UTC day and is keyed by IP, so a restart forgets what was already spent today, and a second process on the same host shares the same IP quota. A greedy token bucket is a safe lower bound, but the server's remaining counter must be allowed to lower the local balance, and a `429` must pause the provider until the minute or day boundary when no `Retry-After` is sent (OpenDota sends none). With an API key, calls above the free limit are billed, so a keyed configuration needs a hard daily stop.
6. **Unbounded waiting.** An interactive command (`!lastgame`) must not queue behind a backlog. The budget needs a wait cap per call (fail fast with a typed `BudgetExhausted` or `RateLimited` failure carrying the delay) and a reserved share for interactive calls against background tracker polls. Both are policy parameters.
7. **Three clocks.** Caffeine's `Ticker`, the budget's clock and coroutine `delay` are independent. Tests that fake one and not the others pass for the wrong reason. Inject one `TimeSource`-style fake into all three and drive it from `runTest`'s scheduler.
8. **OkHttp defaults.** `callTimeout` is 0 (no overall deadline), and `maxRequestsPerHost` is 5, so a burst to one provider queues inside OkHttp invisibly to the budget; size it from the budget. Cap the response size before `body.string()`, because OkHttp has no response limit.
9. **SSRF and entity attacks in the feeds plugin.** Feed URLs come from guild administrators. Allow only `http`/`https`, resolve through a `Dns` that rejects loopback, link-local and private ranges (so redirects are covered), cap redirects and body size, set short timeouts, and keep Rome's DOCTYPE ban at its default. The JDK `HttpClient` offers no equivalent DNS hook.
10. **Leaking stack types into the public API.** `@Serializable` wire classes in a public signature make consumers compile against a serialization runtime and freeze the wire shape into the API; `OkHttpClient` or Caffeine types in signatures do the same. Keep them `internal`, expose domain types and the ports.
11. **Version drift between the library's OkHttp and JDA's.** If `bottools-stats` declares `okhttp-jvm` at a different version from JDA's, Gradle resolves the higher one and the JDA-tested pairing is lost. Declare the same version as JDA's `libs.okhttp` (5.5.0) and bump it only with JDA, as one reviewed change.
12. **Taking the newest of everything.** serialization 1.12.0 and `jda-ktx` 0.15.0 need a 2.4 compiler; Ktor 3.5.0+ needs coroutines 1.11.0. Each is a reason to stay one step back until the toolchain moves.
13. **A rate-limit library hides the real problem.** The hard parts of this budget are fairness, cancellation, wait caps and header feedback, not the refill arithmetic. Bucket4j's value (precise integer math) is the easy half.

## 6. Recommendation for this repo

**Shape (modules and visibility).** Put the shared client stack in `bottools-stats`, with `bottools-plugins` (weather, feeds) using it through its public ports. Declare every stack library as `implementation`; none appears in a public signature, public `inline` body, supertype or default argument.

- Public ports, in `bottools-stats` (tier to be assigned by the API design; the cache, budget and transport seams are `@SupportedExtension` candidates): a provider call facade that takes an `Endpoint` (provider id, name, TTL policy, cost) and returns `Result<T>`; `HttpTransport` (`suspend fun execute(request): Result<TransportResponse>`, expressed in the library's own request and response types); a `ResponseCache` and a `CallBudget` interface, each with the default implementation below. Policy is constructor-parameterised and defaulted: windows, safety margin, wait caps, TTLs, cache size.
- Default `HttpTransport`: `OkHttpTransport`, one shared `OkHttpClient` (`okhttp-jvm` 5.5.0, same version as JDA), `callTimeout` set, `Dispatcher.maxRequestsPerHost` sized from the budget, a `Dns` guard that is on for feed URLs. Accept a `Request` through `executeAsync` copied from OkHttp (cite `okhttp3.coroutines.executeAsync` in a code comment).
- JSON: `internal` `@Serializable` wire types per provider, decoded with a single configured `Json { ignoreUnknownKeys = true; explicitNulls = false; coerceInputValues = true }`, from a size-capped `String`, then mapped to public immutable domain types. Pin `kotlinx-serialization-json` **1.9.0**; allow a move to 1.11.0 when it is useful (Json exception structure) since its metadata 2.3.0 is readable, but do not move to 1.12.0 before the compiler is 2.4. Never log `SerializationException.message` raw.
- Cache: one Caffeine `AsyncCache<CacheKey, Outcome<V>>` per provider. `Expiry` returns `key.endpoint.ttl` (constants such as hero lists in hours, profiles in minutes, recent matches in about a minute, `Missing` in tens of seconds; all overridable), `maximumSize` set per provider, a `Ticker` from the injected clock. The load is `scope.future { budget.await(); transport.execute(); decode }` in a library-owned scope; callers await with `asDeferred().await()`. A caller that needs freshness (the tracker) passes a `maxAge`, implemented as an `invalidate` of an older entry before the get.
- Budget: an in-house `CallBudget` with the Kord shape: `suspend fun acquire(cost: Int = 1, lane: Lane, maxWait: Duration): Result<Permit>`, and `Permit.complete(ResponseSignals)` where the signals are `status`, `retryAfter` and a provider-supplied remaining-count reading. Internally: a list of token-bucket windows (for example `60 per minute` and `3000 per day`, set below the published limits by a margin); reservation and deduction under a `Mutex`, with the wait returned and awaited outside the lock (FIFO by reservation, refund on cancellation); a `pauseUntil` set by `429` (from `Retry-After`, HTTP-date or seconds, or from the provider's window boundary when none is sent); and reconciliation that can only lower the local balance. Each provider supplies a small `RateSignals` parser (OpenDota reads `X-Rate-Limit-Remaining-Minute` and `-Day`; Path of Exile reads `X-Rate-Limit-*`). A 429 is returned to the job as `Failure(RateLimited(retryAfter))` so the scheduler maps it to `RetryAfter(duration)`; the client does not retry in a loop. Expose a read-only utilisation figure so the tracker can lengthen its interval as the audience grows, instead of failing.
- Feeds: `FeedParser` port (`parse(bytes, charsetHint): Result<Feed>`) with a `RomeFeedParser` default, `SyndFeedInput` built with DOCTYPEs disallowed. The feeds plugin fetches through the shared client with a conditional GET (`ETag` / `Last-Modified` stored with the cache entry) and passes the stream to the parser. `rssreader` 3.12.0 is the documented swap if Rome becomes a liability.
- Tests: Level 2 uses a `FakeHttpTransport` that serves fixtures from `src/test/resources/fixtures/<provider>/<endpoint>.json` and scripts statuses and headers (429 with and without `Retry-After`, 500, malformed JSON, slow), and fake time. Level 3 runs the real `OkHttpTransport` against `mockwebserver3` with the same fixtures. A recorder that refreshes fixtures from the live API runs only when an environment variable is set and never in CI; secrets (keys) are stripped from recorded URLs and headers before the fixture is written.

**Why this and not the obvious alternatives.**
- Ktor is the obvious Kotlin choice and the one Kord uses, but Kord needs multiplatform reach and has no JDA OkHttp already in its tree. Here the engine would be the OkHttp already present, wrapped in 19 more artifacts that raise the runtime floor to coroutines 1.11.0 and stdlib 2.3.21 on a library pinned to 1.10.2 and Kotlin 2.2.
- The JDK client would remove the OkHttp dependency in principle, but JDA keeps OkHttp on the classpath regardless, so nothing is saved, while the DNS-guard hook, interceptors and a mature mock server are lost.
- Bucket4j is rejected as the default only because it would not remove the code that matters (reservation, caps, cancellation, header feedback), and the in-house arithmetic is short. If a team prefers it, `consumeIgnoringRateLimits` is the primitive to build the reservation on, and the `CallBudget` port is unchanged.

**Decision points the planner can still change without changing the rest:** Bucket4j for the in-house arithmetic; `rssreader` for Rome; serialization 1.11.0 for 1.9.0. Each sits behind a port or a version pin.
